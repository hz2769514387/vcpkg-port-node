## 执行摘要

本项目是目前公开代码托管平台上**唯一**将完整 Node.js（含 V8）编译为可链接静态库并以 vcpkg overlay port 形式交付的项目。技术深度显著高于一般个人项目，CI 体系、符号审计、版本管理等工程化措施有亮点。

但以 vcpkg 官方 curated registry 的准入标准、Node.js 官方的行为一致性要求、以及开源社区大规模采用的门槛来衡量，**当前状态不可直接合并/采用**，存在 **6 项阻断级问题、14 项严重问题、21 项一般问题**。核心矛盾集中在：

1. **V8 内嵌依赖的符号隔离不达标**——V8 头文件和静态库直接安装到全局 `include/` 和 `lib/`，违反 vcpkg 的 Unique File Mapping Rule，与官方 `v8` 端口（虽为僵尸端口）存在文件冲突，且 `abseil`/`highway` 与 vcpkg 同名端口的共存问题仅以"已知限制"声明，未做技术隔离。
2. **CMake 导出规范违规**——导出目标 `node::node` 未使用 vcpkg 要求的 `unofficial-` 前缀，`find_package(node CONFIG)` 会与未来可能出现的官方 Node CMake 配置冲突。
3. **行为一致性未经验证**——`ada-url` 关闭了 `ADA_USE_SIMDUTF`（IDNA 转码无 SIMD 加速），`--openssl-no-provider` 等关键 configure 选项未明确声明，官方测试套件的 expected-failure 清单尚未收敛，无法证明"编译出的 libnode 与官方 node 行为完全一致"。
4. **平台支持名不副实**——`supports: "windows | linux | osx"` 声明过宽，实际 Tier 1 仅 2 个平台，arm64 存在已知的交叉编译 host toolset 结构性障碍，debug 构建从未编译过。
5. **开源协作基础设施缺失**——无 `CONTRIBUTING.md`、无 Issue/PR 模板、无 `CODE_OF_CONDUCT`、无 `CHANGELOG`、无 tag/release、全中文注释对国际贡献者构成壁垒、单人维护无 bus factor 保障。
6. **构建环境硬依赖过重**——强制 CMake 4.x（vcpkg 2026.07.29 的脚本要求）、Windows 强制 clang-cl、Python3/Ninja 由 vcpkg  acquire 但版本未锁定，可重现性不足。

**结论**：作为个人/团队内部 overlay port 使用，当前质量已可接受（需注意已知限制）；作为 vcpkg 官方端口投稿或大规模社区采用，**必须先解决全部 6 项阻断级问题和至少 10 项严重问题**。

## 视角一：vcpkg 官方 Port 审核者

> 评审依据：[vcpkg Maintainer Guide](https://learn.microsoft.com/en-us/vcpkg/contributing/maintainer-guide)、[vcpkg.json Reference](https://learn.microsoft.com/en-us/vcpkg/reference/vcpkg-json)、[Overlay Ports](https://learn.microsoft.com/en-us/vcpkg/concepts/overlay-ports)、curated registry 合并 PR 的实际审核标准。

### 1.1 Vendored Dependencies 政策合规性

#### 【阻断】V8 内嵌依赖未做符号隔离，违反 Unique File Mapping Rule

**评审标准**：vcpkg 维护者指南明确要求 "Do not use vendored dependencies"；当因客观原因必须保留时，必须做到：① 不污染全局 include 根目录 ② 不污染全局 lib 根目录 ③ 冲突库放入 `manual-link/` 子目录 ④ CMake target 使用独立 namespace。

**事实证据**：
- `portfile.cmake` 安装阶段：
  ```cmake
  file(INSTALL "${SOURCE_PATH}/deps/v8/include/" DESTINATION "${CURRENT_PACKAGES_DIR}/include")
  ```
  V8 头文件（`v8.h`、`v8-*.h`、`libplatform/`、`cppgc/`）直接安装到 `<prefix>/include/` 根目录。
- 静态库安装：
  ```cmake
  file(GLOB_RECURSE _node_archives "${SOURCE_PATH}/out/Release/obj/*${_node_lib_suffix}")
  foreach(_a IN LISTS _node_archives)
      file(INSTALL "${_a}" DESTINATION "${CURRENT_PACKAGES_DIR}/lib")
  endforeach()
  ```
  所有 gyp 产出的静态库（含 `v8_zlib.lib`、`abseil.lib`、`highway.lib`、`v8_base_without_compiler.lib` 等）全部直接安装到 `<prefix>/lib/` 根目录。
- vcpkg 官方已有 `v8` 端口（版本 9.1.269.39，`supports: !(arm | arm64 | uwp | osx | linux)`，即仅 Windows x86/x64），同样安装 `include/v8.h` 和 `lib/v8_monolith.lib`。当用户同时安装 `node`（本端口）和 `v8`（官方端口）时，会触发 `FILE_CONFLICTS` 错误。

**违反的具体规则**：
- Maintainer Guide: "Ports must not install files that conflict with another port."
- Maintainer Guide: "Place conflicting libs in a `manual-link` directory." —— `v8_zlib`（定义了与 zlib 相关的符号）、`abseil`（vcpkg 有独立 `abseil` 端口）、`highway`（vcpkg 有独立 `highway` 端口）均属于"定义了与其他库同名符号"的冲突库，必须放入 `lib/manual-link/`。

**改进要求**：
1. V8 头文件安装到 `<prefix>/include/node-v8/` 或 `<prefix>/include/v8-for-node/`，并通过 patch 让 Node 源码引用非标路径；或至少在 `vcpkg.json` 中声明 `"supports": "!windows"` 以规避与官方 v8 端口的平台重叠（但这只是逃避，不是解决）。
2. `v8_zlib`、`abseil`、`highway`、`crdtp` 等可能与 vcpkg 其他端口冲突的静态库，必须移入 `<prefix>/lib/manual-link/`，并在 `node-config.cmake` 中用绝对路径引用，而非让链接器在全局 lib 目录搜索。
3. 在 `vcpkg.json` 的 `description` 中显式声明："本端口内嵌 V8 x.y.z（Node fork），不使用 vcpkg 的 v8 端口；与 vcpkg 的 `abseil`、`highway` 端口不兼容于同一可执行文件。"

#### 【严重】CMake 导出目标未使用 `unofficial-` 前缀

**评审标准**：Maintainer Guide 明确要求："Any CMake configs that the port exports, which are not in the upstream library, should have `unofficial-` as a prefix. Any additional targets should be in the `unofficial::<port>::` namespace."

**事实证据**：
- `portfile.cmake` 生成的配置文件名为 `node-config.cmake`，导出目标为 `node::node`、`node::libnode`、`node::v8_base_without_compiler` 等。
- `usage` 文件指导用户：
  ```cmake
  find_package(node CONFIG REQUIRED)
  target_link_libraries(<你的目标> PRIVATE node::node)
  ```
- Node.js 上游**不提供**官方 CMake config（上游用 gyp），因此本端口导出的所有 CMake 配置均属于 "not in the upstream library"，按规则必须加 `unofficial-` 前缀。

**风险**：若未来 Node.js 上游添加了官方 CMake 支持（或第三方提交了官方 `node` 端口），`find_package(node CONFIG)` 会产生命名冲突。vcpkg 的 `unofficial-` 约定正是为了避免这种锁定。

**改进要求**：
- 配置文件改为 `unofficial-node-config.cmake`
- 目标改为 `unofficial::node::node`、`unofficial::node::libnode` 等
- `usage` 文件同步更新

---

#### 【严重】`supports` 字段声明过宽，与实际支持矩阵不符

**评审标准**：`vcpkg.json` 的 `supports` 字段必须精确反映实际可构建的平台组合。声明过宽会导致用户在不支持的平台上遇到难以诊断的构建失败。

**事实证据**：
- `vcpkg.json` 声明：`"supports": "windows | linux | osx"`
- 但 README 的支持矩阵明确标注：
  - Tier 1（CI 实测保证）：仅 Windows `x64-windows-static-clang` 和 Linux `x64-linux`
  - Tier 2（允许失败）：`arm64-windows-static-clang`、`arm64-linux`、`arm64-osx`、MSVC 口径、debug 构建
  - Tier 3（结构性不支持）：动态库、32位、mingw、android/ios
- `docs/暂时还没做.md` §2 明确记录：arm64-windows 交叉编译存在 **host toolset 结构性障碍**（`mksnapshot`/`torque`/`node_js2c` 等构建期工具会被编成 arm64，在 x64 构建机上跑不起来），"升级 Tier 1 之前必须先解决这个"。
- debug 构建从未被 CI 编译过（`docs/暂时还没做.md` §1）。

**改进要求**：
- `supports` 应收窄为实际 Tier 1 范围，例如：`"supports": "x64-windows-static-clang | x64-linux"`（vcpkg supports 表达式支持架构限定）
- 或至少在 `supports` 中排除已知不可用的组合：`"supports": "!(arm | arm64 | uwp | mingw | static:!windows)"` 等
- 待 arm64 和 debug 实际通过后再逐步放宽

---

#### 【严重】`node-config-version.cmake` 缺失

**事实证据**：`docs/暂时还没做.md` §5d 明确记录："port 还没写 `node-config-version.cmake`"，导致 `find_package(node 24.21.0 CONFIG)` 不可用，`node_VERSION` 变量为空。

**评审标准**：vcpkg 要求所有提供 CMake config 的端口必须同时提供 version 文件，使用 `write_basic_package_version_file(... COMPATIBILITY SameMajorVersion ARCH_INDEPENDENT)`。

**改进要求**：在 `portfile.cmake` 中生成 version 文件并安装到 `share/node/`。

---

#### 【一般】补丁数量过多且部分为 gyp 基础设施补丁，上游可接受性低

**事实证据**：`PATCHES` 列表共 15 个补丁：
- `0001` ICU system icudata
- `0002`~`0007` gyp ninja/clang-cl 相关（6个）
- `0008` configure shared syslibs + clang-cl
- `0009`~`0010` js2c/torque Windows 路径归一化
- `0011`~`0014` V8 simdutf/zlib 替换
- `0015` configure 前插 V8 自带头

**评审标准**：Maintainer Guide 要求 "Minimize patches" 和 "Avoid patches that upstream would disagree with"。其中 `0002`~`0007` 是对 gyp 工具本身的修改（gyp 是 Node 源码树的一部分，但这些修改不太可能被上游接受——gyp 的 ninja generator 在上游被视为实验性）。

**风险**：Node 每次小版本升级都可能导致这 6 个 gyp 补丁需要 rebase，维护成本高。

**改进建议**：
- 在 `docs/` 中为每个补丁标注：① 修改目的 ② 上游是否已接受/有对应 PR ③ 升级时的 rebase 风险等级
- 考虑将 gyp 补丁合并为更少的文件，或评估是否可通过 `vcpkg_replace_string` 在 portfile 中直接完成（如 `0009`/`0010` 的路径归一化，以及 Windows WHOLEARCHIVE 路径修复已经用了 `vcpkg_replace_string`，说明部分补丁可以不用 patch 文件）

---

#### 【一般】`vcpkg.json` 的 `description` 未声明 vendored V8 和已知限制

**事实证据**：当前 `description` 为：
> "把 Node.js v24.21.0 整棵源码树（含 V8 与 V8 内嵌第三方）用官方 gyp → ninja 编成可链接的 node 静态库，并安装头文件与 CMake 消费配置。Node 自身依赖的官方 port 在此声明，消费方经传递依赖自动获得。"

**问题**：用户执行 `vcpkg list` 时只能看到这段描述，无法得知：① 本端口内嵌 V8 而非使用 vcpkg v8 ② 与 `abseil`/`highway` 不兼容 ③ 仅静态库 ④ Windows 需 clang-cl。这些关键信息只在 README 和 usage 里。

**改进要求**：`description` 应压缩至 2-3 行，但必须包含最关键的限制声明，例如：
> "Node.js v24.21.0 static library (embedded V8, not vcpkg's v8 port). Static-only; Windows requires clang-cl. Incompatible with vcpkg abseil/highway in the same executable."

---

#### 【一般】`vcpkg_find_acquire_program(PYTHON3)` 未锁定版本

**事实证据**：`portfile.cmake` 使用 `vcpkg_find_acquire_program(PYTHON3)` 获取 Python，但未指定版本。Node 的 `configure.py` 对 Python 版本有要求（Node 24 要求 Python 3.11+）。

**风险**：不同 vcpkg 版本 acquire 的 Python3 版本可能不同，导致 configure 行为不一致。

**改进建议**：评估是否需要 `vcpkg_find_acquire_program(PYTHON3)` 的版本参数，或在 portfile 中添加版本断言。

---

#### 【建议】`portfile.cmake` 中使用 `vcpkg_replace_string` 修改 `node.gyp` 应改为补丁

**事实证据**：
```cmake
if(VCPKG_TARGET_IS_WINDOWS)
vcpkg_replace_string("${SOURCE_PATH}/node.gyp"
"/WHOLEARCHIVE:<(PRODUCT_DIR)/lib/<(STATIC_LIB_PREFIX)node_base<(STATIC_LIB_SUFFIX)"
"/WHOLEARCHIVE:<(obj_dir)/<(STATIC_LIB_PREFIX)node_base<(STATIC_LIB_SUFFIX)")
```

**评审标准**：Maintainer Guide 倾向于使用补丁文件而非 `vcpkg_replace_string`，因为补丁可审查、可 rebase、有上下文。`vcpkg_replace_string` 适用于"字符串唯一且上游改行号也不影响"的场景，但这里修改的是构建系统的关键链接参数，应该有补丁上下文。

### 1.2 版本管理与 Baseline

#### 【严重】`versions/n-/node.json` 只有一个版本，无 baseline 机制

**事实证据**：
```json
{
  "versions": [
    { "version": "24.21.0", "git-tree": "1258b56c9dc2223ecd1ddbc60464d8f738e82b29" }
  ]
}
```

**评审标准**：vcpkg 的版本管理要求 `versions/` 目录下有 `baseline.json`（或在 registry 的 `vcpkg-configuration.json` 中指定 baseline），且每个版本的 `git-tree` 必须对应 port 目录的实际 tree 对象。当前只有一个版本条目，没有 baseline，用户在 manifest mode 下使用时无法进行版本约束。

**改进要求**：补充 `versions/baseline.json`，或在文档中说明本 overlay port 的版本约束方式。

---

#### 【一般】`port-version` 机制未使用

**事实证据**：`vcpkg.json` 中只有 `"version": "24.21.0"`，没有 `port-version`。当 portfile 或补丁修改但 Node 版本不变时，无法通过 `port-version` 递增来触发重新构建。

**改进要求**：引入 `port-version`，每次修改 port 内容（非 Node 版本升级）时递增。

### 1.3 与其他端口的共存性

#### 【阻断】与 vcpkg `abseil` / `highway` 端口的共存问题仅声明未解决

**事实证据**：`docs/暂时还没做.md` §5g 详细记录：
- V8 使用 abseil/highway 的**内部符号**（`container_internal::DeallocateBackingArray`、`hash_internal::MixingHashState::kSeed` 等）
- `src/node.cc` 直接 `#include "absl/..."`
- 实测：将 V8 的 abseil 换成 vcpkg 版本 → 链接期 LNK2019
- 当前修法：让 V8 自带头在 include 顺序上排在 vcpkg include 之前（补丁 0015 + redline 脚本）
- 对使用者的影响："同一个可执行里既有 node port、又链 vcpkg 的 abseil/highway ⇒ 两份同名实现 ⇒ 冲突"

**评审标准**：vcpkg 的核心承诺是"所有端口可以任意组合安装，不会有符号冲突"。当前状态下，用户在 `vcpkg.json` 里同时写 `node` 和 `abseil` 就会在链接期失败——这违反了 vcpkg 的基本共存保证。

**这是阻断级问题**，因为 vcpkg 官方审核者会要求：要么解决共存（技术上几乎不可能，因为 V8 依赖 abseil 内部符号），要么在 `supports` 或依赖声明中**显式排除**与 `abseil`/`highway` 的共存（但 vcpkg 没有"互斥依赖"机制），要么将本端口定位为"不进入 curated registry，仅作 overlay 使用"。

**改进建议**：
1. 在 `vcpkg.json` 中添加 `"dependencies"` 的冲突声明（vcpkg 目前不支持 `conflicts` 字段，但可以在 `description` 和 `usage` 中用醒目方式警告）
2. 评估是否可以将 V8 内嵌的 abseil/highway 重命名符号（如 `objcopy --redefine-symbols`），但这会破坏 V8 的内部引用，可行性低
3. **最务实的方案**：明确本端口不进入 vcpkg curated registry，仅作为 overlay port 分发，并在文档首页用红字声明共存限制

---

#### 【严重】`nghttp2` 无 CMake config，port 手动建 imported target，但未验证版本兼容性

**事实证据**：`portfile.cmake` 中：
```cmake
string(APPEND _cfg
"find_library(_nghttp2_lib nghttp2 HINTS \${_node_lib} REQUIRED)\n"
"if(NOT TARGET node::nghttp2)\n"
"  add_library(node::nghttp2 STATIC IMPORTED)\n"
"  set_target_properties(node::nghttp2 PROPERTIES IMPORTED_LOCATION \"\${_nghttp2_lib}\")\n"
"endif()\n")
```

**问题**：vcpkg 的 `nghttp2` 端口**不提供** CMake config 文件（上游也不提供），所以 port 用 `find_library` 手动定位。但 `find_library` 的 `HINTS` 指向 `${_node_lib}`（即 `<prefix>/lib`），这是整个工程共用的 lib 目录，可能找到其他端口安装的同名库。此外，未检查 nghttp2 版本是否满足 Node 24.21.0 的要求。

**改进要求**：添加版本检查，或在 `vcpkg.json` 中对 `nghttp2` 添加版本约束（`"version>="`）。

### 1.4 构建系统与 Triplet

#### 【严重】Windows 强制 clang-cl，但 `supports` 未排除 MSVC triplet

**事实证据**：
- `portfile.cmake` 注释："Windows **必须用 clang-cl**（node 24+ 的官方口径）"
- 但 `vcpkg.json` 的 `supports` 是 `"windows | linux | osx"`，未限定 `x64-windows-static-clang`
- 用户如果用 `x64-windows`（MSVC + 动态 CRT）安装，会在 configure 或编译阶段失败，且错误信息可能不直观

**改进要求**：`supports` 应精确到 triplet 级别，或在 portfile 开头添加 triplet 检查并给出清晰错误信息：
```cmake
if(VCPKG_TARGET_IS_WINDOWS AND NOT VCPKG_CHAINLOAD_TOOLCHAIN_FILE MATCHES "clang")
    message(FATAL_ERROR "node port requires clang-cl on Windows. Use triplet x64-windows-static-clang.")
endif()
```

---

#### 【一般】`VCPKG_BUILD_TYPE release` 硬编码在消费端 triplet，port 未声明不支持 debug

**事实证据**：README 和 CI 都只跑 Release，`docs/暂时还没做.md` §1 确认 debug 从未编译。但 port 本身没有 `vcpkg_check_linkage` 之外的 build type 检查。

**改进要求**：在 portfile 中添加 debug 构建的明确错误或警告，或在 `vcpkg.json` 中声明。

## 视角二：Node.js 官方评审者

> 评审依据：Node.js 官方 [Building Node.js](https://github.com/nodejs/node/blob/main/BUILDING.md)、[configure.py 选项](https://github.com/nodejs/node/blob/main/configure.py)、[官方测试套件](https://github.com/nodejs/node/tree/main/test)、[V8 embedder 指南](https://v8.dev/docs/embed)。

### 2.1 行为一致性

#### 【阻断】`ada-url` 关闭 `ADA_USE_SIMDUTF`，IDNA 转码性能与官方不一致

**事实证据**：`docs/暂时还没做.md` §5e 明确记录：
- Node 官方将 ada 编成单个 amalgamated TU，配 V8 的 simdutf + `ADA_USE_SIMDUTF=1`
- 本端口走 `--shared-ada` 用 vcpkg 的 `ada-url`，但 vcpkg 的 `ada-url` 的 `ADA_USE_SIMDUTF` 是 CPM 下载实现（vcpkg 中不合适），所以 port 写死 `OFF`
- 影响："结果一致，只是 IDNA/Unicode 转码少了 SIMD 加速（性能 delta），不是正确性问题"

**Node.js 官方评审视角**：
- "结果一致"是文档结论，**不是回归测试结论**。IDNA 转码涉及复杂的 Unicode 规则（UTS #46），simdutf 的 SIMD 路径和标量路径在边界 case 上可能有细微差异。Node 官方测试套件中有 `test-whatwg-url` 系列用例覆盖 IDNA，但本项目的 expected-failure 清单尚未收敛（`docs/暂时还没做.md` §5b），无法证明这些用例全部通过。
- 性能 delta 未量化。Node 官方对 URL 解析性能有 benchmark（`benchmark/url/`），本项目未提供与官方 node 的性能对比数据。

**改进要求**：
1. 运行 Node 官方 `test-whatwg-url` 全量用例，确认 100% 通过（或逐条记录 expected-failure 及原因）
2. 运行 `benchmark/url/` 对比官方 node，量化性能 delta，写入文档
3. 若性能 delta 显著（>10%），应考虑 overlay 一份启用 simdutf 的 `ada-url` 端口，或在文档中明确标注"此构建在 URL/IDNA 性能上与官方 node 有差异"

---

#### 【严重】configure.py 参数未完整披露，无法验证是否与官方构建等价

**事实证据**：`portfile.cmake` 中 configure 调用：
```cmake
vcpkg_execute_required_process(
    COMMAND "${PYTHON3}" configure.py
    --ninja
    ${_node_clang_cl_arg}
    --with-intl=system-icu
    ${_node_shared_args}
    "-DVCPKG_SIMDUTF_INCLUDE=${_inc}"
    WORKING_DIRECTORY "${SOURCE_PATH}"
    LOGNAME configure
)
```

**缺失的关键选项**（Node 官方构建中常见，本 port 未显式声明）：
- `--openssl-is-system-fips` / `--openssl-no-provider` / `--openssl-conf-name`：OpenSSL provider 配置。`docs/暂时还没做.md` §5h 提到 `nodejs-openssl.cnf` 和 `NODE_OPENSSL_CONF_NAME`，但 configure 命令中未见相关参数
- `--without-node-snapshot` / `--without-node-code-cache`：snapshot 和 code cache 是 Node 启动性能的关键优化，本 port 未声明是否启用
- `--v8-lite-mode`：V8 lite mode 会禁用某些优化，影响性能
- `--experimental-global-webcrypto` 等 feature flag：Node 24 的某些特性默认开启状态可能受 configure 选项影响
- `--shared-brotli` 等的 `--shared-brotli-libname` 是否正确传递了 vcpkg 的库名（Windows 静态口径 brotli 库名有 `lib` 前缀差异，portfile 中有处理但未验证）

**改进要求**：
1. 在 `docs/` 中提供完整的 configure 命令行展开结果（所有变量替换后），与 Node 官方推荐的构建参数逐项对比

3. 提供 `process.config` 的输出（嵌入构建的 node 可执行跑 `node -p "process.config"`），与官方 node 对比

#### 【一般】ICU 数据完整性未验证

**事实证据**：configure 使用 `--with-intl=system-icu`，依赖 vcpkg 的 `icu` 端口。补丁 `0001-icu-system-add-icudata.patch` 处理了 icudata 问题。

**风险**：

**改进要求**：
1. 确认 vcpkg `icu` 端口的构建模式（static data vs data-file）

### 2.2 性能与优化

#### 【严重】未启用 LTO/PGO，性能可能显著低于官方 node

**事实证据**：
- configure 命令中未见 `--enable-lto` 或 `--v8-enable-lto`
- 未见 PGO（Profile-Guided Optimization）相关步骤
- Node 官方发布的二进制默认启用 LTO，Windows 官方构建还使用 PGO

**影响**：V8 的 JIT 性能和 Node 整体吞吐量对 LTO/PGO 敏感。未启用 LTO 的构建在 microbenchmark 上可能有 5-15% 的性能损失。

**改进要求**：
1. 评估在 port 中启用 `--enable-lto` 的可行性（clang-cl LTO 需要 `/GL` 和 `/LTCG`，与静态库交付可能有冲突）
2. 若不启用，在文档中明确声明"此构建未启用 LTO/PGO，性能低于官方发布版"
3. 提供与官方 node 的 benchmark 对比数据（至少覆盖 `benchmark/http/`、`benchmark/url/`、`benchmark/v8/`）

---

#### 【一般】编译选项未与官方构建对齐

**事实证据**：portfile 中未见对 `CFLAGS`/`CXXFLAGS`/`LDFLAGS` 的显式设置，依赖 gyp 的默认值和 vcpkg toolchain 传入的 flags。

**风险**：vcpkg 的 triplet 会传入 `VCPKG_C_FLAGS`/`VCPKG_CXX_FLAGS`（如 `/O2`、`-O3`），但 Node 的 gyp 构建系统可能不直接消费这些变量（gyp 有自己的 `cflags`/`cflags_cc` 机制）。可能导致优化级别、警告级别、安全选项（如 `/GS`、`-fstack-protector`）与官方构建不一致。

**改进要求**：在 `docs/` 中提供实际编译命令（`ninja -v` 输出抽样），与官方构建的编译选项逐项对比。

### 2.3 Embedder API 完整性

#### 【一般】未验证 Node 公共 embedder API 的完整性

**事实证据**：`test/` 中的嵌入测试使用 `node::Start`（最简单的嵌入方式），未见使用更复杂的 embedder API：
- `node::CreateEnvironment` / `node::LoadEnvironment` / `node::SpinEventLoop`
- `node::MultiIsolatePlatform`
- `node::SnapshotBuilder`
- Worker threads 的嵌入式使用

**风险**：静态库交付时，某些 embedder API 可能因为符号未导出或初始化顺序问题而不可用。`node::Start` 能工作不代表完整的 embedder API 都可用。

**改进要求**：添加使用 `node::CreateEnvironment` 等高级 API 的测试用例，覆盖多 isolate、多 environment、snapshot 等场景。

## 视角四：安全审计者

> 评审依据：[CVE 管理最佳实践](https://cve.mitre.org/)、[SLSA 框架](https://slsa.dev/)、[可重现构建](https://reproducible-builds.org/)、[SBOM 标准](https://cyclonedx.org/)。

### 4.1 供应链安全

#### 【严重】Node 源码下载仅用 SHA512，无签名验证

**事实证据**：
```cmake
vcpkg_download_distfile(NODE_ARCHIVE
    URLS "https://nodejs.org/dist/v24.21.0/node-v24.21.0.tar.gz"
    SHA512 8bb098aa786298ceaf25797adb5551ff4edcafcdc19a669e530a42c60ca71c1b...
)
```

**问题**：
- SHA512 只能验证完整性，不能验证来源真实性。如果 `nodejs.org` 被入侵或 DNS 被劫持，攻击者可以替换 tarball 并同时更新 SHA512（如果攻击者也能修改本仓库的 portfile）。
- Node.js 官方提供 GPG 签名的 tarball（`node-v24.21.0.tar.xz.sig`），但本 port 未验证签名。
- 下载 URL 是 `http://nodejs.org`（非 GitHub），vcpkg 的下载镜像机制可能不覆盖此域名。

**改进要求**：
1. 评估添加 GPG 签名验证的可行性（vcpkg 目前不原生支持 GPG 验证，但可以在 portfile 中手动实现）
2. 至少添加备用下载 URL（如 GitHub 的 nodejs/node release 镜像）
3. 在 `docs/` 中记录 SHA512 的获取方式和验证流程

---

#### 【严重】V8 内嵌依赖的安全补丁无法独立跟踪

**事实证据**：V8 是 Node 源码树的一部分（`deps/v8/`），随 Node 版本一起更新。但 V8 本身有独立的安全公告和 CVE，Chromium 项目会在 V8 中修复漏洞后，Node 项目可能需要数周甚至数月才同步。

**风险**：
- 当 V8 出现 0day 时，本端口的用户无法独立升级 V8（因为 V8 是 Node fork 的，与 Node 版本绑定）
- 使用者无法通过 `vcpkg upgrade v8` 来修复 V8 漏洞
- 本项目未提供安全公告订阅机制或 CVE 跟踪文档

**改进要求**：
1. 在 `SECURITY.md` 中声明安全漏洞响应流程
2. 建立 V8/Node 安全公告的跟踪机制（如定期检查 [Node.js Security Releases](https://nodejs.org/en/security/)）
3. 在 `README` 中明确："本端口的 V8 版本与 Node 版本绑定，安全更新依赖 Node 上游的发布节奏"

---

#### 【一般】14 个 vcpkg 依赖的版本未锁定，传递性 CVE 风险

**事实证据**：`vcpkg.json` 中 14 个依赖均未指定版本约束（`"version>="` 或 `"version<="`），完全依赖 vcpkg baseline 解析。

**风险**：用户的 vcpkg baseline 不同，安装的依赖版本不同，可能引入已知 CVE。例如 `openssl` 如果 baseline 较老，可能包含已修复的漏洞。

**改进要求**：
1. 对安全敏感的依赖（`openssl`、`libuv`、`nghttp2`、`ngtcp2`、`sqlite3`）添加最低版本约束
2. 在 CI 中运行 `vcpkg audit`（如果可用）或依赖漏洞扫描

### 4.2 构建可重现性

**事实证据**：

**改进要求**：

## 视角五：下游集成者与 CI/DevOps 工程师

---

### 5.3 错误诊断性

#### 【一般】configure/build 失败时的错误信息可能不直观

**事实证据**：
- `vcpkg_execute_required_process` 的日志会写入 `buildtrees/node/configure-<triplet>-out.log`，但用户需要知道去那里找
- gyp/ninja 的错误信息通常很长，关键错误可能被淹没
- portfile 中的 `message(STATUS ...)` 输出有限

**改进要求**：
1. 在 `usage` 或 `README` 中提供构建失败时的诊断指引（日志位置、常见错误及解决方法）
2. 对常见错误（如 clang-cl 未找到、CMake 版本过低、内存不足）添加 portfile 内的预检查和清晰错误信息

---

### 5.4 工具链要求

#### 【严重】CMake 4.x 硬依赖对下游用户构成门槛

**事实证据**：
- CI 注释："vcpkg 2026.07.29 的脚本用了 `string(JSON ... STRING_ENCODE)`，那是 CMake 4.x 才有的子命令"
- 这意味着用户必须使用 CMake 4.x，而很多企业项目仍在 CMake 3.2x/3.3x
- 虽然这是 vcpkg 本身的要求而非本 port 的要求，但本 port 锁定了 vcpkg 2026.07.29，间接强制了 CMake 4.x

**改进要求**：
1. 在 `README` 中醒目声明 CMake 最低版本要求
2. 评估是否支持更早的 vcpkg 版本（如果用户的 vcpkg 版本不要求 CMake 4.x）

---

## 视角六：长期维护与 ABI 稳定性评审者

### 6.1 版本升级路径

#### 【严重】Node 版本升级成本极高，无自动化流程

**事实证据**：
- 15 个补丁全部针对 Node 24.21.0 的具体文件和行号
- gyp 补丁（0002-0007）修改的是 gyp 工具的 Python 代码，Node 每次升级可能更新 gyp 版本
- V8 补丁（0011-0015）依赖 V8 的具体构建文件结构，V8 随 Node 版本快速迭代
- `docs/暂时还没做.md` 中记录了大量"试过又撤掉的修法"，说明升级时需要大量试错

**风险**：
- Node 大约每 6 个月发布一个大版本（当前 24，下一个 25 在 2025 年 4 月），每月有小版本和安全更新
- 每次升级可能需要重新适配 15 个补丁，单人维护难以持续
- 无自动化的升级测试流程（如"升级 Node 版本 → 自动应用补丁 → 跑 CI"的脚本）

**改进要求**：
1. 建立版本升级 checklist（`docs/upgrade-checklist.md`），列出每个补丁在升级时的验证点
2. 为每个补丁标注"上游是否已合并"和"预计失效版本"
3. 考虑向上游 Node 提交 gyp ninja 相关的补丁（如果被接受，可减少维护负担）
4. 设定明确的维护承诺（如"跟踪 Node LTS 版本，非 LTS 不保证"）

---

#### 【一般】无 ABI 兼容性承诺

**事实证据**：
- 静态库交付，ABI 稳定性取决于 Node 自身的 ABI（Node 的 C++ API 不保证跨大版本 ABI 稳定）
- `node-config-version.cmake` 缺失，连版本匹配检查都没有
- 未声明 `SameMajorVersion` / `ExactVersion` 等兼容性策略

**改进要求**：
1. 添加 `node-config-version.cmake`，使用 `SameMajorVersion` 兼容性
2. 在文档中声明："Node 的 C++ embedder API 不保证跨大版本 ABI 兼容，升级大版本需要重新编译下游项目"

---

### 6.2 废弃与迁移策略

#### 【建议】无废弃策略

**改进要求**：
1. 如果未来 vcpkg 官方接受了 `node` 端口（或出现了更成熟的替代方案），本项目应有明确的废弃和迁移指引
2. 在 `README` 中声明项目状态（experimental / stable / maintenance-only）
