# 架构重审（二）：路线抉择与依赖替换

> 承接 `docs/架构重审-从二进制配置到源码配置.md`。本轮针对用户提出的两个新方向做**实测**：
>
> 1. 本机有 VS 工具链 + clang，且 **vcpkg tools 机制自带 cmake/ninja/python**（有缓存）；
>    目标从三平台扩到**主流六平台**（x64/arm64 × win/mac/linux）× debug/release ×
>    msvc/clang × 动态/静态；
> 2. **test 太少** —— 要真正以"使用者"的视角做测试：使用者还会加别的 vcpkg 库，
>    与 node port 有无冲突？符号重复？不稳定行为？
>    倾向把 node 内部集成的依赖**全部换成 vcpkg 上的**（openssl、simdutf 等；
>    v8 可例外，名字空间隔离的可例外），同时**综合评估 node 给这些库打的补丁**；
> 3. 这又牵扯：能否**不走 gyp→cmake**，直接在 vcpkg 里按官方 gyp 路径编译？
>    以及**如何用 vcpkg 现有库替换 node 内部集成的**？

- 日期：2026-10-11
- 方法：全部结论均有本机实测支撑（Windows + VS 2022 + vcpkg 已有 `x64-windows-static-clang` 依赖树）

## 1. vcpkg tools 机制核实（用户判断正确）

`scripts/cmake/vcpkg_configure_cmake.cmake:129` 原文：

```cmake
set(generator "Ninja") # the default generator is always ninja!
```

`vcpkg_cmake_configure` 内部 `vcpkg_find_acquire_program(NINJA)`，并：
```cmake
get_filename_component(ninja_path "${NINJA}" DIRECTORY)
vcpkg_add_to_path("${ninja_path}")
vcpkg_list(APPEND arg_OPTIONS "-DCMAKE_MAKE_PROGRAM=${NINJA}")
```

`downloads/tools/` 实测缓存：

| 工具 | 缓存 |
|---|---|
| cmake | `cmake-4.3.3-windows`, `cmake-4.4.0-windows` |
| ninja | `ninja-1.13.2-windows` |
| python | `python-3.14.2-x64-1` |
| perl / nasm / msys2 / win_flex / win_bison / jom | 均有 |

→ **本机确实不需要装 cmake/ninja/python**；`portfile.cmake` 现在只 `vcpkg_find_acquire_program(PYTHON3)`，
其余由 `vcpkg_cmake_configure` 自理。**结论：用户判断正确，现状已符合。**

## 2. 路线抉择：gyp ninja vs gyp→cmake 翻译

### 2.1 三条候选路线

| 路线 | 可行性 | 说明 |
|---|---|---|
| **A. gyp→cmake 翻译**（现状） | 可行 | 自研 gyp2vcpkg，59 份片段 + 1148 行手写 CMake |
| **B. gyp → ninja → vcpkg_build_ninja** | **可行（本轮实测）** | gyp 自带 `generator/ninja.py` |
| **C. 上游 Makefile** | **不可行（Windows）** | 硬依赖 `uname`，见 §2.3 |

### 2.2 路线 B 决定性实验（成功）

**命令**（Windows + VS 2022 + vcpkg 的 openssl 作外部依赖）：

```bash
gyp -f ninja --depth=. --no-parallel \
    -I common.gypi -I <env.gypi> \
    -Dcomponent=static_library -Dlibrary=static_library \
    -Dpython=<python> -Goutput_dir=<out> -Gconfig=Release \
    node.gyp
# → rc = 0
```

**产出 87 个 ninja 文件**，覆盖全部目标：

| 文件 | 行数 |
|---|---|
| `Release/build.ninja` | 310 |
| `obj/tools/v8_gypfiles/v8_base_without_compiler.ninja` | 5305 |
| `obj/tools/v8_gypfiles/run_torque.ninja` | 2899 |
| `obj/tools/v8_gypfiles/v8_initializers.ninja` | 1801 |
| `obj/node_base.ninja` | 1486 |
| `obj/tools/v8_gypfiles/v8_compiler_for_mksnapshot_source_set.ninja` | 1209 |
| `obj/tools/v8_gypfiles/v8_compiler.ninja` | 1039 |
| ……（其余 80 个） | |

内容完整正确：
- MSVC 开关齐全：`/Ox /Ob2 /GF /Oy /Oi /Ot /fp:precise /W3 /Z7 /GR- /Gy /GS /MT /Zc:__cplusplus -std:c++20 /Zm2000 /FS`
- action 规则 + `gyp-win-tool` 包装 + `ninja -t msvc` 依赖探测（`deps = msvc`）
- `environment.x64/arm64/x86` 三份环境文件（可直接支持多架构）

**结论**：**不需要 MSYS2、不需要 GNU make**。`gyp -f ninja` 在 Windows 上原生可用，
配合官方 `vcpkg_build_ninja`（`scripts/cmake/vcpkg_build_ninja.cmake`，读
`${CURRENT_BUILDTREES_DIR}/${config}` 下的 ninja）。

#### 两个 gyp 在中文 locale 下的 bug（绕过即可，非阻塞）

| 现象 | 原因 | 绕过 |
|---|---|---|
| `ValueError: Could not locate Visual Studio installation.` | gyp 靠注册表/vswhere，不读 vcvars | `GYP_MSVS_VERSION=2022` + `GYP_MSVS_OVERRIDE_PATH=<VS 根>` |
| `UnicodeDecodeError: 0xc8 at position 56` | `_FindDirectXInstallation` 用 UTF-8 解 `reg.exe` 的 GBK 输出 | `DXSDK_DIR=C:\nonexistent`（设了就不再探测） |

> 这两个都是 **gyp 自身缺陷**，不修改 node 源码即可绕过。若走路线 B，建议在
> portfile 里显式设置这两个环境变量，并在文档中标注原因。

### 2.3 路线 C 否证（上游 Makefile）

node `Makefile:13`：

```make
OSTYPE := $(shell uname -s | tr '[:upper:]' '[:lower:]')
ARCHTYPE := $(shell uname -m | tr '[:upper:]' '[:lower:]')
```

**硬依赖 `uname` / `tr`**（Unix 工具），Windows 上必须 MSYS2。
且 `Makefile` 全篇 71 处 `$(shell ...)` / `$(wildcard ...)`，与 vcpkg 的
"可直接调用的构建系统"不匹配。

→ **路线 C 排除**；若要"最贴近官方"，**路线 B（gyp ninja）才是正解**——
它复用 node 官方 generator，且跨平台统一。

### 2.4 路线对比建议

| 维度 | A（翻译） | B（gyp ninja） |
|---|---|---|
| 与上游一致性 | 中（自研翻译层） | **高**（直接用官方 generator） |
| 维护成本 | 高（59 片段 + 1148 行手写） | **低**（删掉 gyp2vcpkg + 手写 CMake） |
| 用户集成 | 好（CMake target + config） | 需包一层（ninja 产物 → install/export） |
| 多配置（debug/release） | 需自行处理 | **原生**（gyp 有 `-Gconfig`） |
| 多架构 | 需自行处理 | **原生**（`environment.x64/arm64/x86`） |
| 风险 | 翻译语义偏差（本轮已发现 3 处） | gyp 自身 bug（已定位 2 处，可绕过） |

**倾向**：路线 B 更符合"最正确"的目标，但**产物安装与 CMake 导出**要自己补一层
（gyp ninja 只管编译，不管 install/export）。这层比 1148 行手写 CMake 薄得多。

## 3. 「用 vcpkg 库替换 node 内置库」实测

### 3.1 configure.py 原生支持，且会认版本

```bash
python configure.py --dest-os=win --dest-cpu=x64 \
  --shared-openssl \
  --shared-openssl-includes=<vcpkg>/openssl/include \
  --shared-openssl-libpath=<vcpkg>/openssl/lib
```

config.gypi 结果：

```
node_shared_openssl  = 'true'
openssl_version      = 811597887   (0x3060003f)
openssl_is_boringssl = 'false'
```

`0x3060003f` **与 vcpkg openssl 3.6.3 精确吻合** —— configure.py 会**真的编译探测**头部
（`get_openssl_version` → `<CC> -E -dM -include openssl/opensslv.h`），
说明"版本替换"是上游**显式设计支持**的。

### 3.2 node 对版本差异设计上兼容

- `deps/ncrypto/ncrypto.h` 用 `OPENSSL_VERSION_PREREQ(3, 5)` 等**前向比较**
- `deps/ncrypto/ncrypto.gyp` 有
  `['openssl_is_boringssl=="false" and openssl_version >= 0x3000000f', {...}]`
  —— gyp **自己会按 openssl 版本切换 `OPENSSL_API_COMPAT` 与 `ncrypto_engine` 依赖**

### 3.3 真实编译验证（通过）

用 vcpkg openssl **3.6.3** 头（node 内置 **3.5.8**）+ gyp 真实算出的宏：

```
cl /std:c++20 /I <vcpkg-openssl-3.6.3>/include \
   /D OPENSSL_API_COMPAT=30000 /D OPENSSL_NO_DEPRECATED \
   deps/ncrypto/ncrypto.cc                          → rc = 0  ✅

cl ... /D NCRYPTO_ENGINE_COMPAT=1 /D OPENSSL_SUPPRESS_DEPRECATED \
   deps/ncrypto/engine.cc                           → rc = 0  ✅
```

> 首次手写编译命令**失败**（缺 `OPENSSL_API_COMPAT` 等宏，报 `ENGINE_*` 未声明、
> `C2589` 语法错）——用 **gyp 真实解析出的宏**后全部通过。
> **教训**：绝不能手工猜宏，必须以 gyp 的输出为准。

### 3.4 闭环验证 `seed_gypi.py` 的设计意图（关键）

`configure_library()`（configure.py:1925）把 `--shared-*-includes` 写进的是
**`target_defaults.include_dirs`**（**不是** `variables`）。实测多库后：

```
target_defaults.include_dirs = [
    <vcpkg>/zlib/include,
    <vcpkg>/libuv/include,
    <vcpkg>/openssl/include,
]
target_defaults.libraries    = [ -lz, -luv, -lcrypto, -lssl ]
```

而 `gyp2vcpkg/env/win-x64.json` 的形状是 `{variables, target_defaults}` —— **同构**。

→ **`configure.py` 的输出可以整个替换 `env/<平台>.json`**，一步同时解决
「配置来源 + 依赖归属 + 头/库路径」三件事。**这比原设计（从二进制拿 + 少数覆盖）更正确。**

（我第一轮实验曾只取 `variables` 喂给 gyp2vcpkg，导致 ninja 产物里 include 少了 vcpkg 路径
——正是因为丢了 `target_defaults`。这条偏差**必须**在实现时避免。）

## 4. node 的依赖补丁评估（核心风险）

### 4.1 zlib：19 个补丁逐条分类

| 补丁 | 目标文件 | 影响 node 核心？ |
|---|---|---|
| 0001-simd | crc32.c deflate.c fill_window_sse.c x86.c … | ✅ 性能 |
| 0002-uninitializedcheck | inflate.c | ✅ **正确性/UB** |
| 0003-uninitializedjump | deflate.c | ✅ **正确性/UB** |
| 0007-zero-init-deflate-window | deflate.c | ✅ **正确性/UB** |
| 0011-avx512 | cpu_features.c crc32.c crc32_simd.c | ✅ 性能 |
| 0012-lfs-open64 | gzlib.c | ✅ gzlib |
| 0013-cpu-feature-detection-for-arm | adler32.c | ✅ adler32 |
| 0017-deflate-move-zmemzero | deflate.c | ✅ **正确性/UB** |
| 0000-build | gzread.c zconf.h zlib.h zutil.h + minizip | ⚠️ 部分 |
| 0004-fix-uwp / 0008 / 0014 / 0015 / 0016 / 0018 / 0019 | **minizip/** | ❌ node 不用 minizip |
| 0005-infcover-gtest / 0009-infcover-oob | **test/infcover.c** | ❌ 仅测试 |
| 0010-cmake | CMakeLists.txt | ❌ 无关 |

**8 个涉及 node 用到的核心**（simd/avx512/lfs/arm-cpu + 4 个正确性）。

### 4.2 关键：上游 madler/zlib 1.3.2 **不含**这些修复（已实测）

| node 补丁 | 上游 1.3.2 状态 |
|---|---|
| 0002 `state->check = 1L`（避免未初始化使用 adler32） | **不含**（上游仍 `adler32(0L, Z_NULL, 0)`） |
| 0003 `zmemzero(s->prev, ...)`（避免未初始化使用） | **不含**（上游无此行） |
| 0017 `zmemzero` 位置（避免 NULL 解引用） | **不含** |
| 0011 avx512 / 0001 simd / 0013 arm-cpu | 上游 1.3.2 **无**（是 Chromium 的 SIMD 优化集） |

这些都是 **Chromium / oss-fuzz 的内存安全与性能修复**，上游 madler/zlib 未合入
（提交信息直指 `crbug.com/1137613`、`oss-fuzz #11360`、`libfido2 fuzz harness`）。

> **结论**：直接换 vcpkg zlib **会丢掉 4 个内存安全修复 + 3 个 SIMD 性能优化**。
> 这不是"能不能编过"的问题（能），而是"换掉的库是否等价"的问题。

### 4.3 simdutf 的例外边界

`simdutf` 在 node 侧来自 **v8 的 `tools/v8_gypfiles/v8.gyp:simdutf`**（不是 node 直接依赖）。
v8 已对它做**名字空间/可见性隔离**，故：
- 若坚持"v8 例外"，simdutf 也随 v8 例外；
- 若要把 simdutf 换成 vcpkg 的，需确认 v8 的 `v8.gyp` 是否接受外部 simdutf（`node_shared_simdutf` 存在，说明支持）。

### 4.4 未决风险清单

| 风险 | 状态 |
|---|---|
| zlib 补丁丢失的**实际影响**（是否触发既有测试失败） | **未评估**——需跑 node 自带 test |
| openssl / sqlite / nghttp2 / ngtcp2 等**其余库**是否也有 node 补丁 | **未查**（本轮只细查了 zlib） |

## 5. test 策略：以"使用者"视角重建

### 5.1 现状（严重不足）

现有 `test/` 只有一个 `main.cpp`：`node::Start(argc, argv)` 跑一段 JS。
`test/CMakeLists.txt` 只做 `find_package(node)` + 链接 + Windows manifest。

**缺少**：版本断言、共存冲突测试、符号检测、多平台矩阵。

### 5.2 已落地的第一个测试工具：`tools/symbol_check.py`

本轮边调研边写出的**符号冲突检测器**（Windows + VS，`dumpbin /symbols` + COMDAT 识别）。

**它当场抓到了本项目最严重的隐患 —— 见 §5.3。**

### 5.3 ★ 实测发现：simdutf 双份 + COMDAT 折叠（本轮最重要风险）

**事实**：

| | 版本 | 符号 |
|---|---|---|
| node/v8 内嵌 `deps/v8/third_party/simdutf` | **6.4.0**（`README.chromium`） | `?validate_ascii@implementation@haswell@simdutf@@UEBA_NPEBD_K@Z` 等 |
| vcpkg `simdutf` | **8.2.0** | **完全相同的符号名** |

实测 `dumpbin`（`simdutf.lib` 两份对比）：

```
??_7implementation@haswell@simdutf@@6B@          node:1  vcpkg:1   （虚表）
?validate_ascii@implementation@haswell@simdutf@@UEBA_NPEBD_K@Z  node:1 vcpkg:1
?detect_encodings@implementation@haswell@simdutf@@UEBAHPEBD_K@Z node:1 vcpkg:1
```

**两者的符号都是 `selection 2 (pick any)` 的 COMDAT。**

**这意味着什么**：链接器遇到同名 COMDAT 会**任意挑一份**（"pick any" 的字面语义）。
两版 simdutf 差 **6.4.0 → 8.2.0** 两个大版本，实现与内部状态极可能不同 ——
于是**哪个实现被选中取决于链接顺序**，产生"能跑但偶发行为不一致"的
**不稳定行为**。这正是用户直觉中担心的东西。

> **两次误报的教训**（值得写进方法论）：
> - 第一版检测器把 COMDAT 当强符号 → 报 904 个"冲突"（**假阳性**）
> - 第二版 COMDAT 过滤过头 → 报"无任何风险"（**假阴性**）
> - 真相在中间：**没有强符号冲突，但有同名 COMDAT 的语义折叠风险**
>
> → 检测"符号重复"**必须区分强符号与 COMDAT**，且要单独评估 **COMDAT 同名折叠**。

**解决方向**（待定，需权衡）：

| 方案 | 说明 |
|---|---|
| A. 全项目统一用 vcpkg 的 simdutf（8.2.0） | 需 v8 接受外部 simdutf（`node_shared_simdutf` 存在，说明支持）；**但 v8 对 simdutf 版本可能有 API 要求**，需验证 |
| B. 保留 v8 内嵌 simdutf，不引入 vcpkg simdutf | 即"v8 例外"覆盖到 simdutf；但 simdutf 是 vcpkg 官方 port 且是公共依赖，冲突面广 |
| C. 给两份 simdutf 做**符号前缀隔离** | 最彻底，但要改源码（违背"少改上游"） |

**用户已表态**："v8 可能不行，可以例外；对用户冲突可能明显无影响的库也可以例外，
比如 v8 的依赖里面，做了名字空间隔离的" ——
simdutf 恰好是"v8 的依赖"，且**它自己有 `simdutf::` 名字空间**，
但**名字空间不阻止 COMDAT 折叠**（mangled name 相同），所以"名字空间隔离"这条
判据在 COMDAT 场景下**不成立**，需要靠版本统一或符号前缀解决。

### 5.4 建议的 test 分层

| 层 | 内容 | 回应用户的疑虑 |
|---|---|---|
| T1 冒烟（现有） | `find_package` + 链接 + 跑 JS | — |
| **T2 版本断言** | 断言 `process.versions.*` 与 vcpkg 依赖版本一致 | "依赖是否真被替换" |
