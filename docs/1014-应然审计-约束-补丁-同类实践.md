## 1. 基准一：vcpkg 的"应然"是什么

`[上游源码/官方文档]` 以下四条是**规则**（不是风格偏好），我们的设计必须以此为基准：

1. **端口之间不得安装同名/同位文件**（Unique File Mapping Rule / "ports must install simultaneously"）。
   → 我们把 V8 头挪到 `include/node-v8/`、把 `abseil/highway/v8_zlib/crdtp` 挪到 `lib/manual-link/`，**符合**这条。
2. **上游不提供 CMake config 的 port，导出必须加** **`unofficial-`** **前缀、目标进** **`unofficial::<port>::`**。
   → 我们用 `unofficial-node-config.cmake` + `unofficial::node::node`，**符合**。
3. **toolchain / triplet 属于消费方**（`VCPKG_CHAINLOAD_TOOLCHAIN_FILE` 是 triplet 变量）。
   → 我们的 port 目录里确实**没有** triplet/toolchain（合规），但见 §2.2：代价被**转嫁**给了用户。
4. **`supports`** **只表达平台/配置表达式，不能写 triplet 名**；port 不能"要求"某个 triplet。
   → 符合（vcpkg.json:10）。

**推论（本文反复要用的一条）**：在 vcpkg 里，"正确"的检验标准不是"我们的 port 目录干不干净"，
而是"**一个按 vcpkg 习惯用库的人，需要额外知道/额外抄多少东西**"。用户原话"绑架范围是否足够小"
指的正是这个量。

## 2. 逐条审计：这些约束哪些是硬的

### 2.1 "同一个可执行里不能再链 vcpkg 的 abseil / highway"

**声称（当前 README / vcpkg.json / usage / 欠账 §5g）**：V8 用的是 abseil/highway 的**内部符号**，
两份实现会重复定义，所以同进程共存不可能，作为**已知硬限制**对外声明。

**应然**：理想是**零冲突**；"冲突"必须能被**机制化地证明**，而不是"试过一次失败"。

**证据（本次实测，推翻"内部符号/重复定义"的表述）**：

- 头文件 ABI 配置**不同**（这正是符号不会撞的原因）：
  - V8 自带那份（Chromium 副本）`deps/v8/third_party/abseil-cpp/absl/base/options.h`：
    `ABSL_OPTION_USE_INLINE_NAMESPACE 0`、`ABSL_OPTION_INLINE_NAMESPACE_NAME head`
  - vcpkg 那份（20260107.1）`.../include/absl/base/options.h`：
    `ABSL_OPTION_USE_INLINE_NAMESPACE 1`、`ABSL_OPTION_INLINE_NAMESPACE_NAME lts_20260107`
    `[本机实测]`（两条 `Select-String` 即可复现）
- 符号名因此**不相交**（dumpbin `/symbols`，对**已安装**的两侧库各取"已定义外部符号"）：
  - `manual-link/abseil.lib`（V8 那份，3369 个已定义外部符号）：带 `absl` 的符号里含 `lts_` 的 = **0**
    样本：`?kTrue@Condition@absl@@2V12@B`、`?Now@absl@@YA?AVTime@1@XZ`
  - `lib/absl_*.lib`（vcpkg 那份，90 个库）：带 `absl` 的符号里含 `lts_` 的 = **全部**
    样本：`?GetUsageConfig@flags_internal@lts_20260107@absl@@…`、`?$SeedGenException@lts_20260107@absl@@…`
  - 两侧 `absl` 命名符号**求交 = 0**；`highway` 两侧能取到的 `hwy` 命名外部符号均很少
    （highway 基本是头内联/模板），重叠的只有编译器 intrinsic 弱符号
    （`__xmm@…`、`__real@…`、`_Avx2WmemEnabledWeakValue`、`fprintf`、`sprintf_s`）——**良性**。
    `[本机实测]`（脚本见 §5 E1）
- 反面证据是**另一件事**：我们曾把 V8 的 abseil **换成** vcpkg 那份 → 链接期 LNK2019。
  原因是同一份 `.o` 引用 `absl::X` 而库里只有 `absl::lts_20260107::X` —— 这是**替换**失败，
  不是**共存**失败。

**判定**：**"不能共存"是过度声称**。

- 真正的硬约束是：**V8 必须用它自带那份头/库编译**（否则 ODR/编译错，run #17 的
  `spinlock.cc:71 redefinition of SpinLock::SpinLock` 就是这么来的）。
- 至于"消费方在**同一个可执行**里再链一份 vcpkg abseil"：**链接层是安全的**（符号不相交），
  代价是进程里有两份 abseil 运行时。abseil 官方设计内联命名空间（LTS）的**目的**正是
  "让不同版本的 abseil 能出现在同一个二进制里而不撞"（`[上游文档]` abseil.io/about/releases）。
- 附带一条**事实纠正**：vcpkg 的 `abseil` 端口**不提供 CMake config**
  （`share/abseil/` 下只有 copyright/vcpkg 元数据）`[本机实测]`，消费方本来就得手写链接，
  所以现实中"顺手链上 vcpkg abseil"的概率比想象的**低**。

**★ 根本解（下一 LTS 可达"零冲突"）**：
`[本机实测 + 上游源码]` node **v26.9.0 与 main 的** **`configure.py`** **已有官方开关**
`--shared-abseil` / `--shared-highway`（各带 `-includes/-libname/-libpath`；highway 默认 libname=`hwy`），
而**我们钉的 24.21.0 没有**（本地源码 grep 命中数 = 0；`deps/nghttp3` 也已从树里消失）。
同类项目已在用：FreeBSD `www/node26` 传 `--shared-abseil --shared-highway` 并删掉
`deps/v8/third_party/{abseil-cpp,highway}`；Arch 的 node 26 直接依赖 `abseil-cpp`。
⇒ **一升到下一个 LTS，我们可以删掉** **`patches/0015`、`redline-include-order.cmake`、
`lib/manual-link/`** **里的 abseil/highway 特例**，冲突从"声明"变成"零"。

### 2.2 Windows：必须 clang-cl（硬）vs 必须抄我们的工具链（软）

**应然**：消费方**不应该**为了用一个 port 而维护一份 543 行的工具链。

**现状**：`test/cmake/toolchains/` 共 543 行（`clang-cl.cmake` 182 + `msvc-command-line-env.cmake` 361），
外加 Windows 两个 triplet 各 \~67 行。这些是**消费方的构建配置**，即"用本 port 的人要自己再写一遍的东西"。

**判定**：

- "Windows 必须 clang-cl"——**硬**。node 24+ 官方 Windows 口径就是 ClangCL（`vcbuild.bat` 强制），
  且这是 ninja 生成器能编过 DevTools 协议模板的前提。这条不必解释也不该改。
- "必须把 clang-cl **交接**给 port"——**软**。portfile 本身有三级回退
  （`NODE_PORT_LLVM_BIN` → `$ENV{CC}` 匹配 clang-cl → `find_program(clang-cl)`，portfile:129-146）。
  真正硬的是 **MSVC/SDK 的** **`INCLUDE`/`LIB`** 必须在 port 子进程里就位（gyp + clang-cl 都要），
  而那目前**只有** `msvc-command-line-env.cmake` 会做 ⇒ 回退路径在实践中不成立。
- 这条**没有越界**（我们没把 triplet 塞进 port），但它把成本**转嫁**给了用户 —— 正是用户感受到的"不合格"。

**★ 根本解（可把 543 行退回 port 内部）**：

- vcpkg **自带** `vcpkg_find_acquire_program(CLANG)`（`scripts/cmake/vcpkg_find_acquire_program(CLANG).cmake`
  在 Windows 上会搜 `LLVMInstallDir`、`VCINSTALLDIR/Tools/Llvm`，必要时**下载 LLVM 15.0.6**）。
  `[本机实测]` 且**有官方先例**：`openssl` / `nettle` / `libass` / `libxt` / `gmp` / `vcpkg-make` 六个 port 都在用它。
- "找 VS → 设 `INCLUDE`/`LIB`/`PATH` → 找 SDK 版本 → 找 rc.exe"这一整套（即是那 361 行）**可以搬进
  `ports/node/scripts/`** 并在 `portfile.cmake` 里 include —— port 自己把环境摆好，是 vcpkg port 的常规做法。
- 结果：消费方**连自定义 triplet 都不需要**，直接用标准的 `x64-windows-static` / `x64-windows-static-md` 即可；
  `test/cmake/` 从此只是"本仓库测试工程自己的便利配置"，不再是"用户手册"。

**代价/风险**：搬进去后，port 的行为不再依赖消费方环境 ⇒ 需要 port 侧自己覆盖更全的分支
（VS 布局、SDK 版本、arm64 宿主），这类代码的**验证只能靠 CI 矩阵**（本地机器覆盖不到全部形态）。
这正是我们把 339 行放在消费端的原始理由——但那不是"正确"，只是"省事"。

### 2.3 Debug：消费方"必须用 release CRT"（软，且是自己造的）

**现状（usage:52-63）**：依赖被 triplet 钉死 `VCPKG_BUILD_TYPE release`；CMake/vcpkg 默认会按
CONFIG 给 Debug 切 `/MTd`，于是链接期 `_ITERATOR_DEBUG_LEVEL` mismatch ⇒ **要求消费方在 Debug 下也用** **`/MT`**。

**应然**：`VCPKG_BUILD_TYPE` 是**依赖**的口径开关，vcpkg 的默认是"两个都建"。
让消费方接受"我的 Debug 构建却必须用 release CRT"，是把内部实现细节泄露成对外契约。

**史实（重要）**：这条约束源于**一次过头的选择**。当初为了让 node 编 debug，把 triplet 设成
`VCPKG_BUILD_TYPE=debug`（**debug-only**），于是上游 brotli 等 port 的 `vcpkg_copy_tools`
在 debug-only 布局下直接 BUILD\_FAILED；随后改成了 `release`（**release-only**）。
但 vcpkg 的默认是**不设**（release + debug 都建）——**不设**既不会触发 brotli 那个坑，
也不需要消费方在 Debug 下换 CRT。

**判定**：**软约束，且可去**。

- 路线 A（正确、稳妥）：triplet 不设 `VCPKG_BUILD_TYPE` ⇒ 依赖双份；消费方 Debug 自然拿到 `/MTd` 依赖，
  port 侧按 `VCPKG_BUILD_TYPE` 决定编 node 的哪一份（并可把 debug 库按 vcpkg 惯例装进 `debug/lib`）。
  代价：首次安装的依赖构建时间翻倍（磁盘也翻倍）。
- 路线 B（保留现状）：继续 release-only，但把"消费方 Debug 也要 `/MT`"**由导出配置自动带上**而不是写在 usage 里。
- 附带发现：**`NODE_PORT_BUILD_TYPE`（私有环境变量）本身偏离 vcpkg 惯例** —— vcpkg 里决定
  "编哪一份"的是 `VCPKG_BUILD_TYPE`。这条偏离是为了绕开上面的坑而引入的；路线 A 可以把它消掉。

### 2.4 Windows 嵌入清单 / 增量链接（软，可自动化）

`usage:35-50` 让用户手抄三行：`/MANIFEST:EMBED` + `/MANIFESTINPUT:<清单>` + `/INCREMENTAL:NO`。
其中 `/INCREMENTAL:NO` 的**理由**是真实且查实过的（CMake 的 `vs_link_exe` 增量两遍链接会追加裸
`/MANIFEST /MANIFESTFILE:` 顶掉嵌入模式）。但这条**和已经导出的** **`/STACK:0x800000`** **是同一性质**
（都是"消费方可执行必须带的链接设置"）——`portfile.cmake:892-898` 已经把 `/STACK:` 导进
`INTERFACE` 了，manifest 那三条也该走同一条路。

**判定**：**软约束，自动化即可**（提醒：`/MANIFEST:EMBED` 只对**可执行**有意义，
用 INTERFACE 会连带作用到消费方的静态库目标，需在配置里写清适用条件）。

### 2.5 只交付静态库

**现状**：`vcpkg_check_linkage(ONLY_STATIC_LIBRARY)`，README/usage 写作"动态库**结构性不可能**"。

**应然/事实**：

- node **有** `--shared`（生成 `libnode.so.<NODE_MODULE_VERSION>` / `libnode.dylib`；Debian 就是
  拿它出 `libnode137` + `libnode-dev`、conda-forge 出 `libnode.so.147`）。`[上游源码 + 同类项目]`
- 但 `--shared` 上游自述 **"not officially supported for regular applications"**，
  且会 `force_dynamic_crt=1`（Windows 上切成 `/MD`）—— 与静态 CRT 口径**结构性冲突**；
  再叠加"我们交付的是嵌入用的库、消费方要的是静态链接"这一用途事实。
- ⇒ 正确说法是：**本 port 只实现静态形态**；动态交付需要**另一套 triplet/口径**（动态 CRT + `--shared`），
  属于"未实现"，不是"不可能"（vcpkg 里 `x64-windows` 这种动态 triplet 完全允许）。

**判定**：**半硬 + 有意选择**；建议只改措辞（"未实现"而非"不可能"），不必真做动态形态。

### 2.6 GNU 系 CMake ≥ 3.24 —— 这条反而是"应然"

`$<LINK_GROUP:RESCAN>` 是 CMake 为"静态库之间有环"提供的**官方**构造，且**去重不会把它拆散**
（`portfile.cmake:785-824` 里那段论证是站得住的）。CMake 3.24 发布于 2022，作为最低版本很温和。
⇒ **保留，不动**。（对照组：手上写 `-Wl,--start-group` 才是"自己造一套"，且会被 CMake 去重拆散。）

### 2.7 其他

- `supports: windows | linux | osx`：偏宽（Tier 1 只保证 2 个口径），但用户已拍板"等 arm64/debug 稳定后再收窄"。
- "`lib/manual-link/` 只列 4 个库"：`deps/v8/third_party/` 下还有 `re2 / fast_float / jsoncpp / rapidhash-v8 / siphash`
  等约 20 份 vendor 库 `[本机实测]`；手写白名单有漏网风险，**符号审计**（ctest `symbols-*`）是兜底。
  更稳的应然：白名单由"gyp 目标名 ⊂ vcpkg port 名"**机械推导**，而不是人工枚举。

| 0013 v8-compiler-add-descriptor-array-inl  | `deps/v8/src/codegen/compiler.cc`          | ④                 | 否             | 低            |
| 0018 test-py-print-exit-code               | `tools/test.py`                            | ⑤ 测试驱动            | 否             | 低            |

**读法**：**18 个里 8 个（44%）改的是 gyp 工具自己的 Python**（`tools/gyp/pylib/gyp/**`）。
这类改动既不是 node 的构建描述、也不是 V8 的源码，而是**vendored 的上游构建工具**，
上游随版本更新 ⇒ 每次升级 LTS 都可能要 rebase，且失败方式往往是"生成期静默出错"。

### 3.2 哪些是"官方机制优先"做得对的，哪些还在自己造

**已正确采用官方机制的（应然）**：
`--shared-*`（14 条，portfile:255-268）、`--with-intl=system-icu`、`--ninja`、
`--dest-cpu`+`--no-cross-compiling`（97417fd）—— 与 Debian/conda/Arch/Homebrew 完全同路。

**仍在"自己造一套"的（逐条给判定）**：

| 项                                                                 | 官方有机制吗                                                                             | 判定                                                                         |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| V8 的 simdutf 换成 vcpkg（0011+0012）                                  | **没有**（`--shared-simdutf` 只切 node→simdutf 的边；`v8_base_without_compiler` 仍无条件编自己那份） | 属于"超出官方"。发行版的做法是**接受两份并存**（COMDAT 折叠）。我们的做法更强（消重），但要吃 3 个补丁；**这是可选项，不是必需** |
| V8 的 v8\_zlib 换成 vcpkg（0014）                                      | **没有**（`v8_use_zlib` 是 features.gypi 变量，`configure.py` 未暴露）                        | 同上                                                                         |
| V8 自带 abseil/highway 的 include 优先级（0015 + 红线）                     | **没有**；**但 26 起有** **`--shared-abseil/--shared-highway`**                          | 26 起可整条删除                                                                  |
| clang-cl 的宏探测走 `clang.exe`（0007、0008）                             | 没有（上游只认 cl.exe/MSBuild）                                                            | 这是"换编译器的代价"，属必要                                                            |
| arm64 的 `-m64` 硬编码修正（0017）                                        | 没有（上游 Windows/ARM64 走 MSVC，碰不到这条路径）                                                | 必要                                                                         |
| Windows `msvs_configuration_platform` 大小写（`vcpkg_replace_string`） | 没有（上游走 MSBuild，大小写不敏感）                                                             | 必要，且**已用** **`replace_string`** **而非补丁**（应然的写法）                            |
| `node.gyp` 的 `/WHOLEARCHIVE` 路径（`vcpkg_replace_string`）           | 没有（上游 msvs 生成器的假设）                                                                 | 必要，写法正确                                                                    |

### 3.3 应然的最小化动作（按收益/风险排序）

**能** **`vcpkg_replace_string`** **的别用 patch**：`portfile.cmake` 已用这个套路处理两处（`node.gyp` 路径、
`common.gypi` 大小写），收益是"不怕上游挪行号 + 找不到锚点会当场报错"。
`0001`（`icu-system.gyp` 加一个空壳 `icudata` 目标）、`0011`、`0014` 大多是**对 gyp 文本的整块替换**，
可评估改成 `replace_string`；`0013`（补一行 include）也只是一行。

- **与 clang-cl 无关的 gyp 工具补丁应上游化**：`0006`（迭代器被 `str()` 成 `<map object at 0x…>`）、
  `0003` 的 `key=value` 被 `os.path.normpath` 折叠、`0005`（非 UTF-8 输出解码崩溃）、
  `0016`（thin archive）—— 这些都是**通用 bug**，与我们的口径无关，应该往 node 的 vendored gyp
  （即 gyp-next）上游提。上游化之后，升级即自动继承。
- **26 起删除**：`0015` + `redline-include-order.cmake` + `lib/manual-link/{abseil,highway}` 特例。
- **建立"升级 checklist"（欠账 §15 已记账，这里给出可机械化的条目）**：
  每次只升 LTS 时，逐项核对 ——
  ① `configure.py` 的 `shared_optgroup` 清单与 `configure_library(...)` 调用表是否增删改名；
  ② `tools/v8_gypfiles/*.gyp` 里 abseil/highway/simdutf/zlib 的 `*_ROOT` 与目标名；
  ③ `node.gyp` 的 `StackReserveSize`（`portfile` 已断言**恰好 1 处**，改了会当场红）；
  ④ `node.gyp` / `node.gypi` 的 `/WHOLEARCHIVE` 与 `node_shared_*` 条件；
  ⑤ `0009/0010` 的路径归一化是否上游已修（真修了就当红）—— 建议给这几条也加"锚点断言"。
- **补丁自身的"可验证性"**：现在的补丁只有注释说"为什么"，没有"上游若修好了会怎样暴露"。
  应然：对每个补丁尽量有**锚点唯一性断言**（`replace_string` 天然具备；patch 可用 `--dry-run` 做 lint）。

`[同类项目]` 以下都有可点来源（见 §8）。

| 项目                                | 口径                                                                                                                           | 产物 / 接口                                                                             | 对我们的启发                                                                                                                                                                                                                                                                                           |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Debian** nodejs 24.21.0         | `--shared`（+ 16 条 `--shared-*`）、`--with-intl=system-icu`、**总是传** **`--dest-cpu`**、交叉时用 `CC_host/CXX_host`                    | `libnode.so.<NODE_MODULE_VERSION>` + `libnode-dev`（**无 CMake config / pkg-config**） | ①"用系统库"是发行版共识 ②`--dest-cpu` 常态就该传（我们只在交叉时传）③他们**不出** CMake 接口 —— 我们的 `unofficial-` config 是**加分项**                                                                                                                                                                                               |
| **conda-forge**                   | `--shared` + 8 个 `--shared-*` + `system-icu` + `-j host`                                                                     | `libnode.so.147`                                                                    | 它用**自研 patch** 把 V8 的 abseil 换成系统 abseil（`0004-Support-System-abseil-cpp`，改 `configure.py` + 用空壳 `abseil.gyp`）。⇒ "替换 V8 的 abseil"确有先例，但属**补丁工程、每次升级要返工**；我们**不该**走这条（26 起有官方开关）                                                                                                                  |
| **Arch**                          | node 26 直接依赖 `abseil-cpp`（+ icu/zlib/zstd/nghttp2…）                                                                          | 随包 libnode                                                                          | `nodejs-lts-jod` 的 PKGBUILD **只有一个测试补丁** ⇒ "最小 patch" 的现实标杆                                                                                                                                                                                                                                      |
| **Homebrew**                      | 只 6 条 `--shared-*` + `system-icu`，**零补丁**                                                                                    | formula                                                                             | 依赖解绑是**按需**的，不是越多越好                                                                                                                                                                                                                                                                              |
| **Electron**                      | GN + `third_party/electron_node`，**约 55 个 node 补丁**                                                                          | 不对外提供 SDK                                                                           | 它的哲学是"**收敛成同一份实现**"（node 直接用 Chromium 的 `//third_party/{abseil-cpp,icu,zlib,brotli,zstd}`、BoringSSL 替代 OpenSSL），并且把 `use_system_*` 开关**上游化**（`build_allow_unbundling_of_node_js_dependencies.patch` → nodejs/node#55903）。⇒ ①"两份同名实现"是**公认要避免**的（我们方向对）②但**避免的方式是统一到一份**，不是"让它优先"③把开关上游化比长期维护补丁更省 |
| **vcpkg 官方 registry**             | **没有** node/v8/libnode 端口；只有 `node-api-headers`（纯头）、`node-addon-api`、`vcpkg-tool-nodejs`（host-only 工具，交叉时直接 FATAL）           | —                                                                                   | 我们是生态里**唯一的** node-as-library port ⇒ 没有"官方先例"可抄，但也没有撞名风险                                                                                                                                                                                                                                         |
| **vcpkg 官方 port 惯例**              | `openssl`/`nettle`/`libass`/`libxt`/`gmp`/`vcpkg-make` 用 `vcpkg_find_acquire_program(CLANG)` **自己取得编译器**                     | —                                                                                   | ⇒ §2.2 的"把工具链搬回 port"**有官方先例**，不是异想                                                                                                                                                                                                                                                              |
| **ConanCenter / node-api-dotnet** | Conan 的 `nodejs` 只是**预编译运行时**（`cpp_info` 全清空）；node-api-dotnet 提供 `Microsoft.JavaScript.LibNode`，并在推动**上游直接出 shared libnode** | —                                                                                   | "node as a library"在生态里仍是**少数派需求**，上游也在慢慢补（`--shared`、`--shared-abseil`）                                                                                                                                                                                                                         |

**提炼出的 7 条最佳实践**：

1. 依赖一律 `--shared-*` + `system-icu`，**不要**编自带副本（发行版共识）。
2. `--dest-cpu` 常态传（Debian 就是这么做的；我们的 x64-osx 事故正是没传）。
3. **同一二进制里避免两份同名实现** —— 首选"统一到上游那一份"（Electron），次选"接受折叠"（发行版），
   最次"让它优先"（我们现状）。
4. 能把开关**上游化**就上游化（Electron 的 `use_system_*` 已进 node 主仓）。
5. 补丁要少（Arch 的 LTS 配方只有 1 个补丁），且**与平台无关的补丁优先提上游**。
6. 消费接口**要给出**（Debian/Fedora 只有裸库/`.pc`；我们给 `unofficial-` CMake config 是更现代的形态）。
7. 让**用户**零负担地"按 vcpkg 习惯用"：标准 triplet + `find_package(unofficial-node CONFIG)` 两行足矣
   —— 这正是 §2.2 要修的东西。

## 7. 本研究的局限（未验证项，明确标注）

1. **没有做"两份 abseil 同进程真实链接"的端到端验证**——本次只做到**符号集合不相交**（这已足以
   排除 LNK2005 类"重复定义"，但不能排除运行期行为差异，例如两份 abseil 的全局状态）。

   未进 vcxproj、`-L` 误译、`/WHOLEARCHIVE` 缺失）—— 本文未重复验证。

   需要一轮 CI/本机实测才能定论（重点是：port 自设环境后，标准 `x64-windows-static` 是否能编过）。

6. Fedora rawhide / Arch 当前 node 26 配方的原文**未直接读到**（站点反爬），只有包页依赖与旧版旁证。
