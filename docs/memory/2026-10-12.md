## abseil/highway 的 include 顺序：上一轮的修法是错的，本轮推翻重做

- **错在哪**：上一轮"让自带头在 include 顺序上赢"是把自带目录塞进
  `--shared-openssl-includes` / `--shared-zlib-includes`，理由写的是
  "configure_library() 按调用顺序 append，给的顺序就是 -I 的顺序"。两点都错：
  1. `configure_openssl(output)` 在 configure.py 里是**最后**被调用的（2641 行），
     它给的目录必然排在所有 `${_inc}` **之后**；
  2. gyp 对 `include_dirs` **去重只保留首次出现**，靠 append 永远抢不到前排。
- **证据链**（别再靠猜）：`config.gypi` 的 `target_defaults.include_dirs` 14 条里
  highway/src 在第 0 位、abseil-cpp 在第 **13** 位；生成的 `abseil.ninja` 里

  用 clang-cl 按这四条 `-I` 原样复现 → `error: non-constexpr declaration of
  'SpinLock' follows constexpr declaration`（v8 自带的头是 `explicit SpinLock(...)`，
  vcpkg 的是 `constexpr explicit SpinLock(...)`）。
- **现修法**：`patches/0015-configure-prepend-v8-bundled-includes.patch` 在
  configure.py 末尾**整体前插** `output['include_dirs']`；
  portfile 里 openssl/zlib 的 `--shared-*-includes` 恢复成 `${_inc}`（不再劫持）。
- **配一条可执行红线**：`ports/node/scripts/redline-include-order.cmake`，

## Windows 下 node.exe 链接失败（新发现 + 已修）

- 症状：`LINK : fatal error LNK1356: 找不到为延迟加载指定的库 lib/node_base.lib`。
- 根因：`node.gyp` 里 Windows 的 `/WHOLEARCHIVE:<(PRODUCT_DIR)/lib/<...>` 是照
  **msvs 生成器**写的；gyp 的 **ninja** 生成器在 Windows 上 `type_in_output_root`
  只有 executable / loadable_module / shared_library，static_library 落到 `obj/`
  （实测 `obj/node_base.lib`、`obj/tools/v8_gypfiles/v8_base_without_compiler.lib`，
  `lib/` 目录不存在）。同一文件里 Linux 那侧本来就写 `<(obj_dir)/...`。
- 修法：portfile 里（仅 Windows）用 `vcpkg_replace_string` 改那两条，不用补丁
  （字符串各自唯一，不怕上游改行号）。
- **★ 必须放在 `configure.py` 之前改**（第一版放后面，白跑 30 分钟）：
  改的是 gyp 的**输入**，ninja 文件是 configure.py 内部调 gyp 生成的；而且
  `out/Release/build.ninja` 里**压根没有 `node.gyp` 这个依赖**（gyp 这次没生成
  自更新规则）⇒ 事后改 gyp 既不触发重新生成、也不会被 ninja 察觉。
  验证：替换确实生效（node.gyp 里已是新路径），链接照样报 LNK1356。
  挪到前面之后，生成的 `obj/node.ninja` 里是
  `WHOLEARCHIVE:obj/node_base.lib`（正确）。

## ctest 第二轮（修完第一轮后）新暴露的 4 个坑

1. **`_popen` 在 Windows 底下是 `%COMSPEC% /c <串>`，而 cmd 对 /c 后面那串有著名的
   引号剥离规则：引号数 > 2 时把最外层的一对剥掉**。我们拼的 `"C:\...\node.exe" -p "js"`
   首尾本来就是引号，一剥就变成 `C:\...\node.exe" -p "js`（少前引号）→
   "不是内部或外部命令"，现象看起来像"node 跑不起来"。
   修法：**外面再套一层引号**，让 cmd 剥掉的是故意加的那层。
2. **`cmd /c` 不认正斜杠的程序名**（报"命令语法不正确"，0.02s 就退 —— 根本没跑到
   node）。port 导出的是可移植的正斜杠路径 ⇒ 消费端要用 `file(TO_NATIVE_PATH)`
   转成反斜杠再给 `cmd /c`。**不要**在 port 里做这个转换：那会把
   `${CURRENT_PACKAGES_DIR}`（packages 目录）烤死进配置，而 vcpkg 之后会搬目录。
3. **ctest 的 `PASS_REGULAR_EXPRESSION` 加 `^...$` 锚在 Windows 上不可靠**：
   输出以 CRLF 结尾，`$` 卡在 `\r` 前；连 `^24\.21\.0[[:space:]]*$` 都匹配不上。
   要断言版本号就直接 `24\.21\.0`，别加锚。
4. **比对 openssl 版本要取 `OPENSSL_VERSION_STR`（"3.6.3"），不是
   `OPENSSL_VERSION`**（"OpenSSL 3.6.3 9 Jun 2026"）：后者过"只留数字与点"的
   归一化会把日期拼进来，C++=3.6.3.9.2026 vs JS=3.6.3，看起来像版本不一致。

## run #23 的两条修复线（本轮动手改的）

### 链接组的根因升级：不是"再加一个库"，而是"手写标志用错了工具"

- CMake 官方文档对 `$<LINK_LIBRARY>` 明确写着：**"does not guarantee that the list …
  will be kept grouped together. To manage constructs like --start-group and --end-group …
  use the LINK_GROUP generator expression instead."** ⇒ port 把
  `"-Wl,--start-group" … "-Wl,--end-group"` 当普通链接项塞进 `INTERFACE_LINK_LIBRARIES`
  这件事本身就是错的工具。
- 而且 `$<LINK_GROUP:RESCAN>` 的语义里有一条**正好治我们的病**：CMake 知道这批库属于一个组，
  消费端若又列了组内某个库，**那次出现会被替换回组内** —— 手写标志没有这层语义，
  所以会被"链接项去重"拆散（x64-linux 那 174 条 undefined reference 里 173 条是 nghttp2）。
- RESCAN 的平台支持是**查 CMake 自己的 Modules 得到的硬事实**（不是猜）：
  `cmake-4.4.0/share/cmake-4.4/Modules/Platform/{GNU,Linux,FreeBSD,NetBSD,Haiku,SunOS,Windows-GNU}.cmake`
  里定义了 `CMAKE_LINK_GROUP_USING_RESCAN_SUPPORTED TRUE` + `LINKER:--start-group`。
  **Apple 与 MSVC 都不在列表里** ⇒ Apple 上用它会直接报错，不能无脑统一。
- **又一处上游误读被纠正**（与 §5g 的 abseil 同类）：portfile 原注释说
  "make.py 的 LINK_COMMANDS_MAC（209 行起）用的是同一条命令 ⇒ macOS 的 ld64 也认这组开关"。
  查上游原文：`LINK_COMMANDS_MAC` 是 `$(LINK) … -o "$@" $(LD_INPUTS) $(LIBS)`，**不带**这组开关；
  带 `--start-group` 的 `cmd_link`（260 行）属于**通用（Linux/BSD）**命令表。arm64-osx 的
  `ld: unknown options: --start-group --end-group`（run #23 实测）就是抄错注释的代价。
- 最终口径（建成三分支，每条都有上游或实测依据）：Windows 平铺（link.exe 反复扫描）、
  Apple 平铺（ld64 无 rescan 构造，与上游 MAC 命令一致）、
  其余 GNU 系用 `$<LINK_GROUP:RESCAN,…>`（要求消费端 CMake ≥ 3.24，已在生成的 config 里
  `FATAL_ERROR` 前置检查 + 写进 `usage`）。
- 同时修掉消费端的重复链接：`test/unit/CMakeLists.txt` 里 `unit_node_coexist` 曾同时列
  `node::nghttp2` 与 `${NGHTTP2_LIBRARY}`（同一个 libnghttp2.a）⇒ CMake 去重把**组内那份**删掉。
  现在只留 `GTest::gtest_main / node::node / fmt::fmt`（nghttp2 的头单独给，符号由接口提供）。

### 新增一把"机制"闸门：portfile 必须能被 CMake 解析

- 事实：**CMake 是先整体解析、再执行**（用 `cmake -P` 喂一个第 2 行有未闭合引号的文件实测：
  第 1 行的 `message()` 不执行，直接报 parse error）⇒ `cmake -P` 就是现成的语法闸门
  （执行一定会在第一个 `vcpkg_*` 命令处停下，那不算错）。
- 落地成 `.github/workflows/ci.yml` 的 lint 步骤：遍历 `ports/node/**/*.cmake`，
  出现 "Parse error" 即红。起因很具体：给链接组写注释时我自己就写出过一个未转义的引号
  （在 `string(APPEND _cfg "…")` 里用了 ASCII 引号），当时是 configure 阶段挡下的 —— 运气不是机制。
- 同类受益：任何 `string(APPEND _cfg …)` 里的转义错误（`\$` / `\"` / `\n`）现在配置期就见红。
