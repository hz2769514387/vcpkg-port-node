### ★ 根因（修正了 run #23 时的猜测）

- run #23 时我以为是"宿主工具被编成了 arm64"。**查实是反的**：工具被编成 **x64**，
  却链上了 **ARM64** 的 vcpkg 库。
- 证据链：
  * 链接命令行是 `gyp-win-tool link-wrapper environment.x64 … link.exe /OUT:gen-regexp-special-case.exe`
    ⇒ 用的是 **x64 宿主工具链**；
  * 报错原文就是 `target machine type 'x64'`；
  * 它链上的 21 个库全在
    `test/build/windows-clang-cl-arm64/vcpkg_installed/arm64-windows-static-clang/lib/`
    （icuin/icuuc/icudt/zs/llhttp/libuv/ada…）；
  * 本机 x64 的 `out/Release/build.ninja` 里**根本没有 `environment.*` 字符串**
    （原生构建不生成 host toolset）—— 反证 arm64 那次确实走了 host toolset。
- gyp 定义（`tools/v8_gypfiles/v8.gyp`，node 的 configure 会把 v8 的 gypfiles 生成到这里）：
  ```python
  'gen-regexp-special-case': {
    'dependencies': ['v8_libbase', 'v8_maybe_icu', 'abseil.gyp:abseil'],
    'conditions': [['want_separate_host_toolset', {'toolsets': ['host']}], …],
  }
  ```
  而 `configure.py:1723`：`o['variables']['want_separate_host_toolset'] = int(cross_compiling)`
  ⇒ **交叉编译才打开** host toolset（本机 x64 原生构建时它是 0）。
- **真正的缺口**：`v8_maybe_icu` 依赖 `<(icu_gyp_path):icui18n/icuuc`，而我们用
  `--with-intl=system-icu` ⇒ ICU 变成**外部库、只有一条路径**（= 目标架构那份 vcpkg ICU）。
  gyp 的 host toolset 机制能把**树内**依赖给宿主编一份，但**变不出一份宿主架构的外部 ICU**。
- **不是"一个工具的小毛病"**：`mksnapshot` 也有同一条件
  （`['want_separate_host_toolset', {'toolsets': ['host']}]`）且依赖 `v8_maybe_icu` + 整个 v8
  ⇒ 修完这条后面还有同一堵墙。所以 arm64-windows **交叉编译**这条路要成立，
  必须补一份宿主架构的 ICU（= 真正意义上的 host toolset）。

### ★★ run #26 的 arm64 真因（我自己上一轮那批改动的"报错"把它逼出来了）

## ★★ run #27 的 arm64：第一版把 v8 编起来，撞上 gyp 的大小写 bug（已修）

  ④ `ninja.py:405` `self.ninja.variable("arch", self.win_env[arch])` → `environment.x86`
