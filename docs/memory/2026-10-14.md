## ★ "已经 push 但好像没运行"：其实跑了，是 0 秒失败（workflow 文件非法）

- 现象：`ci lint` 绿（8 秒），但 `ci debug` 与 `platform` 两个 run **0 秒失败、没有 job**，
  而且列表里显示的 run 名是**文件路径**而不是 `name:` —— 这是 GH"文件加载失败"的典型表征。
- 报错原文：
  `Invalid workflow file: .github/workflows/ci-debug.yml#L67 → ./platform.yml : (Line: 75, Col: 5):
   'continue-on-error' is already defined`
- 根因：拆分脚本在 build 作业顶部插入了一份 `continue-on-error`，原作业体里那一份没删
  ⇒ 同一个映射里两个同名键。**PyYAML 遇到重复键只保留最后一份、不报错** ⇒ 本地 YAML 解析
  与结构自检全过，只有 GitHub 会判文件非法。调用方（ci debug）因为依赖它，一起挂。
- 处置（`fc20eab`）：删掉后插的那一份 ⇒ 保留原位置（runs-on 之后）那一份。
- **机制**：新增 `tools/check_workflows.py` 并接进 ci-lint.yml：
  * 自定义 loader —— **遇到重复映射键就报错**（普通 safe_load 抓不到）；
  * 顺带校验 inputs 声明 vs 引用、`uses:` 指向存在且是 workflow_call、`with:` 键合法、
    矩阵字段齐全、`uses:` 与 `steps:` 不混用；
  * `--self-test` 造两个坏样本（重复键 / 引用不存在的被调 workflow）断言会红。
  * 本机正反验证：塞回重复键 ⇒ `duplicate key 'continue-on-error' at line 70` 退出码 1；
    删掉 ⇒ 0。
- **教训（值得记）**：workflow 文件里的**重复键**是"本地任何 YAML 解析都过、GitHub 直接拒收"的
  一类错误；拆分/改写 workflow 后必须过这一条闸门，不能只做 safe_load。
- 待推：`fc20eab`。推了之后 ci lint 与 ci debug 才会真正跑起来（debug 是首次实测，六档 allow_failure）。

## ★ 第二发：continue-on-error 不是布尔 ⇒ 六腿 0 秒处 "Unexpected value 'true'"

- 报错：`Error when evaluating 'continue-on-error' for job 'build'. platform.yml (Line: 71, Col: 24):
  Unexpected value 'true'`（×6，各腿一处）+ logs job `exit 2`。
- 原因：**`continue-on-error` 只接受布尔**。调用方矩阵给的是 `allow_failure: "true"`（字符串），

  ⇒ 必须写成比较。本机正反验证过（改回直接引用 ⇒ 报错退出码 1；改回来 ⇒ 0）。

- 现象：六个腿在**配置期**就挂（`vcpkg install - failed`，随后 Ninja/CXX 找不到的报错都是**连带**，

  ```
  CMake Error at scripts/cmake/vcpkg_copy_tools.cmake:19 (message):

  ```
- 原因：上一版让三元组在 `NODE_PORT_BUILD_TYPE=debug` 时把 **`VCPKG_BUILD_TYPE` 设成 debug**
  ⇒ 依赖也进 debug-only，而 vcpkg 在 debug-only 下把可执行放进 `debug/tools/`，
  brotli 的 portfile 却在 `tools/brotli` 找 ⇒ 直接打死。这类上游 port 不止一个。
- **新口径（`a92c781`）**：依赖**永远 release**（三元组写死 `VCPKG_BUILD_TYPE release`），
  node 自己按 debug 编 —— 两个开关分开：
  * portfile 只看环境变量 `NODE_PORT_BUILD_TYPE=debug` ⇒ `configure.py --debug` +
    gyp 输出目录 `out/${_node_cfg}`；库仍装 `lib/`、可执行仍 `tools/node`（单口径常规布局），
    不碰 vcpkg 的 `debug/` 布局；Windows 上两边都是 `/MT`，不撞运行时库。
  * "debug 从未实测"那条 WARNING 的触发条件也改成同一个环境变量。
  * port-version 9 → 10。
- **教训**：`VCPKG_BUILD_TYPE` 是**依赖**的开关，不是"本 port 自己"的开关；想让本 port 编 debug
  而依赖不动，就要用**自己的**环境变量分出来。另外"配置期 vcpkg install 失败"后面的
  Ninja/CXX 报错全是连带，判读时先找 `error: building <port>`。
- 待推：`a92c781`。预期下一轮能真正进入**编 node（debug）**阶段。

## ★★ 第一夜续：ICU pkg-config 泄漏 + "旧 debug 腿从未真编 debug" 的真相

1. **ICU 不走 --shared-***（node 24 没有 --shared-icu）：走 `--with-intl=system-icu` +
   pkg-config。第一份 portfile 忘了按口径切 PKG_CONFIG_PATH ⇒ debug 构建链 release 的
   icuuc.lib（LNK2038：_ITERATOR_DEBUG_LEVEL 0 vs 2）。已修：PKG_CONFIG_PATH 与 LIB
   都在构建循环里按口径切（debug 侧是 <triplet>/debug/lib/pkgconfig，里面的 icu-uc.pc
   正确指向 -licuucd）。注意 vcpkg 的 PKGCONFIG 获取器给的是 **mingw64 pkgconf**
   （downloads/tools/msys2/*/mingw64/bin/pkg-config.exe）——读得了 Windows 风格
   PKG_CONFIG_PATH；MSYS2 那份（usr/bin/）读不了，别混。
2. **历史真相（重要）**：旧 CI 的 "ci debug" 腿**从未真正编过 debug node**！
   私有开关 NODE_PORT_BUILD_TYPE 是环境变量、**不进 vcpkg ABI 哈希** ⇒ ci-debug 的
   triplet/portfile 与 release 完全一致 ⇒ vcpkg 直接复用已安装的 release 产物。
   memory 里 run #38 的"libcpmtd value 2 vs node_base.lib value 0"（消费方 /MTd 链到
   value 0 的 node_base.lib）就是证据——那个 node_base.lib 是 **release** 编的。
   欠账 §1"debug 从未实测"一直准确。路线 A 把口径放进 triplet ⇒ 进 ABI 哈希 ⇒
   debug 第一次真编，于是这个潜伏 bug 现行。
3. **踩坑**：后台构建日志若只有 `CONFIGURE_RC=1` 一行，说明 cmake 根本没跑——
   是前面的 `rm -rf build/windows` 被残留的 `vcpkg-running.lock` 占用失败、&& 链断了。
   先删 lock 文件再删目录。
4. 当前状态：第三份全量构建（tmp/local-dual-build3.log）进行中，node port 双份编译。
