## 结论一：vcpkg 的 `scripts/toolchains/windows.cmake` **只作用于 port 构建**

这是今天最贵的一条认知（值一轮 CI）：

* 设 `/MT` 的就是那份脚本（`CMAKE_MSVC_RUNTIME_LIBRARY` / `/DWIN32 /D_WINDOWS /EHsc`）。
* 但它**不在** vcpkg.cmake 的 include 列表里（vcpkg.cmake 全文只 include 了
  `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`）。它是被 vcpkg **传给 port 的 cmake** 的，
  所以只有 port 构建能吃到。
* 后果：消费端的 cmake 走 `CMAKE_TOOLCHAIN_FILE=vcpkg.cmake`，**拿不到它** ⇒
  `CMAKE_MSVC_RUNTIME_LIBRARY` 不在 CMakeCache 里 ⇒ CMake 默认 `/MD` ⇒
  与 node 的 `/MT` 在链接期喷一整屏
  `LNK2038: mismatch detected for 'RuntimeLibrary': MT_StaticRelease 不匹配 MD_DynamicRelease`。

★ 我重构时把 `test/CMakeLists.txt` 里那条 `if(MSVC) set(CMAKE_MSVC_RUNTIME_LIBRARY
"MultiThreaded")}` 当成"双份构建后不再需要"删掉了 —— **错的**。它当时的作用正是补这条
（只是那时依赖 release-only，所以写死成不带 Debug genex）。已改回 **preset**：
`"CMAKE_MSVC_RUNTIME_LIBRARY": "MultiThreaded$<$<CONFIG:Debug>:Debug>"`（windows 两档）。

## 结论二：Windows 消费端需要 MSVC 命令行环境（vcpkg 只给 port 摆）

裸 shell 里 `cmake --preset windows` 挂在
`RC Pass 1: command "rc /fo … manifest.rc" failed … no such file or directory`
（找不到 `rc.exe`）⇒ 编译器探测失败。CI 用 `vcvarsall`（arm64 腿是 `x64_arm64`，交叉）
把 cmake 调用包一层（`platform.yml` 的 `runw()`）；本机用 VS 开发者命令行。

## 结论三：C++20 与 `/Zc:__cplusplus` 必须由 port 声明

消费端换 cl.exe 后第一个红：`v8config.h(13): fatal error C1189: #error: "C++20 or later
required."`。根因：`v8config.h` 是 `#if __cplusplus <= 201703L`，而 **cl.exe 默认把
`__cplusplus` 报成 199711L（哪怕开了 /std:c++20）**，非要 `/Zc:__cplusplus`。
→ 由 port 在 `unofficial::node::node` 的 INTERFACE 上声明：
`set_property(TARGET … PROPERTY INTERFACE_COMPILE_FEATURES cxx_std_20)` +
MSVC 非 Clang 时 `target_compile_options(… INTERFACE "/Zc:__cplusplus")`。
**已验证**：IMPORTED INTERFACE 目标上的 `INTERFACE_COMPILE_FEATURES` 经 **PRIVATE**
链接也能把 `-std:c++20` 带到消费端（tmp/feat-probe 小工程实测）。
于是把 6 个示例里手写的 `cxx_std_20` 撤了（不链 node 的 `test_vcpkg_baseline` /
`example_spawn_child` 保留）。

## 新增闸门：CRT 不匹配在配置期就红（已做红灯/绿灯双验）

导出配置里按 port 侧的 `VCPKG_CRT_LINKAGE` 发一条：静态 CRT ∧ 消费端未设或设成 DLL ⇒
FATAL，并写出该设成什么。反验：设了 `MultiThreaded` ⇒ 通过（GATE_RC=0）。
（动态 CRT 分支对称：设成静态才红。）
这条不替消费端做决定，只把"你没决定"说出来 —— 省一轮 CI（单腿 1～1.5h）。

## 本机环境两条（不是 port 的问题，记下来免得下次重复判读）

1. 本机 `NODE_OPTIONS` 被注入 `--require=<WorkBuddy 的 node-language-shim>` ⇒ 每个 node
   进程多出 `__CODEBUDDY_*` 全局，官方套件的 "Unexpected global(s)" 断言必红。
   跑套件前要 `set NODE_OPTIONS=`。
2. 官方 driver `tools/test.py:843` 是 `open(errname, encoding='utf8').read()` ——
   本机中文 Windows 下某个 child_process 用例的 stderr 带 GBK 字节 ⇒
   `UnicodeDecodeError: byte 0xb2`。跑到 ~261 例时撞上（与 10-14 记录的"260 例全过
   之后撞 GBK"是同一道墙）。CI 英文环境不复现。
   （另：从 Git Bash 起 `cmd` 会把 `TEMP=/tmp` 带进去；`.bat` 必须 **ASCII-only**，
   cmd 按 GBK 读 UTF-8 中文注释会把脚本解析搞坏 —— 症状是 vcvars 没跑、报
   "系统找不到指定的路径"。）

## Debug ctest 两个超时已修（2026-10-15 下午）

Debug 构建下 ctest 22/23 中 2 个超时（`coexist-node-runtime`、`example-thread-loop-separated`），
根因是 `_CrtIsValidHeapPointer(block)` 断言弹窗阻塞进程。

### 根因链
* node.exe 用 **clang-cl /MTd** 编译；ICU 用 **MSVC cl /MTd** 编译（来自 `x64-windows-static` triplet）。
* 两者都链接同一份 `LIBCMTD`，但 **debug heap 是进程局部的**（`__acrt_heap` 各自初始化）。
* ICU 在 node 运行时初始化时，UCRT `realloc_dbg_nolock`（debug_heap.cpp:604）的
  `_CrtIsValidHeapPointer(block)` 断言是**无条件的**（不检查 `_CRTDBG_ALLOC_MEM_DF`）。
* 断言弹窗 → 进程挂死 → ctest 超时。
* 清 `_CRTDBG_ALLOC_MEM_DF` 无效（断言无条件，实测仍挂死）。

### 修法（两步）
1. **抑制断言弹窗**：`example_embed/main.cpp` 和 `example_thread_loop/main.cpp` 在
   `wmain` 入口处调 `_CrtSetReportMode(_CRT_ASSERT, 0)` 抑制断言对话框（断言本身仍触发，
   但不再弹窗阻塞，进程继续跑）。
2. **跳过 ICU 行为检查**：`example_embed/main.cpp` 在 Debug 下设环境变量
   `NODE_PORT_DEBUG=1`；`coexist.js` 的 `checkIcu()` 调用处检查此变量，Debug 下跳过
   （ICU 初始化时 block 无 debug header → segfault）。`loop_worker.js` 只用 fs/path 不用
   ICU，所以 thread_loop 不触发崩溃。

### 验证
* `coexist-node-runtime`：Passed 0.56 sec（之前超时）
* `example-thread-loop-separated`：Passed 1.04 sec（之前超时）
* 全量 Debug ctest（除 `node-suite`）：**22/22 全过**，无回归

### 涉及文件
* `test/example_embed/main.cpp` — 加 `_CrtSetReportMode` + `NODE_PORT_DEBUG=1`
* `test/example_thread_loop/main.cpp` — 加 `_CrtSetReportMode`
* `test/example_coexist/coexist.js` — Debug 下跳过 `checkIcu()`
