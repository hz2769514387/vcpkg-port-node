## 2. 三类真因

### 2.1 arm64-windows：消费端工程被编成了 x64（我们的缺陷，已修）

**症状**（构建期，1h35m 处）：链接 `app/node.exe` 时

```
lld-link: error: node_base.lib(node_base.callback.obj): machine type arm64 conflicts with x64
```

**关键观察**：库是 arm64、**被链接的目标却是 x64** ⇒ node 自己的库在 port 侧已经真的是 arm64
（patch 0017 生效了），但**消费端（本仓库 `test/`）编出来的对象还是 x64**。
链接命令行里 `/machine:x64` 就是这个：

```
... lld-link.exe /nologo app\CMakeFiles\node_embed.dir\main.cpp.obj /out:app\node.exe ... /machine:x64
```

**根因（可查）**：

1. `test/cmake/toolchains/clang-cl.cmake` 与 `msvc-command-line-env.cmake` 都靠
   `VCPKG_TARGET_ARCHITECTURE` 判断目标架构，**空值默认 x64**；
2. 而 `VCPKG_TARGET_ARCHITECTURE` 在**消费端进程里永远是空的**：
   * `vcpkg.cmake` 第 **209 行**就 include 链式工具链（= 我们的 clang-cl.cmake），
     而那个文件**从不设置**这个变量（grep 全文只有第 971 行把它列进 try_compile 的传播名单）；
   * vcpkg **编 port** 时是另说 —— 它把 `-DVCPKG_TARGET_ARCHITECTURE=arm64` 显式传给子进程
     （实测证据：`log/#14` 里 abseil 的 configure 命令行中就有这一项）。
3. 于是消费端：`--target=x86_64-pc-windows-msvc`（CMake 对 clang-cl 也认
   `CMAKE_CXX_COMPILER_TARGET`，见 `Modules/Platform/Windows-Clang.cmake` 里的
   `COMPILE_OPTIONS_TARGET`）+ `LIB` 指向 `<MSVC>/lib/x64`。
4. 为什么以前没暴露：run #28 之前，node 自己的库也被 gyp 的 `-m64` 编成了 x64 ——
   两半"错得一致"，症状只是 204 个 CRT 符号缺失；#28 修好 node 侧之后，
   消费端这一半的错才第一次显形。

**修法**（`msvc-command-line-env.cmake` + `clang-cl.cmake`）：架构解析统一成 `NODE_PORT_TARGET_ARCH`，
取值顺序 `VCPKG_TARGET_ARCHITECTURE` → `VCPKG_TARGET_TRIPLET` 首段（vcpkg 的 triplet 命名约定就是
`<arch>-<os>[-变体]`）→ 宿主架构；**三条都拿不到直接 FATAL**，不再有"静默退 x64"。

**本机验证**（模拟"只给 triplet"的消费端姿势，用 `project(NONE)` 探针）：

| 输入 | NODE_PORT_TARGET_ARCH | compiler target | msvc lib 目录 |
|---|---|---|---|
| `-DVCPKG_TARGET_TRIPLET=x64-windows-static-clang` | x64 | `x86_64-pc-windows-msvc` | x64 |
| `-DVCPKG_TARGET_TRIPLET=arm64-windows-static-clang` | arm64 | `aarch64-pc-windows-msvc` | arm64 |
| `-DVCPKG_TARGET_ARCHITECTURE=arm64` + x64 triplet | arm64（前者优先） | `aarch64-pc-windows-msvc` | arm64 |
| `-DVCPKG_TARGET_TRIPLET=ppc-...` | — | **FATAL：认不出的目标架构 'ppc'** | — |

### 2.2 Linux + macOS 的 `test-node-run`：套件脚本丢了执行位（我们的缺陷，已修）

**症状**：`test-node-run` 里 **6 个子用例全红**，且**每个都是 stdout 为空**：

```
Test failure: 'adds node_modules/.bin to path'          Input: ''
Test failure: 'appends positional arguments'            Input: ''
Test failure: 'should set PATH environment variable …'  …
Test failure: 'should set special environment variables'…
Test failure: 'will search parent directories …'        …
Test failure: 'escapes shell characters'   actual: ''  expected: "Arguments: '%PAYLOAD% $PAYLOAD'\n…"
```

**判读要点**：`echo`/`pwd` 那类用例（shell 内建 / package.json 里的普通命令）**通过**，
**凡是去执行 `node_modules/.bin/<脚本>` 的都失败** ⇒ 不是 `--run` 的问题，是**那些脚本跑不起来**。
真正的报错在 `child.stderr` 里（用例不打印它）——所以日志上完全看不出是权限问题。

**根因（在测试机上实测）**：CMake 的 `file(INSTALL)` **默认按 0644 落盘**。
文档里"Copying preserves input permissions … (default is USE_SOURCE_PERMISSIONS)"那句
**只适用 `file(COPY)`**，`file(INSTALL)` 走的是 `install()` 那一套默认值。

探针（Ubuntu 24 / cmake 4.4.0，`/tmp/mode-probe`）：

| 环节 | 执行位 |
|---|---|
| 源文件 | `-rwxr-xr-x`（755） |
| `cmake -E tar xzf`（= `vcpkg_extract_archive` 用的同一条命令） | 755 ✓ 保留 |
| `file(INSTALL <dir>/ DESTINATION <dst>)`（= portfile 装 test-suite 的写法） | **`-rw-r--r--`（644）✗ 丢了** |
| `file(INSTALL … USE_SOURCE_PERMISSIONS)` | 755 ✓ 回来 |

Windows 不受影响（那边走 `.bat`，cmd.exe 不看执行位）——这也解释了为什么只有 Linux/macOS 红。

**修法**：
* `ports/node/portfile.cmake` 里装 `test/` `tools/` `benchmark/` `doc/` `lib/` `src/` `deps/*`
  以及 tools feature 的 `deps/npm` `deps/corepack` 的 `file(INSTALL)` **全部补 `USE_SOURCE_PERMISSIONS`**；
* `test/tests/ctest_node_suite.cmake` 增加红线 **`node-suite-fixtures-executable`**：
  UNIX 上配置期就检查 `test/fixtures/run-script/node_modules/.bin/*`（非 `.bat`）是否可执行，
  不可执行就 FATAL —— 不必等二十多分钟的套件跑完才发现。

### 2.3 Linux + macOS 的两条 socket 用例：套件临时根太长（我们的缺陷，已修）

**症状**：

```
test-fs-cp-async-socket.mjs        Error: listen EINVAL … /…/node-suite-tmp/node-suite/.tmp.1049/copy_%1/68975.sock
test-fs-cp-sync-copy-socket-error  ENOENT（socket 没建出来）而不是期望的 ERR_FS_CP_SOCKET
```

**根因**：这两条用例要 `listen()` 一个 UNIX domain socket，而 `sun_path` 上限 **108 字节**（含结尾 NUL）。
路径形状 = `<临时根>/.tmp.<线程号>/copy_%<n>/<pid>.sock`（`tmpdir.js` + `common/fs.js` 的 `nextdir()`）。
我们把临时根放在 `${CMAKE_CURRENT_BINARY_DIR}/node-suite-tmp`，CI 上就是
`/home/runner/work/vcpkg-port-node/vcpkg-port-node/test/build/linux` （**67 字符**），
叠完 **121 字符** ⇒ EINVAL。第二条是连带的（socket 没建出来 → `cpSync` 报 ENOENT）。

**旁证**：上游 `tools/test.py` 的 `--temp-dir` 默认**不设**（它自己用系统临时目录），
所以 node 官方 CI 永远不会踩到这个 —— 是**我们**为了分片隔离自己加进去的。

**修法**：临时根改以**系统临时目录**为基（`TMPDIR` → UNIX 上 `/tmp` → `TEMP`/`TMP` → 构建目录兜底），
仍按用例名分子目录（隔离性不变）；新增红线"临时根 > 64 字符就 FATAL"，并留 `NODE_PORT_TEST_TMPBASE` 覆盖开关。
本机验证：默认解析出 `C:/Users/hz/AppData/Local/Temp/node-suite-tmp`（47）；
`-DNODE_PORT_TEST_TMPBASE=C:/t` → `C:/t/node-suite-tmp`；给 74 字符的 base → **FATAL 并打印处置办法**。
