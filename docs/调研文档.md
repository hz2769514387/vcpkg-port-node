## 0. 结论速览（TL;DR）

1. **参考实现可用但有强前置依赖**：`C:\work\git\fe\cmake\ports\node` 能把 node v24.21.0 整棵树（含 V8、v8 third_party、vendored 五库）编成可链接的 `node::node`，但它**不是自包含的** —— 它依赖 fe 仓库的 overlay triplet（`x64-windows-static-clang` 等）、toolchain 文件（clang-cl.cmake）、以及构建期变量 `FE_CLANG_RT_BUILTINS`，还大量使用了 fe 专有的变量名（`FE_V8_*` / `NODE_ROOT` / `FE_V8_ROOT`）。要独立成 port，这些都得一并迁入本仓库。
2. **vcpkg 官方没有 `node` 库 port**（只有构建工具 `vcpkg-tool-nodejs` 与头文件 `node-api-headers` / `node-addon-api`），所以 `node` 这个名字目前可用，但上游评审时可能要求改名或补充说明。
3. **CI 的最大风险不是"怎么装 vcpkg"，而是 runner 的资源**：GitHub 托管的标准 runner 只有 **4 vCPU / 16 GB 内存 / 14 GB 可用磁盘 / 单 job 6 小时上限**（`macos-latest` 更只有 **3 vCPU(M1) / 7 GB**）。从源码构建 V8 + node + 16 个官方依赖，磁盘与时长都可能爆掉。已按 D1 决策处理（见 §0.5 与 §4.5）。
4. **指定版本的 vcpkg 可以稳定安装**：`2026.07.29` 这个 GitHub Release **没有二进制附件**，需要用 `https://github.com/microsoft/vcpkg/archive/refs/tags/2026.07.29.zip` 源码包 + `bootstrap-vcpkg` 自举；这与用户本地的 `vcpkg-2026.07.29.zip`（顶层目录 `vcpkg-2026.07.29/`）完全对得上。

## 0.5 已确认决策（2026-10-10）

| # | 议题 | 决策 |
| --- | --- | --- |
| D1 | CI 资源 | **资源是头号问题，磁盘与内存都要治**。允许用脚本清理空间、边编译边删、以及"非标准化配置防止落盘"等极端手段（详见 §4.5）。 |
| D2 | CI 平台 | 三个平台**都要**：`x64-linux`、`x64-windows`、`arm64-osx`。 |
| D3 | Windows 编译器 / CRT | **port 自身对齐 vcpkg 默认口径**（MSVC + 动态 CRT，即 `x64-windows`），以便未来推上游；同时**把 clang-cl + 静态 CRT 作为「推荐给使用者的用法」**输出（文档 + 示例 triplet）。 |
| D4 | 去 fe 化 | **授权**把参考实现按正式 port 方式重构迁入本仓库（重命名 `FE_V8_*` 等变量、迁 triplet/toolchain、改目录布局）。 |

> 由此产生的新工作项（相对参考实现的增量）：
> - port 必须**编译器无关**：既能在 MSVC 下编，也能在 clang-cl 下编（`FE_CLANG_RT_BUILTINS` 这类硬编码必须改成"有则用、无则跳过"）；
> - `CMAKE_MSVC_RUNTIME_LIBRARY` 不能硬编码静态 CRT，要跟随 triplet 的 `VCPKG_CRT_LINKAGE`；
> - 需同时维护**两套 Windows 口径**：内置默认 triplet（MSVC/动态 CRT）+ 随 port 发布的 clang-cl/静态 CRT triplet；
> - `arm64-osx` 需要补 gyp2vcpkg 的 macOS 变量环境（当前只有 win / linux 两份）。

## 1. 背景与目标

- **本仓库目标**：做一个名为 `node` 的 vcpkg 自定义 port，使用者通过 `overlay-ports` 引用，即可在自己的 C++ 程序里 `find_package(node)` + 链接 `node::node`，从而在自己的进程里嵌入 Node.js（libnode + V8）能力。
- **推进原则**（来自用户）：
  - 一开始就按**正式 port** 的方式设计，为将来推送进 vcpkg 官方仓库做准备；
  - 用 **GitHub Actions** 在 CI runner 上跑测试；
  - CI 上安装**指定的 vcpkg 版本 2026.07.29**；
  - AI 只做本地 git 操作，远程 push/pull 由用户完成。

## 2. 参考实现调研：`C:\work\git\fe\cmake\ports\node`

### 2.1 目录职责

| 路径 | 职责 |
| --- | --- |
| `portfile.cmake` | 下载 → 解压 → 拷工程 → configure/build/install → 收尾，共 6 步 |
| `vcpkg.json` | port 清单：`node` 24.21.0，声明 16 个官方依赖 |
| `usage` | 面向消费者的使用说明（装进 `share/node/usage`） |
| `gyp2vcpkg/` | **核心工具**：把 node 自带的 gyp 工程翻译成 CMake 片段（Python，三步管线） |
| `project/` | **构建工程**：真正把整棵树编成静态库的 CMake 工程（含 `generated/*.cmake`） |

### 2.2 portfile 的 6 步流程

见 [portfile.cmake](file:///C:/work/git/fe/cmake/ports/node/portfile.cmake)：

1. `vcpkg_download_distfile` 下载 `node-v24.21.0.tar.gz`（带 SHA512，本地 downloads 有同文件即离线复用）；
2. `vcpkg_extract_source_archive` 解压并剥掉顶层 `node-v24.21.0/`；
3. `vcpkg_find_acquire_program(PYTHON3)` 取**构建期** python（不依赖系统 python）；
4. 把 `project/` 与 `gyp2vcpkg/` **拷进源码树**（构建工程从源码树读 node 源码）；
5. `vcpkg_cmake_configure`（传 `-DNODE_ROOT` 与 `-DPython3_EXECUTABLE`）+ `vcpkg_cmake_build` + `vcpkg_cmake_install`；
6. 安装 `usage`、`vcpkg_install_copyright`。

### 2.3 gyp2vcpkg：三步管线

见 [README.md](file:///C:/work/git/fe/cmake/ports/node/gyp2vcpkg/README.md)。设计要点是**不自写 gyp 解析器**，而是调用 node 树自带的 gyp（gyp-next），用一个自定义 generator 把 gyp 跑完 14 步后的 `target_dicts` dump 出来：

```
resolve → gyp_resolved.json      用 node 自带 gyp 解析 .gyp
collect → compile_config_*.json  收成编译配置数据集（路径归一）
generate → generated/<目标>.cmake 只 set() 变量的 CMake 片段
```

它刻意**不认识调用方**：变量名（`FE_V8_*` / `NODE_ROOT` 等）全部由调用方的 `config.json` 配置。产物 `generated/*.cmake` **入库**，只在指纹对不上时重新生成。

### 2.4 project/ 构建工程

| 文件 | 职责 |
| --- | --- |
| `project/CMakeLists.txt` | 顶层：设 C++20、静态 CRT、Windows 宏，`add_subdirectory(config/v8/tools/vendored/node)`，最后**手写消费配置**并安装 |
| `project/consume.cmake` | gyp2vcpkg 的**消费层**：`fe_add_v8_target`（清单变量→CMake 目标）、`fe_add_v8_action`（代码生成动作→`add_custom_command`）、`fe_drop_bundled_include`（摘掉 node 自带第三方副本的 include，统一用 vcpkg 那份） |
| `project/FeTargetPatch.cmake` | **没有 gyp 清单**的自有目标（vendored 五库、node_js2c 等）的编译选项补齐 |
| `project/generated/*.cmake` | 46 个由 gyp2vcpkg 生成的目标清单 + 13 个动作清单 |
| `project/config/seed_gypi.py` | 变量环境注入 |

### 2.5 安装与消费配置

- 装出 **20 个静态库**（`node_base`/`node_main`/`v8_*`/`simdutf`/`highway`/`abseil`/`ncrypto`/…）；
- 装头：node 的 `src/*.h` → `include/node/`，V8 公开头 → `include/`；
- **手写** `node-config.cmake`（不用 `install(EXPORT)`，原因：gyp 的 `none` 目标在 CMake 里是 INTERFACE 库、其 `INTERFACE_SOURCES` 指向构建树源码，导出给消费者等于让消费者去编这些源）。配置里 `find_dependency` 14 个第三方、定义 imported 目标、按平台接链接（Linux 用 `$<LINK_GROUP:RESCAN,...>` 解静态库环，Windows 追加 `Dbghelp/Psapi/Winmm/...` 系统库）；
- 额外装 Windows 平台兼容性清单 `node.exe.extra.manifest`（缺失会导致进程启动退出码 216）。

### 2.6 依赖清单（16 个官方 port）

`libuv`、`llhttp`、`zlib`、`brotli`、`zstd`、`ada-url`、`ada-idna`、`openssl`、`nghttp2`、`c-ares`、`sqlite3`（带 dbstat/fts3/fts5/geopoly/math/percentile/rtree/session）、`simdjson`、`icu`、`ngtcp2`、`hdr-histogram`。消费方经**传递依赖**拿到，自身的 vcpkg.json 只需依赖本 port。

### 2.7 参考实现的「隐含前置条件」——独立成 port 必须处理

这是调研发现的**最关键的落差**。参考实现假设自己活在 fe 仓库里：

| 前置条件 | 位置 | 独立成 port 的处理 |
| --- | --- | --- |
| overlay triplet `x64-windows-static-clang` / `x64-linux-gcc` / `arm64-osx-clang` 等 | fe `cmake/triplets/` | 必须迁进本仓库（或改用 vcpkg 内置 triplet） |
| toolchain `clang-cl.cmake` / `msvc-command-line-env.cmake` / `clang-posix.cmake` | fe `cmake/toolchains/` | 同上 |
| 构建期变量 `FE_CLANG_RT_BUILTINS`（clang 的 compiler-rt 内建库） | `project/CMakeLists.txt`（WIN32 下缺失即 `FATAL_ERROR`） | 需在 port 内自行定位，或去掉 clang 依赖 |
| 变量名 `FE_V8_*` / `NODE_ROOT` / `FE_V8_ROOT` / `G2V_*` | `gyp2vcpkg/config.json` + `project/generated/*` | 与"正式 port 无关"的名字，建议重命名为 `NODE_PORT_*` 之类 |
| 静态 CRT（`CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`） | `project/CMakeLists.txt` | 与 vcpkg 默认 triplet（`x64-windows` 用动态 CRT）**冲突**，必须配自定义 triplet |
| Windows 用 **clang-cl** | 注释与 toolchain | vcpkg 上游 CI 用 **MSVC**；是否改回 MSVC 是决策点 |
| `icu_gyp_path` 指向自备的 `icu-vcpkg.gyp` | `gyp2vcpkg/config.json` | 需一并迁入 |

## 3. 「正式 vcpkg port」的要求

### 3.1 必备文件

```
ports/node/
  portfile.cmake      # 构建脚本
  vcpkg.json          # 清单（name/version/license/dependencies/supports）
  usage               # 可选：使用说明，装进 share/<port>/usage
  # 许可证由 portfile 里 vcpkg_install_copyright 安装
```

### 3.2 vcpkg.json 规范要点

- `license` 必须是 **SPDX 标识**（node 是 `MIT`，当前写法正确）；
- `version` / `version-semver` / `version-date` + `port-version`（同一上游版本改 port 时 `port-version` 递增）；
- `supports` 声明支持的三元组表达式（上游会检查）；
- `dependencies` 只写**运行/链接所需**，构建工具用 `host` 依赖标示（如 `vcpkg-cmake`、`vcpkg-cmake-config` 应为 `"host": true`）；
- 有可选能力时用 `features`。

### 3.3 版本数据库 `versions/`

正式 port（注册表 / 上游 PR）需要 `versions/n-/node.json` 记录版本与 git-tree。overlay-port 单独使用时**不强制**，但既然目标是上游，建议一开始就建。

### 3.4 portfile 规范细节

- 用官方 helper：`vcpkg_from_github` / `vcpkg_download_distfile`、`vcpkg_cmake_configure`、`vcpkg_cmake_install`、`vcpkg_cmake_config_fixup`、`vcpkg_fixup_pkgconfig`、`vcpkg_copy_pdbs`、`vcpkg_install_copyright`；
- **不允许硬编码绝对路径 / 机器专有路径**；
- 正确处理 **static / dynamic 两种 triplet**（`VCPKG_LIBRARY_LINKAGE`）；
- CMake config 包要放到 `share/<port>/` 且 `find_package(node CONFIG)` 可用；
- Windows 静态库需 `vcpkg_copy_pdbs`；
- 尽量**减少构建期对外部程序的依赖**（当前依赖 vcpkg 的 python3，属合规）。

### 3.5 上游 PR 的额外门槛（供参考）

- vcpkg 官方 CI 会跑 `x64-windows` / `x64-linux` / `arm64-osx` 等；
- 对**构建时长与产物体积**有隐性容忍度；node+V8 属于「超大 port」，评审可能要求拆分或说明理由；
- port 名唯一性。

### 3.6 命名

- vcpkg 现有 `vcpkg-tool-nodejs`（**构建工具**，非库）、`node-api-headers`、`node-addon-api`；
- **没有**提供 libnode 的 `node` port（本地 vcpkg 2026.07.29 的 `ports/node` 不存在，已核实）；
- 结论：`node` 名字可用；上游是否接受叫 `node`（而非 `libnode` / `nodejs`）需在 PR 时确认。overlay 使用不受此限。

### 3.7 我们需要收敛的「偏离项」清单

1. 变量名去 fe 化（`FE_V8_*` → 中性名）；
2. triplet / toolchain 自包含；
3. 静态 CRT 硬编码 → 跟随 triplet 的 `VCPKG_CRT_LINKAGE`（默认口径动态 CRT）；
4. Windows 编译器硬编码 clang-cl → 改为**编译器无关**（MSVC 能编，clang-cl 也能编）；
5. `FE_CLANG_RT_BUILTINS` 硬依赖 → 改为"有则用、无则跳过"；
6. 手写 `node-config.cmake` 是否有更"标准"的做法（保留亦可，但需注释充分）；
7. 补 gyp2vcpkg 的 macOS 变量环境（服务 `arm64-osx`）；
8. 依赖声明里 `vcpkg-cmake` / `vcpkg-cmake-config` 应标 `"host": true`；补 `supports` 字段。

## 4. GitHub Actions CI 设计

### 4.1 runner 环境调研（核实来源见 §7）

| 项 | `ubuntu-latest`（24.04 x64） | `windows-latest`（Server 2025 x64） | `macos-latest`（macOS 26 **arm64**） |
| --- | --- | --- | --- |
| CPU / 内存 / 磁盘 | 4 vCPU / 16 GB / 14 GB SSD | 4 vCPU / 16 GB / 14 GB SSD | **3 vCPU（M1） / 7 GB / 14 GB SSD** |
| 单 job 上限 | 6 小时 | 6 小时 | 6 小时 |
| 编译器 | gcc、clang（多版本） | MSVC（VS 2026）+ **LLVM 20.1.8**（含 clang-cl） | Apple clang（Xcode） |
| CMake | 预装 | **4.4.0** | 预装 |
| 预装 vcpkg | — | **`C:\vcpkg`**（`VCPKG_INSTALLATION_ROOT`，非 2026.07.29） | — |
| 其它 | — | VS 2026 已含 `VC.Llvm.Clang`；Python 3.12.10 | — |

> 磁盘口径说明：文档写「14 GB」，指的是**可用**空间；底层卷实际约 72 GB，全新 runner 实测空闲约 20+ GB，会随下载/编译迅速消耗。三者里 **macOS arm64 只有 3 核 7 GB 内存**，是资源最紧张的一档。

**三个必须注意的点：**

1. `windows-latest` 上的 VS 已从 2022 迁移到 **2026**（2026-06 完成）。toolchain/setup 脚本不要写死 VS 2022 路径。
2. runner 上**预装了另一个版本的 vcpkg**（`C:\vcpkg`），它会通过 `VCPKG_INSTALLATION_ROOT` 生效。我们要用 **2026.07.29**，必须显式 `VCPKG_ROOT` 指向自己装的目录，并避免被预装版干扰（必要时先 `Remove-Item C:\vcpkg` 腾空间）。
3. `macos-latest` 是 **arm64**（`macos-14/15/26`），对应 triplet `arm64-osx`；没有 Intel 需求时不要用 `macos-*-intel`。

### 4.2 在 CI 上安装指定版本 vcpkg（2026.07.29）

核实结果：`2026.07.29` 的 GitHub Release **`assets` 为空**，即**没有官方二进制包**；本地那份 `C:\work\vcpkg-2026.07.29.zip` 顶层目录为 `vcpkg-2026.07.29/`，正是 GitHub 自动源码包（zipball）的形态。

因此 CI 上的安装方式（Windows / Linux 通用思路）：

```yaml
- name: Install vcpkg 2026.07.29
  shell: bash
  run: |
    curl -L -o vcpkg.tar.gz \
      https://github.com/microsoft/vcpkg/archive/refs/tags/2026.07.29.tar.gz
    mkdir -p "$RUNNER_TEMP/vcpkg-src"
    tar -xzf vcpkg.tar.gz -C "$RUNNER_TEMP/vcpkg-src" --strip-components=1
    "$RUNNER_TEMP/vcpkg-src/bootstrap-vcpkg.sh" -disableMetrics
    echo "VCPKG_ROOT=$RUNNER_TEMP/vcpkg-src" >> "$GITHUB_ENV"
    echo "$RUNNER_TEMP/vcpkg-src" >> "$GITHUB_PATH"
```

- `bootstrap-vcpkg` 会按 `scripts/vcpkg-tool-metadata.txt` 里的 `VCPKG_TOOL_RELEASE_TAG=2026-07-27` 下载对应 vcpkg-tool（与本地一致）；
- Windows 上用 `bootstrap-vcpkg.bat`，`shell: pwsh`；
- 也可把源码包**预先缓存**（`actions/cache`）以省去每次下载自举。

### 4.3 工作流草案（骨架，非最终）

```yaml
name: ci
on: [push, pull_request]
jobs:
  build:
    strategy:
      fail-fast: false
      matrix:
        include:
          - os: ubuntu-latest
            triplet: x64-linux
          - os: windows-latest
            triplet: x64-windows          # 对齐 vcpkg 默认：MSVC + 动态 CRT
          - os: macos-latest             # arm64
            triplet: arm64-osx
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - name: Free disk space                # 见 §4.5
      - name: Install vcpkg 2026.07.29       # 见 §4.2
      - name: Install node port (overlay)
        run: vcpkg install node:${{ matrix.triplet }} --overlay-ports=ports --clean-after-build
      - name: Consume smoke test
        run: cmake -S test -B build -DCMAKE_TOOLCHAIN_FILE=$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake ...
```

### 4.4 CI 要跑什么（建议分层）

| 层 | 内容 | 成本 | 是否受磁盘限制 |
| --- | --- | --- | --- |
| L1 静态校验 | `vcpkg x-ci-verify-versions`、YAML/JSON 合规、`versions/` 数据库一致性 | 低 | 否 |
| L2 依赖 + port 构建 | `vcpkg install node --overlay-ports=ports` | **极高** | **是** |
| L3 消费冒烟 | `test/` 里一个最小 C++ 程序，`find_package(node)` + 链接 `node::node`，跑一段 `node::Start` 或嵌入脚本 | 中 | 是（依赖 L2 产物） |

### 4.5 关键风险与对策：磁盘 + 内存（**头号问题**，对应 D1）

**问题量级**：标准 runner 只有 14 GB 可用 SSD（底层约 72 GB、实测新机空闲 20+ GB），内存 16 GB（macOS arm64 仅 **7 GB**）。而本 port 要从源码构建：

- node 源码树 + V8 源码树（含 third_party）+ 16 个官方依赖（icu / openssl / sqlite3 / nghttp2 / nghttp3 / …）；
- V8 自身是出了名的「大目标多 + 单个 TU 吃内存 + 最终链接吃内存」；
- 若 triplet 同时构建 debug + release（vcpkg 默认行为），磁盘再翻倍。

因此 CI 必须**主动、分层地控制磁盘与内存**，不能指望默认配置跑通。

#### 4.5.1 磁盘：清理 + 边编译边删 + 不落盘

| 手段 | 具体做法 | 平台 |
| --- | --- | --- |
| 预清理 runner 预装物 | 删 `/usr/share/dotnet`、`/usr/local/lib/android`、`/opt/ghc`、`/usr/local/share/boost`、`/opt/hostedtoolcache`（部分）等；或直接用社区 action `jlumbroso/free-disk-space` | ubuntu |
| 预清理（Windows） | 删 `C:\Android`、`C:\hostedtoolcache`、`C:\Program Files\Android`，以及**预装的 `C:\vcpkg`** | windows |
| 预清理（macOS） | 删 Xcode 的旧 SDK/模拟器、`/Library/Developer/CoreSimulator`、`~/Library/Caches` | macos |
| **边编译边删** | `vcpkg install ... --clean-after-build`（= `--clean-buildtrees-after-build` + `--clean-downloads-after-build` + `--clean-packages-after-build`，**每个包编完立即清**，是控制峰值的关键） | 全平台 |
| 只编 Release | 设 `VCPKG_BUILD_TYPE=release`（默认 triplet 会编 debug+release，等于双倍） | 全平台 |
| 不生成调试信息 | 关掉 PDB：MSVC 用 `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT`（避免 `/Zi` 落 .pdb）；Linux 链接后 `strip -g`；不调 `vcpkg_copy_pdbs` | 全平台 |
| vcpkg 目录不落 `.git` | 用源码 tar/zip 包 + `bootstrap`（本就是 `refs/tags/2026.07.29.tar.gz`），不要 `git clone` | 全平台 |
| 下载目录另置 | `VCPKG_DOWNLOADS` 指到 `$RUNNER_TEMP`，用完即弃；或 `--clean-downloads-after-build` | 全平台 |
| 后台守护式清理 | 极端手段：后台循环 `rm -rf buildtrees/*/`（对已经编完的包），进一步压低峰值 | 全平台（谨慎） |
| 二进制缓存 | `VCPKG_BINARY_SOURCES=filesystem,<path>,readwrite` + `actions/cache`，key 带上 vcpkg 版本 + triplet + portfile 哈希 | 全平台（注意仓库 cache 上限约 10 GB、有淘汰） |

> 注意 `--clean-after-build` 清的是 `buildtrees/`、`downloads/`、`packages/`，**不会**清最终安装树（`installed/` / `vcpkg_installed/`），所以 L3 消费冒烟仍能拿到产物。

#### 4.5.2 内存：并发度必须收着用

- 用环境变量 **`VCPKG_MAX_CONCURRENCY`** 限制 vcpkg 传给构建系统的并行度：
  - `ubuntu-latest`（4C/16G）：建议 `3`（V8 个别 TU 单编译吃内存大，`-j4` 有 OOM 风险）；
  - `windows-latest`（4C/16G）：建议 `2~3`；
  - `macos-latest`（**3C/7G**）：建议 `2`，甚至 `1` 换稳定。
- 链接阶段（V8 静态库合并链接）是内存尖峰，必要时给链接单独降并发；Windows 上注意 `link.exe` 单进程也吃几个 GB。
- 不要开 LTO、不要开 `/MP` 与 vcpkg 并发叠加（两者相乘会放大内存）。
- 4.5.1 的"不落盘"同日也降内存压力（少写盘 → 少脏页回写），二者同源。

#### 4.5.3 时长与失败兜底

- 编译以**小时**计，逼近 6 小时上限；并发度又不能开高（内存受限），二者互相拉扯。
- 建议顺序：先 **L1 静态校验**（秒级、必过）→ 再 L2 全量构建；L2 失败不阻塞 L1 的结论。
- 若标准 runner 仍跑不下，兜底顺序：
  1. 加二进制缓存 + ccache，让第二次起命中缓存；
  2. 缩小 CI 目标（先保证 `x64-linux` 跑通，windows/macos 用缓存/降级）；
  3. 改用 **Larger runner**（磁盘更大、内存更多）或**自托管 runner**。

> 明确记录：**"标准托管 runner + 全量源码构建 V8/node" 是高风险组合**；本方案的立场是「先用 §4.5.1/4.5.2 的极端省资源手段硬试，试不通再上 Larger/自托管」，并把这作为 CI 落地时的第一优先验证项。

### 8.2 已实测的结论（本机，非 CI）

1. **只配置不编译**：用 clang-cl + 静态 CRT（x64-windows-static-clang）+ fe 现成的 `vcpkg_installed` 做 cmake configure —— **通过**（识别 Clang 19.1.5、找到 ICU/OpenSSL/ZLIB、59 份生成片段全部载入）。证明去 fe 化重构在 CMake 层是自洽的。
2. **vcpkg CLI 识别**：`vcpkg install node:x64-windows-static-clang --overlay-ports=ports --overlay-triplets=triplets --dry-run` —— **通过**，解析出 `node:x64-windows-static-clang@24.21.0` + 16 个依赖 + 4 个 host 工具。
3. **踩到的坑（已修）**：本版 vcpkg 在**加载 triplet 之前**处理 `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`，所以裸 cmake + overlay triplet 时写在 triplet 里的 chainload 不生效（编译器识别为 unknown）；vcpkg CLI 配置 port 时会把它作为命令行 cache 变量传入，故真实流程可用 —— 保持 vcpkg 标准写法即可。
