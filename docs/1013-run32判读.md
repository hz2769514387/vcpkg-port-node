## 2. 根因（V8 自己说的）

上一轮加的 0018 让退出码第一次落盘 ⇒ `0xC0000409`。本机再用"打过 0018 的 test.py 跑全量套件
（`-j 4`，叠加两个压测任务）"复现到同一码，拿到了真正的现场：

```
=== release test-process-execve-socket ===
[low_level_alloc.cc : 554] RAW: Check new_pages != nullptr failed: VirtualAlloc failed
--- exit code: 3221226505 (0xC0000409) ---
```

* 那个文件是 **V8 自带的 abseil** 的 `absl/base/internal/low_level_alloc.cc`（不是 V8 自己的分配器）；
* 失败点：`VirtualAlloc(nullptr, new_pages_size, MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE)`
  ⇒ **提交量（commit charge）耗尽**，不是内存踩踏、不是栈损坏。

这一条把所有反常全解释通了：

| 现象 | 解释 |
|---|---|
| 只有 Windows 出这个码 | Linux/macOS 默认 overcommit，提交失败几乎不发生；Windows 的提交量是**硬限制**（RAM + 页面对换文件） |
| 每轮换一批用例 | 4 个并发 node 进程（V8 老生代上限按机器内存自动放大到 GB 级）叠加摸到上限，**谁那一刻在分配谁就崩** |
| macOS 从来没出过 | 它本来就跑 `-j 2` |
| 全是 http/net/子进程类用例 | 它们本身吃的内存最多（多连接 + 巨量头 + 反复 spawn） |

**判读教训（补进方法论）**：上游 `HasCrashed()` 的判定是
`0x80000000 & code and not (0x3FFFFF00 & code)` —— 0xC0000409 恰好落在被排除的那一档
（因为它通常是"故意 abort"的码），所以日志里既没有 `--- CRASHED ---` 也没有任何输出，
只有**退出码**能定性。上一轮我正因为缺退出码，把它误判成抖动。

## 3. 已做的缓解（提交 `2f1ad65`）

Windows 两档的套件并发压到 `-j 2`（与 macOS 同口径）：峰值提交量大致减半（约 5~9 GB，
16 GB runner 有余量）。落地位置与理由：

* `test/CMakePresets.json` 的两个 windows preset 加 `"NODE_PORT_TEST_JOBS": "2"`
  （子预设覆盖 base 的 `$env{VCPKG_MAX_CONCURRENCY}`；已用最小预设工程验证继承语义，
  并验证命令行 `-D` 仍能进一步覆盖 —— 想跑 4 的人有出口）；
* 理由、crash 码、源码行、代价（套件墙钟约翻倍到 15 分钟量级）写在
  `test/tests/ctest_node_suite.cmake` 里该变量旁边。

**这不是藏失败**：用例一条不少、一条不跳，只降并行度。
