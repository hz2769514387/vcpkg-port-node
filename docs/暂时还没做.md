## 2. arm64 实测（含交叉构建的 host toolset）★ 优先级已提高

- **现状**：arm64 各口径都进了 CI 矩阵，但都是 `allow_failure: true`（Tier 2）。
- **本轮已做**：补丁里写死的 `--target=x86_64-pc-windows-msvc` 与
  `clang_rt.builtins-x86_64` 已参数化 —— 现在由 port 按 `VCPKG_TARGET_ARCHITECTURE`
  经环境变量 `NODE_PORT_CLANG_TARGET` / `NODE_PORT_CLANG_RT_BUILTINS_NAME` 交接，
  默认值保持 x86_64（不设变量时行为与之前一致）。
- **★ 新识别到的结构性障碍**：arm64-windows 是在 x64 宿主上**交叉编译**，而 node 的
  构建期工具（`mksnapshot` / `torque` / `node_js2c` 等）要在构建机上**跑**，必须是宿主
  编译（x64）才能执行。现在 `configure.py` 的 `make_global_settings` 只给了
  `CC`/`CXX` 一套（没有区分 host / target toolset），于是 host 工具会被编成 arm64 →
  在 x64 构建机上**跑不起来**。这不是补丁能解决的：要么给 gyp 单独的 host toolset，
  要么在有 arm64 宿主（或能跑 arm64 二进制的仿真环境）上原生构建。
  **升级 Tier 1 之前必须先解决这个。**
- **★ run #23 又给这条加了一个新的暴露面（2026-10-12）**：这次挂在 **node port 的构建期**，
  不是消费端 —— `gen-regexp-special-case.exe`（v8 的构建期小工具）链接失败：
  `LNK2019: unresolved external symbol "icu_78::UnicodeSet::..."` 一大片，外加
  `LNK4272: library machine type 'ARM64' conflicts with target machine type 'x64'`。
  即**宿主小工具（x64）拉到了目标架构（arm64）的 vcpkg ICU 库**。
  与我们为 arm64 交叉编译加的 `ENV{CC}/ENV{CXX}`（triplet 里那两条）直接相关：
  它让 autotools 端口编出 arm64，而 v8 的构建期工具本该是宿主编译。
  ⇒ 与上面那条是同一个根因（缺 host/target toolset 分离），只是换了个位置暴露。
- **试过又撤掉的修法**：给该 triplet 加 `-DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY`（交叉编译的常规做法，能过 "跑不了 arm64 exe" 那一关），但它有更坏的副作用 —— try_compile 不再链接，于是**库存在性检查全部误报成功**，实测 brotli 因此加了 `-lm` 而挂
  （`lld-link: could not open 'm.lib'`）。撤掉，宁可挂在"一眼能懂"的地方。
- 状态：⬜ 未做（不阻塞发版；但已从"理论可过"降级为"有已知障碍"）

## 5b-1. 链接组的表达方式（顺带在同一次改动里修掉）★ 2026-10-12

- 症状：run #23 的 **x64-linux 硬门**挂掉，`unit_node_coexist` 链接期 174 条 `undefined reference`，
  其中 **173 条是 nghttp2**。
- 根因不是"少链了一个库"，而是**用错了工具**：port 把
  `"-Wl,--start-group" … "-Wl,--end-group"` 当普通链接项塞进 `INTERFACE_LINK_LIBRARIES`。
  CMake 官方文档对 `$<LINK_LIBRARY>` 明确写着它**不保证列表保持分组**，要做分组得用
  `LINK_GROUP` 生成器表达式；而且 CMake 会对链接项**去重** ——
  消费端（本仓库 test/unit）只要重复列一个 nghttp2，就会把**组内那份**删掉、只留组外那份，
  而组外那份位于 node 静态库之前，单趟扫描早已扫过 ⇒ 组内解析不了。
- 修法：三分支，每条都有依据 ——
  * Windows：平铺（link.exe 自己反复扫描，实测全绿）；
  * Apple：平铺（**上游 `LINK_COMMANDS_MAC` 就是平铺**；ld64 没有 rescan 构造）；
  * 其余 GNU 系：`target_link_libraries(node::node INTERFACE "$<LINK_GROUP:RESCAN,…>")`
    （CMake 官方机制，等价于 --start-group，且**去重不会把它拆散**）。
    RESCAN 的平台支持是查 `cmake-4.4.0/Modules/Platform/*.cmake` 得到的硬事实：
    只有 GNU/Linux/FreeBSD/NetBSD/Haiku/SunOS/Windows-GNU 定义，**Apple 与 MSVC 都没有**。
    因此生成配置里前置了 `CMAKE_VERSION VERSION_LESS 3.24` 的 FATAL_ERROR，并写进 `usage`。
- **★ 又一处上游误读被纠正（与 §5g 的 abseil 同类）**：portfile 原注释称
  "make.py 的 `LINK_COMMANDS_MAC`（209 行起）用的是同一条 `--start-group` 命令 ⇒ ld64 也认"。
  查上游原文：`LINK_COMMANDS_MAC` 是 `$(LINK) … -o "$@" $(LD_INPUTS) $(LIBS)`，**不带**这组开关；
  带它的是**通用（Linux/BSD）命令表**的 260 行。arm64-osx 的
  `ld: unknown options: --start-group --end-group`（run #23 实测）就是抄错注释的代价。
- 同时修掉消费端自己的重复链接（`test/unit/CMakeLists.txt` 里 `node::nghttp2` 与

## 5h. openssl：node 自带那份 → 换成 vcpkg 那份，行为是否一致 ★ 用户提出

- **问**：node 给 openssl 打过补丁吗？现在改成用 vcpkg 的 openssl，会不会行为不一致？
- **答：node 不打 openssl 的源码补丁** —— `deps/openssl/` 下**没有** `patches/` 目录。
  它的定制只有三处，且**共享模式下两处根本用不上**：
  1. `deps/openssl/config/archs/<arch>/{asm,asm_avx2,no-asm}/` 里按架构预生成的头
     （`configuration.h` / `bn_conf.h` / `dso_conf.h` …）—— 只服务于"编自带那份"；
  2. 编自带那份时带 `OPENSSL_API_COMPAT=0x10100001L`（`openssl.gyp`）—— 共享模式下
     node 自己的代码改按 vcpkg 那份头的默认级别（3.6）编，实测能编过；
  3. **`nodejs-openssl.cnf`**：编进二进制后由 `src/node.cc` 用
     `NODE_OPENSSL_CONF_NAME(=nodejs_conf)` **显式**喂给 OpenSSL 去激活 provider ——
     这条路跟用哪份 openssl 无关，是我们这条链路的保险。
- **所以真正会变的只有一件事：vcpkg 那份编了哪些东西。** 逐项比对两边的
  `configuration.h`（`OPENSSL_NO_*` 开关 + `OPENSSL_CONFIGURED_API`）结论是
  **没有能力回退**：
  | 差异 | 方向 | 影响 |
  | --- | --- | --- |
  | 版本 3.5.0 → 3.6.3 | vcpkg 更新 | 小版本前进 |
  | `ec_nistp_64_gcc_128` | vcpkg **多开**（node 那份没开） | 纯性能优化，更好 |
  | `apps` / `docs` / `acvp-tests` / `allocfail-tests` | vcpkg 关掉 | 与 node 的 JS 能力无关 |
  | `fips-post` / `fips-securitychecks` | vcpkg 关掉 | 两边 FIPS 都没开 |
  | `brotli` / `zlib` / `zstd` | vcpkg 关掉 | 只关 OpenSSL 自己的压缩；node 的 `node:zlib` 走它自己的 zlib（本工程就是 vcpkg 的 zlib），不经 openssl |
  | `lms` | vcpkg 关掉 | 3.6 新算法；node 24.21 面向 3.5，本来就没引用 |
  - 另：vcpkg 的 `no-autoload-config` 是**消费端可选**项，我们没开 ⇒ provider 自动加载行为不变。
- **但"比对过"只是文档结论，不是回归保护** ⇒ 新增 ctest 用例
  `coexist-openssl-surface`（`test/coexist/openssl_surface.js`）：真跑算法面
  （`getHashes/getCiphers/getCurves` 覆盖基线）+ 端到端功能（sha256 与 HMAC 已知向量、
  aes-256-gcm 往返、ed25519 签名验签、secp256k1 ECDH、pbkdf2、随机数、
  `tls.createSecureContext()`、TLS 1.3 套件）。**provider 没起来 / 算法被裁掉**
  会以红灯形式暴露，不再靠人记着。
- 状态：✅ 已回答 + 已加可执行用例（2026-10-12）

## 5i. Windows 下 node.exe 链接不到静态库（node.gyp 的 WHOLEARCHIVE 路径）★ 2026-10-12 修

- **症状**：`LINK : fatal error LNK1356: 找不到为延迟加载指定的库 lib/node_base.lib`。
- **根因**：`node.gyp` 里 Windows 那两条 `/WHOLEARCHIVE:<(PRODUCT_DIR)/lib/<...>` 是照
  **msvs 生成器**写的（msvs 把静态库放到 `$(OutDir)lib\`）。但 gyp 的 **ninja** 生成器在
  Windows 上 `type_in_output_root` 只有 `executable / loadable_module / shared_library`，
  `static_library` 走 `GypPathToUniqueOutput` ⇒ 落在 `obj/` 下（实测 `obj/node_base.lib`、
  `obj/tools/v8_gypfiles/v8_base_without_compiler.lib`，`lib/` 目录根本不存在）。
  同一文件里 Linux 那侧本来就写的是 `<(obj_dir)/...`，macOS 的 static_library 在 output root，
  **只有 Windows 这一条对不上**。
- **修法**：portfile 里（仅 Windows）把 `node.gyp` 的那两条替换成
  `<(obj_dir)/<(STATIC_LIB_PREFIX)node_base<(STATIC_LIB_SUFFIX)` 与
  `<(obj_dir)/tools/v8_gypfiles/<(STATIC_LIB_PREFIX)v8_base_without_compiler<(STATIC_LIB_SUFFIX)`。
  用 `vcpkg_replace_string` 而不是补丁：两处字符串各自唯一，替换不怕上游改行号。
- **★ 必须放在 `configure.py` 之前改**（第一版我放在后面，白跑 30 分钟）：
  改的是 gyp 的**输入**，而 ninja 文件是 configure.py 内部调 gyp 生成的；而且
  `out/Release/build.ninja` 里**完全没有 `node.gyp` 这个依赖**（gyp 这次没生成
  自更新规则），所以事后改 gyp 既不会触发重新生成、也不会被 ninja 察觉 ——
  替换确实生效了（node.gyp 里已经是新路径），链接照样失败。
- 状态：✅ 已修（2026-10-12，待本地 / CI 实测确认）

## 5m. `.cmd` 垫片必须 ASCII-only ★ 通用规则，2026-10-12

## R4. Debug / CRT 口径（**2026-10-14 用户拍板：路线 A + MD 也要支持**）

- **用户原话**："vcpkg 正统双份构建 + MD 也要支持：记住：用户绑架最小化原则。"
- **最终设计**：
  1. port 按 `VCPKG_BUILD_TYPE` 决定构建计划：未设（双份 triplet）⇒ Release + Debug
     都编，debug 库按 vcpkg 惯例进 `debug/lib`；设 `release` ⇒ 只编 Release；
     设 `debug` ⇒ **FATAL**（debug-only 会让 brotli 等上游 port 的
     `vcpkg_copy_tools` 布局直接 BUILD_FAILED，且 release 消费方无库可链；
     要 debug 请用不设 `VCPKG_BUILD_TYPE` 的双份 triplet）。
  2. CRT 跟随 `VCPKG_CRT_LINKAGE`：static ⇒ /MT(/MTd)；dynamic ⇒ /MD(/MDd)。
     实现：`VCPKG_CRT_LINKAGE=dynamic` 时给 configure.py 传
     `NODE_PORT_FORCE_DYNAMIC_CRT=1`（replace_string 改 configure.py 的
     `force_dynamic_crt` 赋值行使之生效），并 replace_string 改 common.gypi 的
     两处 `MSVC_runtimeType` 条件（加上 `force_dynamic_crt != 1`）——
     v8 侧 toolchain.gypi 本来就认 force_dynamic_crt（三处已核对）。
  3. 消费方体验：双份安装下 Debug/Release 都原生可用（/MTd 或 /MDd 与库一致），
     **不再需要** usage 里"Debug 也必须用 /MT"那条；release-only 安装 + Windows
     Debug 消费方 ⇒ 配置期 FATAL（清楚告知换双份 triplet），Linux/macOS 静默用
     release 库（无双 CRT 概念，vcpkg `-release` triplet 的既有行为）。
  4. 私有开关 `NODE_PORT_BUILD_TYPE` **删除**（vcpkg 里决定编哪份的就是
     `VCPKG_BUILD_TYPE`；CI debug 腿改用双份 triplet + 消费方 Debug）。
- **本机实测（2026-10-14，探针已删）**：
  * 干净 shell（无 cl.exe / INCLUDE / LIB / CC）+ 标准 triplet `x64-windows-static`：
    c-ares（CMake）与 openssl（**nmake**，最重依赖）都构建成功，且**双份**
    （rel+dbg 两个 buildtrees；安装布局 `debug/lib` 有 libcrypto/libssl，
    头文件在 release 侧 include/ 共享）⇒ 路线 A 的依赖侧无未解风险，
    brotli 的坑仅限于 debug-**only**。
  * vcpkg 官方双份 port 的模式：`if(NOT VCPKG_BUILD_TYPE)` 建 release、
    `if(NOT VCPKG_BUILD_TYPE OR VCPKG_BUILD_TYPE STREQUAL "debug")` 建 debug
    （ace / activemq-cpp / apr-util 同款）⇒ 双份模式下该变量为假值。
  * node 24.21.0 CRT 机制（buildtrees 里的源码树实核）：common.gypi 的
    `MSVC_runtimeType` 跟 `node_shared`；toolchain.gypi（v8）跟
    `force_dynamic_crt`；configure.py 仅在 `--shared` 时置 force_dynamic_crt=1。
    **gyp 的 -D 传不动**（config.gypi 经 gyp -I 引入、写死 0 赢）⇒ 用
    replace_string 改 configure.py 赋值行 + common.gypi 两处条件。实测：77 个
    编译单位 /MT → /MD。
- **★★ 第一次真编 debug 暴露的潜伏 bug（2026-10-14 本机全量构建，已修）**：
  1. **ICU 经 pkg-config 泄漏 release 库**：ICU 不走 `--shared-*`（node 24 没有
     `--shared-icu`），走 `--with-intl=system-icu` + pkg-config，而 PKG_CONFIG_PATH
     写死 release 侧 ⇒ debug 构建链 release 的 icuuc.lib（LNK2038：level 0 vs 2，
     MT_StaticRelease vs MTd_StaticDebug）。**修**：PKG_CONFIG_PATH 与 LIB 都按口径切。
     另注：vcpkg 的 PKGCONFIG 获取器给的是 **mingw64 pkgconf**（读得了 Windows 风格
     PKG_CONFIG_PATH；MSYS2 那份读不了，别换错二进制）。
  2. **历史真相**：旧 CI 的"debug 腿"**从未真正编过 debug node** —— 私有开关

     欠账 §1"debug 从未实测"的表述是**准确的**；路线 A 让构建口径进 triplet ⇒ 进
     ABI 哈希，debug 才第一次真编。

  由 MSVC cl.exe 编，链接期干净（CRT 一致、manifest 自动嵌入、compiler-rt 带上）。

  待做：① port 侧补 C++20 声明与 `/Zc:__cplusplus`（见 R9）后**再跑一遍全量**（改
  portfile ⇒ node 重编约 1.3h）；② Debug 消费端（`-DCMAKE_BUILD_TYPE=Debug`）本机验证。

## R9. Windows 消费端：三件"任何 CMake 工程都要做、port 替不掉"的事（2026-10-15 新增）

> 起因：R1 把 toolchain 内化之后，消费端第一次**不挂** chainload toolchain 就跑，
> 三个真因接连暴露。三条都不是本 port 的私货 —— 换成任何一个 `x64-windows-static`
> 的 port 都一样，但**必须写清楚**，否则下一次又要花一小时从报错反推。

1. **MSVC 命令行环境**：vcpkg 只给 **port 构建**摆环境（所以装依赖从来不需要它）；
   消费端的 cmake 跑在裸 shell 里就没有 `cl.exe` / `rc.exe` / `LIB` / `INCLUDE`，
   编译器探测挂在一个离真因极远的地方：
   `RC Pass 1: command "rc /fo … manifest.res … manifest.rc" failed … no such file or directory`。
   → 在 VS 开发者命令行里跑；CI 见 `platform.yml` 的 vcvarsall 包装
   （arm64 腿用 `x64_arm64`，因为是交叉编译）。
2. **`CMAKE_MSVC_RUNTIME_LIBRARY` 必须消费端自己给**：设 `/MT` 的那份脚本
   （`scripts/toolchains/windows.cmake`）**只作用于 port 构建** —— vcpkg 把它当
   chainload toolchain 传给 port 的 cmake，消费端的 cmake 根本不会加载它
   （本机实测：CMAKE_MSVC_RUNTIME_LIBRARY 不在消费端 CMakeCache 里）。
   ⇒ 默认值 `/MD`，与 node 的 `/MT` 在链接期喷一屏 LNK2038
   `mismatch detected for 'RuntimeLibrary': MT_StaticRelease 不匹配 MD_DynamicRelease`。
   → preset 里给 `MultiThreaded$<$<CONFIG:Debug>:Debug>`。
   ★ 重构时我把 test/CMakeLists.txt 里那条 `if(MSVC) set(CMAKE_MSVC_RUNTIME_LIBRARY …)`
   当成"双份构建后不再需要"删掉了 —— **错的**：它当时的作用正是补这一条（只是那时
   依赖 release-only，所以写死成不带 Debug genex）。已改回 preset，并带 Debug genex。
   待办：在导出配置里加一道**配置期闸门**（port 静态 CRT ∧ 消费端未设或设成 DLL ⇒
   FATAL 并给出确切修法），省掉一轮 CI。
3. **C++20 与 `/Zc:__cplusplus`**：`v8config.h` 直接 `#if __cplusplus <= 201703L → #error`；
   而 cl.exe 默认把 `__cplusplus` 报成 `199711L`（**即使开了 /std:c++20**），非要
   `/Zc:__cplusplus` 才报真值 ⇒ 消费端换 cl.exe 后第一个红就是
   `fatal error C1189: #error: "C++20 or later required."`。clang-cl 没这个毛病。
   → **由 port 在 `unofficial::node::node` 的 INTERFACE 上声明**
   （`INTERFACE_COMPILE_FEATURES cxx_std_20` + MSVC 非 Clang 时 `/Zc:__cplusplus`），
   消费端一行都不用写。
- 状态：🟡 1、2 已在 preset / CI 落地（本机验证过）；3 待写进 portfile（改 portfile
  ⇒ node 重编，排在 R4 的重跑里一起做）。

### 本机环境两条（**不是 port 的问题**，记在这里免得下次重复判读）
- 本机 `NODE_OPTIONS` 被注入 `--require=<WorkBuddy 的 node-language-shim>`，给每个
  node 进程塞 `__CODEBUDDY_*` 全局 ⇒ 官方套件的 "Unexpected global(s)" 断言必红，
  且它的 stderr 不是 UTF-8，driver 的 `open(errname, encoding='utf8')` 直接抛
  `UnicodeDecodeError: byte 0xb2`。**跑套件前 `set NODE_OPTIONS=`**（CI 是英文环境、
  没有这个注入，所以这条本机独有）。
- 从 Git Bash 起 `cmd` 会把 `TEMP=/tmp`（MSYS 路径）带进去 ⇒ node 的 `os.tmpdir()`
  拿到 `/tmp`，`cd` 在 cmd 下报中文错误。**bat 里显式 `set TEMP=`**。
  另：`.bat` 文件必须 **ASCII-only** —— cmd 按控制台代码页（本机 GBK）读，UTF-8 中文
  注释会把脚本解析搞坏（症状是 vcvars 没跑、报"系统找不到指定的路径"）。

## R5. 依赖策略（feasibility 调研新增，独立于 R1，用户定优先级）

> 立场：我们的目标不是"全量 vcpkg 化"（V8 树无 `--shared-v8` 是硬墙，Debian 的全 shared
> 也要吃 30+ 条测试 skip），而是"关键依赖行为对齐 + 差异入账"。

- **R5.1 libuv（🔴 有安全修复丢失）**：vcpkg 1.52.1 与 node vendored 1.52.1 **版本号同、
  源码不同** —— node 从 libuv main backport 了 4 处修复（`src/win/fs-event.c` 目录监视
  越界/短路径修复、`src/win/tcp.c` GetVersionEx 初始化、`src/unix/fs.c` 别名 UB 加固、
  `src/uv-common.c` 强转）。我们走 `--shared-libuv` ⇒ **这些修复全部丢失**，Windows 用户
  受影响最大。选项：① 接受 + 文档（Debian 接受系统 libuv，还因此吃过 io_uring CVE 的亏）；
  ② overlay `ports/libuv/` 带上 4 处 backport（补丁传播风险**极低**：libuv 在 vcpkg 有
  14 个依赖者，但补丁是纯 bugfix + ABI 不变 + `uv.h` 0 差异）；③ 回退内嵌（丢"依赖全走
  vcpkg"的卖点，且 node 自带 uv 与 v8 侧无冲突，单纯是构建变慢）。
  推荐 ②（符合用户"不惜在 port 目录给那个库打 patch"的授权）。
- **R5.2 zlib（🟡 性能）**：node 用 chromium fork（SIMD crc32/adler32 + cpu_features 探测），
  vcpkg 是 madler 官方版（无 SIMD）⇒ 压缩吞吐差异。**不能简单回退内嵌**：node 的 zlib 与
  v8 的 v8_zlib 已一并换成 vcpkg 那份（避免两份 zlib 符号相撞），回退一份就会撞。
  overlay chromium-zlib 风险**高**（248 个依赖者，行为性改变 ⇒ "选边站"）。
  推荐：接受 + README 量化 benchmark 后标注（§16 已有 URL/IDNA benchmark 欠账，可合并）。
- **R5.3 ada-url（🔴 版本 + 特性双缺口）**：vcpkg 3.4.4 vs node 4.0.0（1 个 major，URL 行为
  差异风险）+ 无 simdutf feature（本机复核成立，见 §5e 修订）。推荐 overlay
  `ports/ada-url/`：加 simdutf feature（参照 `ada-idna` portfile 的 `ADA_USE_SIMDUTF`
  处理，但依赖 vcpkg 的 simdutf port 而非 CPM）+ REF 固定 4.0.0。
- **R5.4 sqlite3（⚠️ 调研文档一处不成立）**：feasibility 称 vcpkg sqlite3 "rbu 全覆盖"——
  **本机复核不成立**：2026.07.29 的 sqlite3 features 里**没有 rbu**（只有 dbstat/fts*/
  geopoly/math/percentile/rtree/session/snapshot/…）。node 的 gyp 要 RBU 宏 ⇒ 无法对齐，
  只能文档标注（Debian 同样跳 test-sqlite）。**这是外部调研集"不一定靠谱"的实证**，
  其余结论引用前都要本机复核。
- **R5.5 openssl（🟡 版本差）**：vcpkg 3.6.3 vs node 3.5.8。已有 openssl 行为面 ctest 组
  （§5h）守着，维持现状。
- 状态：⬜ 待用户定优先级（推荐顺序：R5.1 libuv → R5.3 ada → R5.2 zlib 量化 → R5.4/R5.5 入账）
