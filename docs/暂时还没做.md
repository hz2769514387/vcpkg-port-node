## 1. debug 构建的 CI 实测 ★ 用户已决策必做

- **现状**：CI 全部 triplet 都是 `VCPKG_BUILD_TYPE release`（省盘省时）。
  debug 从未被 CI 编译过。
- **风险**：V8 debug 构建体积/时长约翻倍；路线 B 的补丁（PCH、`/std:` 分语言发出、
  rsp 文本处理）在 debug 口径下未验证过。debug-only 的编译错误完全可能存在。
- **绕超时方案（用户提议）**：CI 的 6 小时超时是单次 run 的限制——
  **两次 push 配置不同**：push A 跑 release 矩阵，push B 只跑 debug 矩阵；
  或用 `workflow_dispatch` 手动触发 debug 专用 job。
- **验收标准**：debug 口径下 node 静态库链接成功 + test 侧消费通过。
- 状态：⬜ 未做（**用户明确说先留着**，2026-10-11）

## 2. arm64 实测（含交叉构建的 host toolset）★ 优先级已提高

- **现状**：arm64 各口径都进了 CI 矩阵，但都是 `allow_failure: true`（Tier 2）。
- **本轮已做**：补丁里写死的 `--target=x86_64-pc-windows-msvc` 与
  `clang_rt.builtins-x86_64` 已参数化 —— 现在由 port 按 `VCPKG_TARGET_ARCHITECTURE`
  经环境变量 `NODE_PORT_CLANG_TARGET` / `NODE_PORT_CLANG_RT_BUILTINS_NAME` 交接，
  默认值保持 x86_64（不设变量时行为与之前一致）。
- **★ 新识别到的结构性障碍**：arm64-windows 是在 x64 宿主上**交叉编译**，而 node 的
  构建期工具（`mksnapshot` / `torque` / `node_js2c` 等）要在构建机上**跑**，必须是宿主
  编译（x64）才能执行。现在 `configure.py` 的 `make_global_settings` 只给了
  `CC`/`CXX` 一套（没有区分 host / target toolset），于是 host 工具会被编成 arm64 →
  在 x64 构建机上**跑不起来**。这不是补丁能解决的：要么给 gyp 单独的 host toolset，
  要么在有 arm64 宿主（或能跑 arm64 二进制的仿真环境）上原生构建。
  **升级 Tier 1 之前必须先解决这个。**
- **试过又撤掉的修法**：给该 triplet 加 `-DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY`（交叉编译的常规做法，能过 "跑不了 arm64 exe" 那一关），但它有更坏的副作用 —— try_compile 不再链接，于是**库存在性检查全部误报成功**，实测 brotli 因此加了 `-lm` 而挂
  （`lld-link: could not open 'm.lib'`）。撤掉，宁可挂在"一眼能懂"的地方。
- 状态：⬜ 未做（不阻塞发版；但已从"理论可过"降级为"有已知障碍"）

## 5e. ada 少了 simdutf（依赖特性差异）★ 用户提出

- 现状：node 的 `deps/ada/ada.gyp` 用 `ADA_USE_SIMDUTF=1`（配 v8 的 simdutf 做 UTF-8 校验），
  而 **vcpkg 的 ada-url port 没有 simdutf 这个 feature** → 我们链接的那份 ada 少了 SIMD 加速。
- 影响：**结果一致，只是性能 delta**（ada 自己的测试两种路径都跑）；不是正确性问题。
- 我们这侧修不了（feature 不在 ada-url port 里，消费端无法给别人的 port 加 feature）。
  可选路径：① 向上游 vcpkg 给 ada-url 提 feature；② 自己 overlay 一份 ada-url port（本仓库
  目前不做多 port，见 §13.4）；③ 接受并记录。
- 其余依赖的同类审计结论（有实测探针）见 `docs/架构重审-路线B落地实验.md` §15.10 ——
  其中 sqlite3 的 column metadata 与 `*_STATICLIB` 那一族经探针实测**不是问题**（虚警）。
- 状态：⬜ 已知差异，发版前只需在 README/usage 里写明

## 6. node.exe / npm / corepack 等工具的输出

- 状态：✅ **已实现**（2026-10-11，作为 port 的可选 feature `tools`）
- **按 vcpkg 规则落实的分工**（参考 directx-dxc / vtk / qtbase 这些"复杂 port"）：
  * 可执行文件 → `<prefix>/tools/node/`（**不是** share/；share/ 放 cmake 配置、usage、数据）；
  * 由 `node-config.cmake` 导出变量给使用者（directx-dxc 导 `DIRECTX_DXC_TOOL` 同一套路）：
    `node_EXECUTABLE` / `node_TOOLS_DIR` / `node_NPM` / `node_NPX` / `node_COREPACK`；
  * 布局照 node 官方发行版：可执行 + `node_modules/{npm,corepack}` + 垫片
    （POSIX sh 与 Windows .cmd 两套都装，只用相对路径定位，不依赖 PATH）；
  * **triplet / toolchain 不输出** —— 那是消费端的构建配置，port 不该自带
    （本仓库 test/cmake/ 下有一份可抄的参考）。
- 消费端拿法：`test/vcpkg.json` 里给 node 打开 `tools` feature，ctest 的 `tools` 组会真跑
  `node_EXECUTABLE` / `npm --version` / `npx --version` / `corepack --version`。
