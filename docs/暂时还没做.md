## 2. arm64 实测（含交叉构建的 host toolset）★ 优先级已提高

- **现状**：arm64 各口径都进了 CI 矩阵，但都是 `allow_failure: true`（Tier 2）。
- **本轮已做**：补丁里写死的 `--target=x86_64-pc-windows-msvc` 与
  `clang_rt.builtins-x86_64` 已参数化 —— 现在由 port 按 `VCPKG_TARGET_ARCHITECTURE`
  经环境变量 `NODE_PORT_CLANG_TARGET` / `NODE_PORT_CLANG_RT_BUILTINS_NAME` 交接，
  默认值保持 x86_64（不设变量时行为与之前一致）。
- **★ 新识别到的结构性障碍**：arm64-windows 是在 x64 宿主上**交叉编译**，而 node 的
  构建期工具（`mksnapshot` / `torque` / `node_js2c` 等）要在构建机上**跑**，必须是宿主
  编译（x64）才能执行。现在 `configure.py` 的 `make_global_settings` 只给了
  `CC`/`CXX` 一套（没有区分 host / target toolset），于是 host 工具会被编成 arm64 →
  在 x64 构建机上**跑不起来**。这不是补丁能解决的：要么给 gyp 单独的 host toolset，
  要么在有 arm64 宿主（或能跑 arm64 二进制的仿真环境）上原生构建。
  **升级 Tier 1 之前必须先解决这个。**
- **试过又撤掉的修法**：给该 triplet 加 `-DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY`（交叉编译的常规做法，能过 "跑不了 arm64 exe" 那一关），但它有更坏的副作用 —— try_compile 不再链接，于是**库存在性检查全部误报成功**，实测 brotli 因此加了 `-lm` 而挂
  （`lld-link: could not open 'm.lib'`）。撤掉，宁可挂在"一眼能懂"的地方。
- 状态：⬜ 未做（不阻塞发版；但已从"理论可过"降级为"有已知障碍"）

## 5e. ada 少了 simdutf（依赖特性差异）★ 用户提出

- **事实**：node 把 ada 编成**单个 amalgamated TU**（`deps/ada/ada.gyp` 的 `ada_sources: ['ada.cpp']`，
  里面自带 `ada_idna.cpp`），并配 v8 的 simdutf + `ADA_USE_SIMDUTF=1`。
  我们走 `--shared-ada` 时用的是 vcpkg 的 ada-url，它的 `ADA_USE_SIMDUTF` 是
  **CPM 下载 simdutf** 的实现（vcpkg 里不合适），所以 port 写死 `OFF`。
- **影响**：**结果一致，只是 IDNA/Unicode 转码少了 SIMD 加速**（性能 delta），不是正确性问题。
- **用户指出 ada-idna 有 simdutf feature** —— 属实（`ADA_USE_SIMDUTF` + `find_dependency(simdutf)`），
  但**node 不用 ada-idna**：它的 ada 自带 idna；node 树 `deps/` 下没有独立 idna、源码里无人引用、
  vcpkg 的 `ada-config.cmake` 也不依赖它。⇒ 给 ada-idna 开 simdutf 对 node 无影响，
  而且我们之前声明 `ada-idna` 属于**多余依赖**（已删，见 port 的 vcpkg.json）。
- **要真正补上**：① 上游给 vcpkg 的 ada-url 加一个不走 CPM 的 simdutf feature；
  ② 自己 overlay 一份 ada-url port（本仓库目前不做多 port，见 §13.4）。两者都超出"改自己 port"的范围。
- 同类审计的其它结论见 §15.10（sqlite3 的 column metadata 与 `*_STATICLIB` 经探针实测**不是问题**）。
- 状态：⬜ 已知差异，发版前在 README/usage 里写明即可

## 5g. abseil / highway 无法与 node 在同一个可执行里共存（★ 已知限制，有实测）

- **事实**：v8 用 abseil / highway 的**内部符号**（`container_internal::DeallocateBackingArray`、
  `hash_internal::MixingHashState::kSeed`、`SetMutexDeadlockDetectionMode`…），而且
  `src/node.cc` 也直接 `#include "absl/..."` ⇒ **必须**用 v8 自带那份。
  实测：把 v8 的 abseil 换成 vcpkg 的那份（当时的 patch 0015/0016，已删除）→ 编译期通过、
  **链接期 LNK2019**。⇒ 已撤回，改为"让自带头在 include 顺序上赢"。
- **★ 2026-10-12 补记：那个"让自带头赢"的第一版修法是错的，已被实测否证。**
  当时把自带目录塞进 `--shared-openssl-includes` / `--shared-zlib-includes`，以为
  "configure_library() 按调用顺序 append，给的顺序就是 -I 的顺序"。错在两点：
  ① `configure_openssl()` 在 configure.py 里是**最后**被调用的（2641 行），它给的目录
  必然排在 vcpkg include **之后**；② gyp 对 `include_dirs` 去重只保留**首次出现**，
  所以靠 append 永远抢不到前排。run #17 的 x64-linux / arm64-linux 照旧死在
  `spinlock.cc:71 redefinition of SpinLock::SpinLock(SchedulingMode)`（第 48/1908 步）。
  **现修法**：`patches/0015-configure-prepend-v8-bundled-includes.patch` 在
  configure.py 末尾**整体前插** `output['include_dirs']`；
  再配一条**可执行红线** `ports/node/scripts/redline-include-order.cmake`，
  在 configure 之后立刻断言 `target_defaults.include_dirs` 前两条就是那两个自带目录
  （不写文档、当场变红；正反两个方向都离线验证过）。
  ⚠️ 补丁编号注意：0015 现在是"include 顺序"，不是当年那个"换成 vcpkg abseil"（已删）。
- **影响（对使用者）**：同一个可执行里既有 node port、又链 vcpkg 的 `abseil` / `highway`
  ⇒ 两份同名（含内部符号）实现 ⇒ 冲突（重复定义/未解析符号）。`simdutf` / `zlib` 没有这个问题
  （v8 只用它们的公开接口，已换成 vcpkg 那份 ✓）。
- **我们这侧能做的**：① README/usage 明写这条限制；② 符号审计（T4）本来就报跨库重复

  可以再评估替换（现在两边的内部符号集就不同）。

## 5h. openssl：node 自带那份 → 换成 vcpkg 那份，行为是否一致 ★ 用户提出

- **问**：node 给 openssl 打过补丁吗？现在改成用 vcpkg 的 openssl，会不会行为不一致？
- **答：node 不打 openssl 的源码补丁** —— `deps/openssl/` 下**没有** `patches/` 目录。
  它的定制只有三处，且**共享模式下两处根本用不上**：
  1. `deps/openssl/config/archs/<arch>/{asm,asm_avx2,no-asm}/` 里按架构预生成的头
     （`configuration.h` / `bn_conf.h` / `dso_conf.h` …）—— 只服务于"编自带那份"；
  2. 编自带那份时带 `OPENSSL_API_COMPAT=0x10100001L`（`openssl.gyp`）—— 共享模式下
     node 自己的代码改按 vcpkg 那份头的默认级别（3.6）编，实测能编过；
  3. **`nodejs-openssl.cnf`**：编进二进制后由 `src/node.cc` 用
     `NODE_OPENSSL_CONF_NAME(=nodejs_conf)` **显式**喂给 OpenSSL 去激活 provider ——
     这条路跟用哪份 openssl 无关，是我们这条链路的保险。
- **所以真正会变的只有一件事：vcpkg 那份编了哪些东西。** 逐项比对两边的
  `configuration.h`（`OPENSSL_NO_*` 开关 + `OPENSSL_CONFIGURED_API`）结论是
  **没有能力回退**：
  | 差异 | 方向 | 影响 |
  | --- | --- | --- |
  | 版本 3.5.0 → 3.6.3 | vcpkg 更新 | 小版本前进 |
  | `ec_nistp_64_gcc_128` | vcpkg **多开**（node 那份没开） | 纯性能优化，更好 |
  | `apps` / `docs` / `acvp-tests` / `allocfail-tests` | vcpkg 关掉 | 与 node 的 JS 能力无关 |
  | `fips-post` / `fips-securitychecks` | vcpkg 关掉 | 两边 FIPS 都没开 |
  | `brotli` / `zlib` / `zstd` | vcpkg 关掉 | 只关 OpenSSL 自己的压缩；node 的 `node:zlib` 走它自己的 zlib（本工程就是 vcpkg 的 zlib），不经 openssl |
  | `lms` | vcpkg 关掉 | 3.6 新算法；node 24.21 面向 3.5，本来就没引用 |
  - 另：vcpkg 的 `no-autoload-config` 是**消费端可选**项，我们没开 ⇒ provider 自动加载行为不变。
- **但"比对过"只是文档结论，不是回归保护** ⇒ 新增 ctest 用例
  `coexist-openssl-surface`（`test/coexist/openssl_surface.js`）：真跑算法面
  （`getHashes/getCiphers/getCurves` 覆盖基线）+ 端到端功能（sha256 与 HMAC 已知向量、
  aes-256-gcm 往返、ed25519 签名验签、secp256k1 ECDH、pbkdf2、随机数、
  `tls.createSecureContext()`、TLS 1.3 套件）。**provider 没起来 / 算法被裁掉**
  会以红灯形式暴露，不再靠人记着。

## 5i. Windows 下 node.exe 链接不到静态库（node.gyp 的 WHOLEARCHIVE 路径）★ 2026-10-12 修

- **症状**：`LINK : fatal error LNK1356: 找不到为延迟加载指定的库 lib/node_base.lib`。
- **根因**：`node.gyp` 里 Windows 那两条 `/WHOLEARCHIVE:<(PRODUCT_DIR)/lib/<...>` 是照
  **msvs 生成器**写的（msvs 把静态库放到 `$(OutDir)lib\`）。但 gyp 的 **ninja** 生成器在
  Windows 上 `type_in_output_root` 只有 `executable / loadable_module / shared_library`，
  `static_library` 走 `GypPathToUniqueOutput` ⇒ 落在 `obj/` 下（实测 `obj/node_base.lib`、
  `obj/tools/v8_gypfiles/v8_base_without_compiler.lib`，`lib/` 目录根本不存在）。
  同一文件里 Linux 那侧本来就写的是 `<(obj_dir)/...`，macOS 的 static_library 在 output root，
  **只有 Windows 这一条对不上**。
- **修法**：portfile 里（仅 Windows）把 `node.gyp` 的那两条替换成
  `<(obj_dir)/<(STATIC_LIB_PREFIX)node_base<(STATIC_LIB_SUFFIX)` 与
  `<(obj_dir)/tools/v8_gypfiles/<(STATIC_LIB_PREFIX)v8_base_without_compiler<(STATIC_LIB_SUFFIX)`。
  用 `vcpkg_replace_string` 而不是补丁：两处字符串各自唯一，替换不怕上游改行号。
- **★ 必须放在 `configure.py` 之前改**（第一版我放在后面，白跑 30 分钟）：
  改的是 gyp 的**输入**，而 ninja 文件是 configure.py 内部调 gyp 生成的；而且
  `out/Release/build.ninja` 里**完全没有 `node.gyp` 这个依赖**（gyp 这次没生成
  自更新规则），所以事后改 gyp 既不会触发重新生成、也不会被 ninja 察觉 ——
  替换确实生效了（node.gyp 里已经是新路径），链接照样失败。

## 5l. tools feature 只装了文件、**没导变量**（静默失效）★ 2026-10-12 修

- 症状：消费端 `test/tests/ctest_tools.cmake` 一直是
  `if(NOT node_EXECUTABLE) → 跳过`，**那组用例从来没跑过**；而文档 §6 却写着"已导出"。
- 根因：`node-config.cmake` 里压根没有 `node_EXECUTABLE` / `node_TOOLS_DIR` /
  `node_NPM` / `node_NPX` / `node_COREPACK` —— 只装了文件，忘了导变量。
- 修法：补上（Windows 上垫片给 `.cmd`，POSIX 给 sh）。
- 教训：**"文档说做了" ≠ "做了"**。这类"没导出 ⇒ 整组用例静默跳过"的失效，
  正确的做法是给跳过的分支留一句醒目的 STATUS，并且**不要**让"跳过"变成常态。
- 状态：✅ 已修（2026-10-12）

## 5m. `.cmd` 垫片必须 ASCII-only ★ 通用规则，2026-10-12

- 症状：`npm --version` / `npx --version` / `corepack --version` 三个 ctest 全红，
  报"命令语法不正确"，报错里还跑出了注释里的中文片段（`'corepack}' …`）。
- 根因：**cmd.exe 按 ANSI 代码页（中文 Windows 上是 GBK）读 `.cmd`**，
  UTF-8 的中文注释被切分后，片段被当成命令去执行。
- 规则：**`.cmd` 里一个非 ASCII 字节都不要有**，注释用英文，中文解释放文档。
  （`.gitattributes` 里 `*.cmd text eol=crlf` 只解决换行，解决不了代码页。）
- 状态：✅ 已修（三个垫片改成纯 ASCII，实测 npm 11.19.0 / npx 11.19.0 / corepack 0.36.0）

## 5n. 符号审计第二处"自己比自己"：本 port 自己也在 packages 里 ★ 2026-10-12 修
