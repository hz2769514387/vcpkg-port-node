# 06 · 可行性结论与行动建议

> 基于 [01](01-依赖全景与版本总表.md)~[05](05-特性差异与node-patch深挖.md) 的实测分析，回答核心问题：**把 Node 的 deps 全部 vcpkg 化，有没有可能？**

## 1. 直接回答

**没有可能做到"全量"且"无副作用"的 vcpkg 化；但可以做到"主体可替代、部分 1:1、部分必须保留内嵌"。**

按依赖个数统计（node26 视角 32 项 / node24 视角 30 项）：

| 策略档 | 数量（v26） | 占 C/C++ 依赖 | 代表 |
|---|---|---|---|
| 直接用 vcpkg 现有 port（逐字节 1:1） | 4 | 中 | c-ares、zstd、ngtcp2、nghttp3（需 overlay 去 TLS） |
| 版本一致但 node 带 patch | 2 | 低 | libuv（4 处 backport，含 Win fs-event 越界修复）、brotli（1 处 platform.h 补丁，低风险） |
| vcpkg 可用 + 需固定版本/裁剪特性 | 11 | 高 | openssl、icu、sqlite3、llhttp、nghttp2、simdjson、ada-url、LIEF、libffi、perfetto、hdr-histogram |
| 不可 vcpkg 化（内嵌/生态外） | 15 | — | **v8 及其 entire third_party**、uvwasi、merve、nbytes、ncrypto、postject、amaro、inspector_protocol、crates、5 个 JS 依赖 |

**"全部 vcpkg 化"的两个硬墙**：
1. **V8（含 third_party）**：node 自有分支 + 源码树内嵌依赖，**无 `--shared-v8` 通道**，物理上无法外接 vcpkg —— 仅 V8 一层就代表剩余的 ~15 项中的绝大多数。
2. **node 主创库**（uvwasi/merve/nbytes/ncrypto/postject/inspector_protocol）：vcpkg 无 port、无外部消费场景、且与 node 源码强绑定，自制 overlay-port 收益为负。**注意**：这些库在 configure 中**有 `--shared-*` 通道**（见 [07](07-官方shared机制与发行版实践.md)），"必须内嵌"的根因是 vcpkg 无 port 而非 node 不让外接。

## 2. 三种替代策略对比

| 策略 | 说明 | 覆盖度 | 成本 | 风险 |
|---|---|---|---|---|
| **A. 全内嵌（现状）** | 维持 node 官方 vendored 依赖 | — | 0 | node 官方同步的风险由 node 上游承担 |
| **B. 混合（推荐）** | 1:1 组接 vcpkg + 内嵌其余 | ~60% 的 C/C++ 库可外接，其余内嵌+登记版本清单 | 中（需 overlay 若干版本） | 低（与官方二进制行为差异最小） |
| **C. 全替代** | 所有能找到 vcpkg port 的都替换（含 zlib→zlib-ng、openssl→3.6.3、simdutf→8.2.0 等） | ~75% | 高（大量 overlay + 回归测试） | 高（行为偏移、性能损失、供应链误判） |

**推荐 B**：只把"逐字节零差异"的 3 个（c-ares/zstd/brotli）+ 特性对齐后的 sqlite3 先试点，观察构建集成与测试结果；libuv 因带 4 处 backport（含 Windows fs-event 越界修复）暂不外接；其余维持内嵌。

## 3. 分档行动清单

### 3.1 可直接替换（零/低风险）
| 依赖 | vcpkg 用法 | 注意事项 |
|---|---|---|
| c-ares 1.34.8 | `c-ares` | 不需要 tool feature |
| zstd 1.5.7 | `zstd` | 不需要 tools feature |
| brotli 1.2.0 | `brotli` | 默认 feature 即可；node 带 1 处 platform.h 补丁（仅 IA64 等新平台），主流平台无差异 |
| ngtcp2 / nghttp3 | `ngtcp2`+`nghttp3` | ⚠️ 必须 overlay：去掉 TLS 后端 feature（node 自接 openssl）、nghttp3 去 sfparse 依赖 |
| sqlite3 3.53.4 | `sqlite3[dbstat,fts3,fts5,geopoly,math,percentile,rtree,session,rbu,...]` | 先在 node 的 gyp 里核对宏全集再定 feature 集 |

> ⚠️ **libuv 不在此列**：虽版本号一致（1.52.1），但 node 带 4 处 backport（含 Windows fs-event 越界修复），外接 vcpkg libuv 1.52.1 会丢失这些修复。若必须外接，需 overlay 到含 backport 的版本。详见 [05 §2.3](05-特性差异与node-patch深挖.md)。

### 3.2 可替换但需版本管理（node 领先或 vcpkg 领先）
| 依赖 | 动作 |
|---|---|
| openssl 3.6.3（vcpkg 领先） | 优先接受 vcpkg 3.6.3 并在 crypto 全量测试中回归；若坚持与 node 官方 3.5.9 一致则 overlay 固定 |
| simdutf 8.2.0（vcpkg 领先） | v8 层，不拆（保持内嵌） |
| llhttp / nghttp2 / simdjson / ada-url / LIEF / libffi | overlay-port 固定 node 版本（见 [04 §3](04-vcpkg缺失与overlay-port方案.md)） |
| perfetto / hdr-histogram | 不变更：perfetto 随 v8 同步内嵌；histogram 若 node26 需 0.12.0 则 overlay |
| icu | 除非接受体积，否则保持 icu-small 内嵌 |

### 3.3 必须内嵌（vcpkg 化无意义或不可能）
- **v8 全树** + third_party（abseil-cpp/simdutf/highway/dragonbox/fast_float/fp16/rapidhash-v8/jsoncpp/siphash/utf8-decoder/wasm-api/ittapi 等）
- node 主创：uvwasi、merve、nbytes、ncrypto、postject、inspector_protocol
- amaro（WASM）、crates（Rust）、全部 JS 依赖（npm/undici/acorn/minimatch）
- zlib（推荐内嵌；替代论证见 [05 §2.1](05-特性差异与node-patch深挖.md)）

### 3.4 供应链管理建议（不必"全外接"也能达成管理目标）
- 为**内嵌库**建立 vendored 版本清单（`deps/README.md` 式登记表）：库名 / 版本 / vendored commit / 对应 vcpkg port（若有）/ 差异摘要 —— 替代"必须 vcpkg 化"才能追踪版本的目标。
- 对**采用 vcpkg 的库**用 baseline 固定 2026-07-29 快照，锁定可复现构建。

## 4. 风险清单（若推进 vcpkg 化）

1. **RTL/ABI**：node 的 gyp 编译默认 /MD（Windows）；vcpkg triplet 必须选对（`x64-windows`），否则链接期符号冲突。
2. **行为差异**：openssl 3.6.3、ada-url 3.4.4、zlib 无 SIMD —— 三类都可能导致 `node:crypto` / `URL` / 压缩基准与官方二进制存在差异，**必须建立行为回归基线**。
3. **ada-url simdutf feature 缺失**（[05 §2.8b](05-特性差异与node-patch深挖.md)）：node 启用 `ADA_USE_SIMDUTF=1` 做 IDNA 转码，vcpkg `ada-url` port 无此 feature → 替换会丢失 SIMD 加速。overlay 需同时加 simdutf feature + 固定 simdutf 版本。
4. **v8 内部一致性**：simdutf/simdjson 的 node 版本由 v8/内部代码引用（如 `process.versions.simdutf` 输出），vcpkg 版本若不同会造成版本报告与行为不一致。
5. **补丁传播与"选边站"**（[05 §4](05-特性差异与node-patch深挖.md)）：overlay 打补丁影响 vcpkg 依赖图所有消费者。libuv（14 个依赖者）/brotli（9 个）补丁是纯 bugfix + ABI 不变，风险极低；但 zlib（**248 个依赖者**）/openssl（**198 个**）是枢纽节点，overlay 等于"绑架"整个依赖图 → 不推荐。
6. **许可与合规**：每个库的 LICENSE 与 vcpkg port 一致（绝大多数同许可），但 chromium fork（abseil/zlib）的 NOTICE 文件需保留。
7. **维护负担**：overlay-port 越多，跟随上游的成本越高；"node 领先"的库（llhttp/nghttp2/ada-url）vcpkg 跟进极快，长期看 overlay 是临时的。

## 5. 推荐路线图（若立项）

```mermaid
graph LR
  A[试点：3 个逐字节零差异库外接] --> B[验证构建集成 + 全量测试]
  B --> C{结果?}
  C -- 通过 --> D[扩展: sqlite3 feature 对齐 + ngtcp2/nghttp3 overlay]
  C -- 失败 --> F[回退内嵌, 登记版本清单]
  D --> E[评估 openssl 3.6.3 替换 + brotli 外接]
  E --> G[其余库维持内嵌 + 供应链清单]
```

1. **阶段 1（快赢）**：c-ares / zstd / brotli 外接 vcpkg（逐字节一致或仅新平台补丁）。
2. **阶段 2（难点攻坚）**：sqlite3 feature 集对齐；ngtcp2/nghttp3 overlay（去 TLS）。
3. **阶段 3（风险评估）**：openssl 3.6.3 vs 3.5.9 的 crypto 回归；zlib 维持内嵌或 zlib-ng 论证；libuv 外接可行性评估（需 overlay 含 backport 的版本）。
4. **阶段 4（收尾）**：建立内嵌库版本台账；把"全量 vcpkg 化"目标修正为"供应链可追踪 + 关键库可外接"。

## 6. 一句话结论

> **Node 依赖"全量 vcpkg 化"不可行（V8 树无 shared 通道 + node 主创库无 vcpkg port 是两道硬墙）；"主体 vcpkg 化 + 内嵌登记"可行（约 50% C/C++ 依赖可外接，其中逐字节 1:1 仅 4 个，另有 2 个版本一致但 node 带 patch）。** node 官方提供了 24 个 `--shared-*` 外接通道（见 [07](07-官方shared机制与发行版实践.md)），Debian 已实践全量 shared-deps 但代价是 30+ 条测试 skip/flaky。建议以"供应链可追踪、关键路径低风险外接"为目标，而非追求 100% vcpkg 覆盖。
