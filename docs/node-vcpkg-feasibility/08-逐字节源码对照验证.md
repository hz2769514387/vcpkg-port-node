# 08 · 逐字节源码对照验证（vcpkg downloads vs node deps）

> 方法：从 `C:\work\vcpkg\downloads`（本机 vcpkg 已下载的构建源包）解压 upstream 源码，与 `node-v26.11.1/deps/<对应目录>` 做 `diff -rq`。这一章回答"版本一致是否真的逐字节一致"。
> 对照口径：upstream tag 包 vs node vendored 源码；`Only in node` = node 额外加入的（绝大多数是构建文件 BUILD.gn/*.gyp）；`Only in upstream` = 被 node 省略的（文档/test/m4 等）。

## 1. 六组"版本声称一致"库的实测

| 库 | vcpkg 缓存包 | 声称版本 | 源码差异文件数 | 结论 |
|---|---|---|---|---|
| zstd | facebook-zstd-v1.5.7 | 1.5.7 | **0** | ✅ 源码逐字节一致（仅构建文件差异） |
| c-ares | c-ares-c-ares-v1.34.8 | 1.34.8 | **1**（仅 `.gitignore`） | ✅ 源码一致（.gitignore 非代码） |
| ngtcp2（lib 部分） | ngtcp2-ngtcp2-v1.25.0 | 1.25.0 | **0** | ✅ 源码一致（node 只取 lib+crypto 子集；额外一个生成的 version.h） |
| sqlite | sqlite-autoconf-3530400 | 3.53.4 | **0** | ✅ 源码一致（node 用官方 amalgamation） |
| brotli | google-brotli-v1.2.0 | 1.2.0 | **1**（`c/common/platform.h`） | 🔶 node 有 1 处补丁（见下） |
| libuv | libuv-libuv-v1.52.1 | 1.52.1 | **4**（src 下 4 个 .c） | 🔴 node 含 upstream main 分支 backport（见下） |

### 1.1 brotli 的 node 补丁（platform.h）

```diff
 #if defined(__ia64__) || defined(_M_IA64)
+#define BROTLI_TARGET_IA64
...
-#if BROTLI_GNUC_HAS_ATTRIBUTE(model, 3, 0, 3)
+#if !defined(BROTLI_MODEL) && BROTLI_GNUC_HAS_ATTRIBUTE(model, 3, 0, 3) && \
+    !defined(BROTLI_TARGET_IA64) && !defined(BROTLI_TARGET_LOONGARCH64)
...
-#if BROTLI_GNUC_HAS_ATTRIBUTE(cold, 4, 3, 0)
+#if !defined(BROTLI_COLD) && BROTLI_GNUC_HAS_ATTRIBUTE(cold, 4, 3, 0)
```

- 类型：**编译兼容性补丁**（IA64/新 GCC 的 `model:`/`cold` 属性处理）。影响：新平台（IA64、LoongArch64）与启用 `BROTLI_MODEL/BROTLI_COLD` 宏的调用方；x64/ARM 主流平台无行为差异。
- 结论：**brotli"源码 99.5% 一致"，1 处 node 维护的兼容补丁**。vcpkg brotli 替换是低风险的，但严格说不是逐字节一致。

### 1.2 libuv 的 4 处差异 = upstream main 分支 backport（这才是重点）

| 文件 | 差异本质 | 风险影响 |
|---|---|---|
| `src/unix/fs.c` | `preadv/pwritev` 缓存从 `ssize_t(*f)(...)` 指针直接加载改为 **union 包装**（消除 function-pointer↔object-pointer 转换的严格别名 UB） | 减少未定义行为，属 UBSan/严格编译加固 |
| `src/uv-common.c` | `cpu_infos[i].model` 释放处加 `(char*)` 强转（C++ 兼容性修正） | 编译层面修正 |
| `src/win/fs-event.c` | `uv__relative_path` 从 void 改为**返回 int + 越界检查**；修正**短路径（short path）目录监视的回退逻辑** | **Windows 目录监视的健壮性/崩溃修复** |
| `src/win/tcp.c` | `GetVersionEx` 调用前补 `dwOSVersionInfoSize`/`szCSDVersion` 初始化（`minimal_windows10_version1709`） | Windows 版本探测可靠性修复 |

- 解释：这些差异**不是 node 自行发明**，而是 node 把 **libuv main（1.53.0 预发布/修复分支）的修复反向合入 vendored 的 1.52.1**（node 与 libuv 同 org，发布节奏上有"冰线"。README.chromium 式版本管理不适用于 libuv；node 实际按 tag 取源 + cherry-pick 关键修复）。
- 结论：**libuv"1.52.1"≠ vcpkg 的 1.52.1**。若用 vcpkg libuv 1.52.1 外接，会**丢掉这些修复**（win fs-event 的越界/崩溃修复、fs.c 的 UB 加固）。这正是用户提醒"版本一致不代表完全等同"的教科书级案例。

## 3. nghttp3 的待验证项

- 本机 vcpkg downloads 中 nghttp3 缓存是 **1.16.0**，而 vcpkg port `nghttp3` 声明版本为 **1.18.0**（与 node 一致）——说明本机 vcpkg 仓库已更新 port 但未实际用 1.18.0 构建过（downloads 只留最近产物）。
- 因此 nghttp3 的逐字节对照**无法在本机完成**；但从 ngtcp2 的零差异结果与 nghttp3 的版本号一致推断，风险低。建议后续用 `vcpkg install nghttp3 --dry-run` 触发下载后再验证。

## 4. 验证局限性与严谨性声明

1. **对照对象**：vcpkg downloads 中的包是 **vcpkg port 配置的 REF**（即 vcpkg 声明版本的官方 tag tarball），我们已验证"vcpkg 包↔node 源码"的差异；"vcpkg port 实际构建时是否打了 port patch"（如 zlib 的 OHOS patch、各 port 的 PATCHES 目录）**未做产物级验证**——port 的 PATCHES 会在构建时改动源码，理论上最终产物差异更大。如需更严，应做 `vcpkg install xxx` 后对 installed/include 头文件与 node 头文件做 hash 对比。
2. **libuv 差异溯源**：我们确认了"node 与 upstream tag 不同"，但**没有 git 历史可确认这些改动来自哪个上游 commit**（本机为无 .git 的源码包）。判断为"upstream main backport"是基于改动内容与 node-libuv 协作惯例，标注为推断而非实锤。
3. **node26 侧对照以 v26.11.1 为准**；node24 的同款对照未全部复跑（libuv v24 与 v26 的 vendored 源码基本同步，v24.21.0 的 zlib 为 8002e91、brotli 同样本）。如需 node24 精确结论，可按同样步骤复跑。
