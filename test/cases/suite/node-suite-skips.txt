# Skips for Node.js's own test suite - the single source of truth, read by
# test/cases/suite/CMakeLists.txt.
#
# Format, one per line:  <test name> | <platform> | <reason>
#
#   <test name>   the driver's name for it: no .js suffix, no test/<suite>/ prefix
#                 (test/parallel/test-fs-rm.js is written as test-fs-rm).
#   <platform>    all / windows / linux / macos, optionally narrowed with -<arch>
#                 (windows-x64, macos-arm64). Unrecognized values simply never match, so a
#                 typo makes the case run instead of hiding it.
#   <reason>      mandatory. An entry without one fails the configure step.
#
# Before adding anything here:
#
#   * Upstream already marks cases SKIP or FLAKY in each *.status file and the driver honours
#     those. Listing them again is a duplicate and it freezes upstream's decision.
#   * A test that fails because a file is missing is usually our installation being
#     incomplete - install the file, do not skip the test.
#   * Anything that crashes in native code is our build until proven otherwise. Cross-check
#     against the official Node.js binary first: official passes and ours fails means look
#     here, not at Node.js.
#
# Every entry is re-examined whenever the pinned Node.js version changes.

# -- Cross-checked against the official Node.js binary -------------------------
#
# The residual failures of the first run that put Node.js's own suite on every push
# (2026-10-18: 5003 passed, 5 failed) have been cross-checked the way this file's header
# asks for: upstream's own binary, upstream's own suite, the same GitHub-hosted runners.
#
# Run 41552041717 (2026-11-03, official-binary-baseline.yml, sequential + parallel, on
# windows-2022 and windows-11-arm, node-v26.13.0) fails exactly these five on both runners,
# zero crashes on either: test-child-process-exec-any-shells-windows, test-fs-mkdir-
# recursive-eaccess, test-fs-rm, test-fs-rmSync-special-char-additional-error and
# test-snapshot-typescript. That is the same verdict as run 39201696549 gave at the previous
# pin, and it is what each entry above stands on.
#
# One of the five is gone, and not because the runner changed:
#
#   * test-snapshot-warning was ours by design - Node.js builds the `--trace-warnings` hint
#     from the executable's own name, so it passed for node.exe and failed for node_embed.exe.
#     Fixed rather than skipped: the suite now runs through a POST_BUILD copy of the embedder
#     named `node` (cases/embed), which is what upstream's tests assume throughout. Measured
#     2026-11-03: node_embed prints "Use `node_embed --trace-warnings ...`", the copy prints
#     "Use `node ...`", and the case passes through the copy.
#   * test-fs-rmSync-special-char-additional-error was removed and put back the same day. It
#     passes 3/3 with this port's binary on an ordinary machine, which is not the question:
#     the official binary fails it on both hosted runners, so it belongs in this list. The
#     local pass is the note that keeps the entry from looking unexplained.
#
# Everything here is re-examined when the pinned Node.js version changes, and the
# cross-check is re-runnable from the Actions tab.

# The three below drive icacls to deny themselves access and then assert EPERM. The official
# binary fails them on both GitHub-hosted Windows runners (runs 39201696549 and 41552041717)
# and they pass on an ordinary machine, which is the runner running the job as an account in
# the Administrators group - a deny ACE is not the same obstacle for an elevated process.
test-fs-rm | windows | icacls /deny does not stop an elevated process, so the expected EPERM never comes
test-fs-mkdir-recursive-eaccess | windows | same icacls mechanism; the official binary fails it on the runner and passes it locally
test-fs-rmSync-special-char-additional-error | windows | the official binary fails it on both GitHub-hosted runners (run 41552041717, 2026-11-03) and passes 3/3 on an ordinary machine - the same elevated-account mechanism as the two above

# Exercises whatever shells the machine has - cmd, PowerShell, and any bash on
# PATH - by symlinking each into a directory whose name contains spaces. The
# official binary fails it with exit status 1 for "echo foo bar" on the runner
# (run 39201696549). Already in the symlink skip list, because on a machine
# without that privilege it never gets as far as the shells.
test-child-process-exec-any-shells-windows | windows | depends on the shells installed; "echo foo bar" exits 1 on the runner, for the official binary too

# -- Windows ------------------------------------------------------------------
# The TypeScript compiler emits CRLF on Windows while the fixture expects LF. Upstream test
# bug, and confirmed environment-shaped by run 39201696549: the official binary fails it on
# both Windows runners too. The mechanism is the "line endings in generated output"
# category in docs/node-suite.md, section 4.
test-snapshot-typescript | windows | tsc emits CRLF on Windows, the fixture compares against LF

# The test asserts empty stderr and the environment carries both NO_COLOR and FORCE_COLOR,
# which makes Node.js print a warning about that combination. Measured 2026-10-16 with a
# port-built executable; re-check against the official binary before trusting this entry,
# because an environment difference could just as easily be ours.
test-runner-reporters | windows | NO_COLOR and FORCE_COLOR both present in the run environment

# -- macOS x64 (Rosetta 2) ----------------------------------------------------
# The port's x64 macOS leg builds x64 and executes it on arm64 hardware under Rosetta 2,
# and the process.execve family is unstable there in a way that is not ours to fix: the
# crash lands on a *different member of the same family* depending on the binary.
#
# Evidence, same suite, same runner image, both binaries:
#   * ours (run 39294243423):        test-process-execve-throws CRASHED (Signal: 10 / SIGBUS),
#                                    test-process-execve-socket passed;
#   * official binary (run 39342169919,
#     the official-binary-baseline): test-process-execve-socket CRASHED (Signal: 10 / SIGBUS),
#                                    test-process-execve-throws passed.
#   * ours (run 39351011619):        test-process-execve-on-exit CRASHED (Signal: 10 / SIGBUS),
#                                    the two entries above passing - a third member, on a run
#                                    where nothing else in the suite failed.
# The official binary's native arm64 macOS run has no execve failures at all, so this is the
# Rosetta cell rather than the platform. Which member crashes is nondeterministic, so every
# observed one is listed; if another member of the family crashes there, add it with the same
# reasoning rather than treating it as a new defect. That is what the third line below is:
# the family, not the individual case, is what Rosetta breaks.
test-process-execve-throws | macos-x64 | SIGBUS under Rosetta 2; the official binary crashes the sibling execve-socket there instead (runs 39294243423 / 39342169919)
test-process-execve-socket | macos-x64 | SIGBUS under Rosetta 2; the official binary fails this very case on the same image (run 39342169919)
test-process-execve-on-exit | macos-x64 | SIGBUS under Rosetta 2, a third member of the same family; added under the standing rule above (run 39351011619)
test-process-execve-permission-granted | macos-x64 | SIGBUS under Rosetta 2, a fourth member of the same family; the standing rule above says to add it rather than treat it as a new defect (runs 40130285780 crashed, passed on rerun; 40130285788 crashed)
