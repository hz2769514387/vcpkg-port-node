### 1) Windows：MSVC 收到 clang 风格开关（D8021）

- 现象：`cl : Command line error D8021 : invalid numeric argument '/Wno-invalid-offsetof'`，
  ninja 只到 `[1/4121]`（abseil `cycleclock.cc.obj.ddi`）就停。
- 根因：node `common.gypi` 的 `msvs_settings.VCCLCompilerTool.AdditionalOptions` 把两个驱动的
  开关混在一份里（`-Wno-*` 给 clang、`/bigobj` `/Zc:__cplusplus` `/Zm2000` `/utf-8` 给 MSVC）。
  gyp2vcpkg 把整份抄成 `<目标>_MSVS_FLAGS` → cl.exe 报 D8021。
- 修法：`gyp2vcpkg/generate.py` 新增 `_split_msvc_clang()`，按前缀分流成
  `_MSVS_FLAGS`（`/`）与 `_CLANG_FLAGS`（`-`），共同项两边都带；`project/consume.cmake` 按
  `CMAKE_CXX_COMPILER_FRONTEND_VARIANT` 分别喂给 cl.exe / clang-cl。
- 关键：不能直接丢掉 `-` 那份 —— 本仓库口径"三平台一律 clang"（toolchains/clang-cl.cmake），
  clang-cl 下那些 `-Wno-*` 要有。

### 2) macOS：node_mksnapshot 链接缺 `-framework Security`

- 现象：`[2066/2069]` 链接 `Release/bin/node_mksnapshot` 报 13 个 undefined symbol
  （`_SecCertificateCopyData` / `_SecTrustCreateWithCertificates` / `_kSecClass` …），
  全部来自 `libnode_base.a[166](crypto_context.cc.o)`。
- 排查：整个 mac 解析结果里 `Security` 一次都没出现 → 不是生成器丢的。逐处核实上游 node
  v24.21.0 的 `node.gyp` / `common.gypi` / `deps/ncrypto/ncrypto.gyp`，`OTHER_LDFLAGS` 里只有
  `-framework CoreFoundation`，**没有 Security**（上游已迁 CMake/GN）。是 gyp 事实本身缺一件。
- 修法：`project/consume.cmake` 里 `if(APPLE AND name STREQUAL "node_base")` 补
  `target_link_options(${name} ${_kw} "-framework Security")`（`${_kw}` 静态库为 PUBLIC，
  随 INTERFACE_LINK_OPTIONS 传到 node_mksnapshot / node）。

### 结论一：两条假设被否证

- **上游没有自研 CMake**。`BUILD.gn` 头部原文写明 GN "is NOT the build system used
  for building official binaries"；源码树内 `deps/*/CMakeLists.txt` 是依赖库自带的。
  官方入口是 `Makefile` + `configure.py` + gyp。→ **不能"直接用上游 cmake"**。
- **gyp 自带 cmake generator 不可用**：`tools/gyp/pylib/gyp/generator/cmake.py` 头部
  自述 experimental / 仅 Linux / "should not be relied on for building"。
  → **自研 gyp2vcpkg 翻译路线必要且正确**。

### 结论二：二进制取配置可去掉，且原配置本身是错的（决定性实验）

- 官方二进制导出的 `env/*.json` 里 **19 个 `node_shared_*` 全是 `false`**
  —— 这是"为 bundling 而设"的官方二进制口径，而 vcpkg 要用系统依赖，**值本身错误**。
- gyp 语义（`node.gypi:178-250`）：`node_shared_x=="false"` 时**主动**把
  `deps/x/x.gyp` 加进依赖树。
- **实验**：在纯源码上用 `configure.py --dest-os=win --dest-cpu=x64` + **18 个
  `--shared-*`**（注意：zstd/ada/simdjson/simdutf/nghttp3/http-parser 的选项
  **在 `configure.py:327-587` 确实存在**，此前误判为不支持）→ 18 个 shared 转 `'true'`。
- 喂给 gyp2vcpkg 跑完整三步后对比：
  - bundled 源文件：`deps/uvwasi` 9→**0**、`deps/merve` 1→**0**、`deps/nbytes` 1→**0**；
  - `deps/` 引用合集：**20 → 5**（保留的 5 个逐一核实为必需：cares/uv 仅 include、
    inspector_protocol/crdtp 是 node 自身源码、ncrypto、postject、googletest 仅 include）；
  - target 数：merve / nbytes / ncrypto_engine / uvwasi **4 个从依赖树消失**。
- **三平台交叉验证**：`--dest-os=linux` / `--dest-os=mac` 均可在 **Windows 本机**生成配置，
  各自 `resolve` **110 targets 全部成功**。mac 会在 gyp 步报
  `No Xcode or CLT version detected!` 但 **config.gypi 已先写出**（`configure.py:2613`
  在调 gyp 之前 write）；缺的 `xcode_version` 在 `common.gypi`/`node.gyp`/`node.gypi`/
  `v8_gypfiles` 里**零引用**，不影响求值。
- **注意**：`--shared-openssl` 与 `--openssl-no-asm` **互斥**（configure.py 直接 ERROR）。

### 结论三：推翻第一轮 macOS 修复的真因（重要）

- `collect.py:107-120` 的 `_extract_config()` **只读 `td["configurations"][cfg]`**，
  而 gyp 的 `libraries` 挂在**目标顶层** → `generate.py` 的 `_list_of(d,"libraries")`
  读 `d["config"]["libraries"]`，**永远读不到**。
- 实测 mac 解析结果：`node_base` 顶层 `libraries = ["-framework CoreFoundation
  -framework Security"]`，`OTHER_LDFLAGS` 只有 `-framework CoreFoundation`。
  上游 `node.gypi:252-258` 的 mac 分支**明确带 Security**（注释：needed for --use-system-ca）。
  → 第一轮"上游没有 Security"的结论**错了**，`consume.cmake` 的硬编码补丁掩盖了真因。
- **影响面（三平台实测）**：win **12** 个目标有顶层 `libraries`（`node_base` 缺
  Dbghelp/Psapi/Winmm/Ws2_32，`node` 缺 ole32/iphlpapi/psapi/shell32/userenv/uuid 等）；
  linux **15** 个（`node` 缺 `-ldl -lm`，工具链缺 `-ldl -lrt`）；
  mac **13** 个（node/node_base/libnode 等缺两个 framework）。
- 附带：`'-framework CoreFoundation -framework Security'` 是**一个字符串含两项**，
  `generate.py:344` 只对 `OTHER_LDFLAGS` 做了 split，**`libraries` 字段没有**。

### 结论三：用 vcpkg 库替换 node 内置库，技术上成立

  ——它会**真的编译探测**头部版本。
- ncrypto 用 `OPENSSL_VERSION_PREREQ(3,5)` 前向比较 + `ncrypto.gyp` 按

### 结论四：闭环验证 seed_gypi.py —— 必须连 target_defaults 一起换

`configure_library()`（configure.py:1925）把 `--shared-*-includes` 写进
**`target_defaults.include_dirs`**（不是 `variables`）。实测多库后：
```
target_defaults.include_dirs = [<vcpkg>/zlib, <vcpkg>/libuv, <vcpkg>/openssl]
target_defaults.libraries    = [-lz, -luv, -lcrypto, -lssl]
```
与 `env/win-x64.json` 的 `{variables, target_defaults}` **同构**。
→ configure.py 输出可**整个替换** env/*.json，一步解决"配置来源+依赖归属+头库路径"。
**陷阱**：只取 `variables` 会丢 include（我第一轮就踩了）。

### 结论五：node 的 zlib 补丁是实质风险

19 个 patch 分类：**8 个涉及 node 用到的核心**（0001-simd / 0002-uninitializedcheck /
0003-uninitializedjump / 0007-zero-init-deflate-window / 0011-avx512 / 0012-lfs-open64 /
0013-arm-cpu-feature / 0017-deflate-zmemzero），其余是 **minizip（node 不用）**、
infcover（仅测试）、cmake（无关）。

**关键**：上游 madler/zlib **1.3.2 不含** 0002/0003/0017（Chromium/oss-fuzz 的内存安全修复）
与 0001/0011/0013（SIMD 优化）。→ 直接换 vcpkg zlib **会丢 4 个内存安全修复**。

### 结论六：★ simdutf 双份 + COMDAT 折叠风险（实测抓到的最大隐患）

- v8 内嵌 `deps/v8/third_party/simdutf` = **6.4.0**（README.chromium）
- vcpkg `simdutf` = **8.2.0**
- 两版符号**完全同名**，且都是 **`selection 2 (pick any)` 的 COMDAT**
  （如 `??_7implementation@haswell@simdutf@@6B@`、`?validate_ascii@...@haswell@simdutf@@...`）

→ 链接器**任意挑一份**，两版差两个大版本 → **不稳定行为**（能跑但行为可能不一致）。
**注意**：名字空间 `simdutf::` **不阻止 COMDAT 折叠**（mangled name 相同），
所以用户"名字空间隔离的可例外"这条判据在 COMDAT 场景下**不成立**。

**两次误报的教训**：第一版检测器把 COMDAT 当强符号 → 904 个假阳性；
第二版过滤过头 → 假阴性"无风险"。**必须区分强符号 vs COMDAT，并单独评估 COMDAT 同名折叠。**

### ★★ 确定缺陷 2：`libnode` 的导入路径多一个 `lib`（Linux/macOS 消费端必挂）

- gyp 命名规则：`tools/gyp/pylib/gyp/generator/ninja.py:1844-1850`
  （`prefix=="lib"` 时 `StripPrefix(target,"lib")` 再补前缀），
  `ninja.py:30` 非 win 的 `STATIC_LIB_PREFIX="lib"`、`:2038` 只有 win 置空。
- node.gyp:16-18 注释自己写明："Gyp will prefix this with `lib` if this name does not start with `lib`"。
- → target `libnode` 的产物是 **`libnode.a`（POSIX）/ `libnode.lib`（Windows）**。
- 而 portfile 生成 node-config.cmake 时非 Windows 走 `set(_node_pre "lib")`，
  `IMPORTED_LOCATION` 算成 `"lib" + "libnode" + ".a"` = **`liblibnode.a`** → 不存在。
  消费端 CMake 报 "imported target … references the file … but this file does not exist"。
- 影响：x64-linux / arm64-linux（`allow_failure: false` → 整轮红）+ x64-osx / arm64-osx。
  Windows 恰好对（前缀为空）。
- 修法（照抄 gyp 的 StripPrefix 语义）：

```cmake
foreach(_a IN LISTS _node_all_archives)
    if(VCPKG_TARGET_IS_WINDOWS)
        set(_node_file "${_a}.lib")
    else()
        string(REGEX REPLACE "^lib" "" _node_stripped "${_a}")
        set(_node_file "lib${_node_stripped}.a")
    endif()
```
